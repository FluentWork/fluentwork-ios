## 本轮做了什么（三件）

### 1. D15 — 3 处上行发送失败的 `return nil` 不再终止进程级的上行泵

**它是 D14 的另两条路径。** D14 修的是 `.failed` 分支（引擎报错），而 `audioEventPump` 里
另有 **3 处** `catch { dispatch(.failed); return nil }`——触发是**发送**抛错：

| 行（改动前） | 触发事件 | 抛出的调用 |
|---|---|---|
| `:480-483` | `.speechStarted` | `sendSpeechBoundary(started: true, …)` |
| `:537-540` | `.speechEnded` | `sendSpeechBoundary(started: false, …)` |
| `:551-554` | `.pcmChunk` | `sendAudioPCM(data)` |

`return nil` 跳出的是 `for await event in audioEngine.events()`——**进程级的流**。
后果与 D14 逐字相同：泵死后本次进程内所有后续会话没有上行，房间卡「连接中」，
10 秒后报「连接超时」，**错误信息指向网络**。而三个发送点覆盖上行**全部**三类报文，
`.pcmChunk` 还是每帧路径（约 86 帧/秒）——是最可能先失败的一条。

**修法**：`return nil` → `speechCaptureGate.abort()`（先关闸，后派发）。

**关键发现：抑制不需要新结构。** `23_` §7 说这条要先定「每会话报一次」的语义，否则
`.pcmChunk` 会把一次断连放大成 86 次/秒的 `.failed`。实施时发现**闸门本身就是抑制器**：
`abort()` 关闸后每个 `.pcmChunk` 都被 `takeForwardDecision()` 拒绝**且计入 `droppedOutside`**，
`.speechEnded` 也被 `guard isOpen` 挡住。所以**不需要新类型、不需要新标志位**。
实际语义是「**每句话报一次**」而非「每会话一次」——而这更准（每次尝试是独立的失败）。

**先红**（逐字，`SpeakingRoomSessionWiringTests.swift:520`）：
```
✘ Test aFailedUplinkSendDoesNotRetireTheProcessLifetimePump() recorded an issue at SpeakingRoomSessionWiringTests.swift:520:5: Expectation failed: store.state.speakingRoom.phase == .aiSpeaking
↳ store.state.speakingRoom.phase == .aiSpeaking → false
↳   store.state.speakingRoom.phase → .connecting
✘ Test aFailedUplinkSendDoesNotRetireTheProcessLifetimePump() failed after 1.086 seconds with 1 issue.
```
5 段断言里**前 4 段改动前就通过**（含「失败仍要被报出来」那一半），只有第 5 段
（会话二能否被 `.captureFirstBuffer` 打开）失败——**精确隔离了坏掉的那一半**。

**测试设计**：会话二**不能**用 `makeSessionLive`（它绕过泵，用了就永远绿），
必须走真实路径：`socketReady` + 引擎的 `.captureFirstBuffer`。

  逐字同形的 `catch`。**判据：修完一处 `return nil` / 一处守卫，就 grep 同形状的兄弟。**
  本次靠 `grep -c` 精确数到 3（确认不是 4 也不是 2），才敢用 `replace_all`。

  `abort()` + `takeForwardDecision()` 已经构成完整抑制，且**自带计数**。
  **判据：想加去重结构之前，先问「已有的闸门/状态是否已经表达了这件事」。**
