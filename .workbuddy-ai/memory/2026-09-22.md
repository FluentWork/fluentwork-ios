`dispatch(.aiFirstAudioChunk)` 与 `markTurnOnce("ai_first_chunk")` / `markFirstResponse` 都在
`ttsCoordinator.onAudioFrame` **之前**。被丢弃的帧也会把会话推进到 `.aiSpeaking` 并污染 `first_response_ms`。
`swift test` 日志原文即证据：同一 `sequence: 1` 先记 `timing_ai_first_chunk` + `timing_first_response`，

**其余要点**：
- D2 传输层 `BargeInAudioGate` 是**序号水印**：`markInterrupted()` 取 `maxObservedSequence`，

- D5 `ai.tts.start` 把 `voice_id`/`sample_rate`/`codec` 当**必需**字段解码，而客户端从不消费它们；

- D4 `.waitingUser` 打断既不停播也不发 interrupt（`SpeechSessionMachine.swift:110-114`），`08_` §5.1 已记、未修。
- 唯一需要后端配合的收尾 = `03_` 的 **Stage 3**（帧自带 `turn_id`），即甲 `04:395` 唯一可取的一条。

## 第三张票：缺必需字段的解码失败要点名字段（同日晚）

**提交**：`bf266b6` — `fix(networking): 缺必需字段的致命解码失败要点名字段`（6 files, 277+/6-）。

**缺陷**：`WSControlFrameCodingError.missingField` 是**死码**（全仓无 throw）。缺必需字段抛的是
`KeyedDecodingContainer` 的裸 `DecodingError.keyNotFound`，落进 `handle(message:)` 里
`catch let error as WSControlFrameCodingError` 旁边的泛化 catch，走 `error.localizedDescription`
→ NSError 桥接的 "The data couldn't be read because it is missing."。
而 `describe(_:)` 的注释声明它存在的理由正是「让**致命**解码失败不退化成桥接文案」，
并明说 `missingField` 是「必须保住可读信息」的那个 case。**声明的目的可证明地未被满足。**

**改法**：新增 `WSControlFrameCodingError.classify(_:)` 只认领 `keyNotFound` →
`.missingField(key.stringValue)`（线上名）；`WSControlFrameCodec.decode` 用它归类。
失败策略不变（仍致命）。归类放 codec 而非 `init(from:)`：枚举 `init` 必须恰好给 `self`
赋值一次，抽辅助方法要把 115 行 switch 重写成静态工厂，代价不成比例。

**门禁**：`swift test --disable-sandbox` **582 tests / 28 suites 全通过**（原 580）；
Debug build `BUILD SUCCEEDED`。说明见 `docs/70_tts_wss_refactor/13_*.md`。

### 本票最有价值的产出：D5 被读码推翻，需重判

原本要修 D5（「解码必需的字段，是客户端从不消费的字段；缺一个就断连」），读码后**两处立论不成立**：

1. 「`voice_id`/`sample_rate`/`codec` 没有任何消费者」**不准确**——三者都在
   `SpeechSessionMiddleware.swift:780-782` 作为 `tts_start` 的埋点属性被读走。
   准确说法是「没有任何代码**按它们的值分支**」。
2. 「同一条推理没被应用到字段缺失」**不成立**——作者在 `handle(message:)` 注释里**画过线**：
   未知 `type` = 版本差异（跳过），缺必需字段 = 契约违规（失败）。是画过线的，不是漏改。

**决定性事实（基线遗漏）**：冻结的 `Shared/FluentWorkCore/Resources/Schemas/wss-control-frames-v2.json`
写着 `aiTTSStart.required = ["type","turn_id","voice_id","sample_rate","codec"]`。
**客户端的严格与后端自己发布的契约逐字一致**，不是擅自加严。

→ D5 从「客户端加严」重判为**失败策略**问题：一个只用于打日志的字段缺失，代价是整条会话拆掉。
三个可选方向（保持现状 / 只对无分支消费的字段宽松 / 整帧宽松）待产品+后端共同决定。
已在 `10_事实基线与缺陷清单.md` 的 D5 条目加「修订（2026-09-22）」块，并在 `13_` §7 展开。

### 可复用的排查手法（本票验证有效）

- **注释声明 vs 代码行为**：`describe(_:)` 的注释声明了目的，而代码路径到不了它。这类缺陷
  在「注释写得很认真的仓库」里最值得查——注释就是可验证的规格。**拿注释当断言去反查可达性。**
- **死码的三种表现**：声明的 case 无 throw、声明的分支无生产者、声明的入口无调用点
  （第三种的先例见 `07_` §2 的 `AudioPlaybackGate`）。查 `Grep` 一个符号的 `throw` / 赋值点。
- **既有测试只钉「会不会死」、不钉「说什么」时，文案类缺陷会长期存活。**
  `receiveLoopStillDiesOnAMalformedControlFrame` 就是这样。断言要落在操作员实际读到的字上。
- **schema 是判断「客户端是否擅自加严」的唯一依据**。`Shared/FluentWorkCore/Resources/Schemas/`
  下的 JSON 是镜像自 `fluentwork-infra` 的冻结契约，`PackageBaselineTests` 钉住它。
  判断「某字段该不该必需」时先读它的 `required` 数组，别从「有没有消费者」推。

## 第四张票：D3 一次 barge-in 只发一次 interrupt（同日晚）

**提交**：`bfc8fc2` — `fix(speech): 一次 barge-in 只发一次 control.interrupt (D3)`（5 files, 250+/2-）。

**缺陷**：`control.interrupt` 两个触发点都经 `submitTranscript("__interrupt__")`（不幂等：
`transport.markInterrupted()` + `send(control: .interrupt)`）：
1. `SpeechSessionMiddleware.swift:470-472`（pump 的 `.speechStarted`，**在 start 之前**，对）；
2. `SpeechSessionMachine.swift:106`（`.aiSpeaking` barge-in 臂）。

**第二次必定晚于 start，是结构性事实**：`.vadSpeechStart` 全仓只有一个派发点
（`SpeechSessionMiddleware.swift:482`），而它在 `sendSpeechBoundary(started: true)`（`:476-480`）
之后才 dispatch。2026-09-12 把顺序修在了 pump，状态机那一份没修。

**改法**：把 `.aiSpeaking` 的 arm 按事件拆成两条——`vadSpeechStart` 只 `.stopPlayback`；
`holdStart` 保持 `.stopPlayback + .sendInterrupt`。判据是「**谁能保证顺序**」：pump 能
（它 `await` 了发送）；`.sendInterrupt` 是 `.fireAndForget`，排不出顺序。

**门禁**：`swift test --disable-sandbox` **584 tests / 28 suites 全通过**（原 582）；
Debug build `BUILD SUCCEEDED`。说明见 `docs/70_tts_wss_refactor/14_*.md`。

### 本票最有价值的产出：一个反复出现的模式

**「同一个决定被两个地方做」+「测试只覆盖了没有生产者的那条路」= 缺陷长期存活。**

- 状态机测试与接线测试都断言 barge-in 的 interrupt，但**接线那条直接 `dispatch(.holdStart)`、
  绕过 pump**，于是钉住的只是状态机那一次。**VAD 路径（唯一有生产者的那条）的计数一直是空白。**
- 与 D1 的教训同构：D1 那条测试也是「看起来在验证 A，实际验证的是 B」。
- 通用手法：**看到「同一件事有两个实现点」，先问「测试覆盖的是哪一条」，再问「哪一条有生产者」。**

### 另一条可复用手法：判据 = 「谁能保证顺序」

本次不靠「谁先想到」或「谁看起来更该负责」，而是问：**这个副作用的正确性依赖时序，
而哪个调用点能真正保证那个时序？** pump 能（`await` 了发送），状态机不能（fire-and-forget）。
这条判据把「两处都做」的模糊状态一次消掉，且不引入新状态。

### 新发现（未修，已记录）

- **`.holdStart` 在生产代码里没有任何派发点**（全仓仅测试派发）。相关四条 arm 是
  「测试在养的死路径」，同 `07_` §2 的 `AudioPlaybackGate` 类（不是没人调用，是接不上）。
- **pump 的 barge-in 判定存在窄窗口**：`phaseBox.get() == .aiSpeaking` 与状态机原判定
  读同一值但在不同时刻，中间隔两次网络 await。改动前该窗口会补发一次 interrupt（但按上述
  必定晚于 start，同样无效）；改动后不发。**要真正关掉，判定条件须换成跨 await 稳定的信号
  「是否有在飞的 TTS 轮次」**——协调器在 `ai.tts.start` 时即知，早于相位翻转。与 `07_` §2 /
  D2 / Stage 3 同轴，属音频路径（High-Risk #1），建议单独立项。

## 第五张票：D4 `.waitingUser` 的 barge-in 必须停播（同日晚）

**提交**：`ddee3ae` — `fix(speech): .waitingUser 下的 barge-in 必须停掉残留音频 (D4)`（6 files, 365+/7-）。

**缺陷**：`.waitingUser` 下用户开口时不停播。该相位**完全可能**还有声音在播——TTS 是
burst 到达的（`14_` 引的真机数据：276 帧 / 27.6 秒音频在 88ms 内送达），`ai.turn.end`
与「声音播完」是两件不相干的事。而 `.processing/.evaluation` 那条 arm 的注释
（`:96-99`）明确把停播交给了打断：「barge-in stops it on both paths that mean it —
from `.aiSpeaking` and from this phase」。实际有三条路径，`.waitingUser` 是第三条。
pump 也帮不上忙：它的 barge-in 判定是 `phaseBox == .aiSpeaking`。

**改法**：把 `.waitingUser` 与 `.processing/.aiAnswer` 共用的合并 arm 拆成两条。
只给 `.waitingUser` 加 `.stopPlayback`，**不加** `.sendInterrupt`——能走到 `.waitingUser`
的路径上 `ai.turn.end` 都已到达，服务端这一轮已结束，没有可打断的流；剩下的是本地
播放器里排着的音频。与 `.evaluation` 那条 arm 的政策一致。
`TTSPlaybackCoordinator.onInterrupt` 的 `interruptNow()` 是**无条件**调用的，故
`turnID == nil` 时仍会清空播放器缓冲（这是本条能成立的关键事实）。

### 本票最有价值的产出：`effects.isEmpty` 在这个状态机里几乎总是错的断言

新测试第一版写 `#expect(effects.isEmpty)`，红了而**代码是对的**。原因是 `reduce` 在
返回前会对每次相位变化插入一条 `trackTransition`（`SpeechSessionMachine.swift:342-357`）。
`effects` 只要相位动过就不为空。

同文件里 `recordingTimedOutFromWaitingUserIsNoOp`、`evaluationTimedOutFromWaitingUserIsNoOp`
也用 `isEmpty`——它们对，是因为**前提是相位不变**。**改相位又断言 `isEmpty`，一定红。**
断言应写成「不含 X / 不含 Y」。

### 另一条：既有测试的夹具在骗人（与 D1 同构）

`08_` §5.1 早就记录过 D4（「属于状态机（高风险区），建议单独立项」），两次判断都对、
两次都没落地。原因之一：**`.waitingUser` 那条 arm 的 effects 从没被断言过。**

### 决策：删，不是「补一道兜底」

## 第十张票：D11 —— 已知但无人接的控制帧必须留痕（`de19195`）

### 先红

`audioChunkControlFrameLeavesATrace`（`TransportRoutingEquivalenceTests.swift:202`）。
改动前 `CapturingTracker` 收到的是 **`[]`** ——一条都没有。注意另一半：
`recorder.actions.isEmpty` 那一句是**通过**的，它确认了「这类帧确实不产生动作」。
失败点落在 `trace != nil`，不是落在「事件名写错了」。

### 缺陷的形状（值得记）

同一个高度上有两个方向相反的对照：

| 情形 | 留下什么 |
|---|---|
| **未知** type（如 `ai.tts.audio`） | `transport_control_frame_ignored`（传输层对未知 type 发 `unsupportedControlFrame` 诊断） |
| **已知、但没人接**（`ai.audio.chunk`） | **一条都没有** |

`unsupportedControlFrame` 只对**未知** type 触发，所以「已知但没人接」是唯一无声的一类
——而它恰好是「音频」那一类。

### 风险不是活的（关键事实）

后端 `voiceproto/frames.go:21` 是 `ai.audio.chunk` 的**唯一**出现处；`frames_test.go:445-447`
的冻结断言记它「no producer, no consumer, no test, **on either side of the wire**」；
`58_` 实现说明记「全仓再无一处引用 —— 连测试都没有」；V2 设计（`51_` §:169）明确「❌ 不加」。

所以**不补播放**，只补可见性。补播放等于给一条不存在的路修路。

### 改法与两处有意不做

- 给 `.aiAudioChunk` 注册**只上报**的 handler，track `tts_audio_chunk_ignored`（`type` + `sequence`）。
- 新事件名而不是复用 `transport_control_frame_ignored`：后者的含义是「我们落后了」，
  两者方向相反，混进同一个查询会让更值得看的那条找不到。
- **不**把这类帧计进 `ttsTrace.audioFrameCount()`——那个数字是诊断静音的关键，混进「没播的通知帧」会污染它。
- **不**动 `SocketTransportEventMapper`——`.aiAudioChunk` 的正确映射**就是没有动作**；塞进 mapper 会破坏「映射可单独断言」。

### 本次更值得留下的：把「没人接」变成能被判读的名单

`unownedControlFramesChangeNothing` 原来是一串**没有理由**的类型。一张「没人接」的名单
如果不写理由，下一个人分不清某一项是**有意忽略**还是**漏了**——D11 就是这样：它在这张名单
里待过，而没人说得清它为什么在这。**名单本身没错，错在它没有可判读的内容。**

let classified = Set(unowned.map(\.frame.wireType)).union([.error])
let unownedByTable = Set(WSControlFrameType.allCases)
    .subtracting(Set(TransportRoutingEquivalenceTests.ownedTypes))
#expect(classified == unownedByTable, ...)
