**版本**：V1.0

**上游真源**：`fluentwork-meta`

---

## 一、这份文档解决什么问题

本仓不复制整份 PRD，也不复制整份 iOS 技术文档。

这份文档只做入口索引：

1. 当前第一波 iOS 开发对应 PRD 的哪些模块
2. 当前第一波 iOS 开发应重点看的技术文档章节
3. 当前第一波明确不做什么
4. 当前 GitHub issue / Epic 应按什么顺序推进

如果这里与 `fluentwork-meta` 冲突，以上游为准。

---

## 二、第一波的目标

第一波只聚焦下面这条主链路：

1. 用户进入说的房间
2. iOS 创建 session
3. iOS 用票据连上 WSS
4. iOS 与 backend 完成至少一轮最小对话
5. 会话结束后可查看最小 review 状态

也就是说：

> **第一波目标是把“说 -> 回顾状态可见”这条最小链路打通，而不是把全部页面和模块一次做完。**

## 六、第一波的代码边界

### 当前应该优先改的区域

1. Root Store / AppState / DI baseline
2. SocketTransport
3. APIClient
4. 说的房间状态接线
5. speaking room 最小 UI 壳
6. review 轮询状态

### 当前不应该抢先展开的区域

1. 每日一读完整页面
2. 闪测全链路
3. 语料库页完整体验
4. 订阅入口
5. 发音评测
6. 与第一波无关的广泛目录重构

---

## 七、必须遵守的禁区

1. 不修改人写的 `SpeechSession` 状态机本体
2. 不随意重构 AudioEngine 边界
3. 不在 View 中直接依赖 transport 或 audio 底层实现
4. 不把每帧高频数据塞进全局 Store
5. 不因为方便而绕开上游契约

---

## 八、提交与评审口径

1. 每个 PR 尽量只对应一个 iOS issue 或一个 PR 级任务
2. 行为变化必须补测试或说明为什么当前只能先补占位
3. 若接口依赖 backend 未就绪，优先保留清晰边界，不做硬编码临时方案
4. 若发现 PRD 或技术文档口径冲突，应先回写 `meta`，不要在本仓自行定案

---

## 九、最终口径

`fluentwork-ios` 当前第一波开发的标准口径应统一为：

1. 先做 Root Store / Transport / API / speaking room 壳
2. 只打通“说 -> review 状态可见”最小闭环
3. 不复制上游真源，只在本仓保留开发入口索引
