# iOS 测试分层与依赖隔离规范

**定位**：统一 FluentWork iOS 后续测试写法，明确哪些场景必须 hermetic，哪些场景允许 simulator / 手工实测，避免再次把真实网络、真实麦克风、真实系统权限误带进 `swift test`。

---

## 1. 总原则

默认规则只有一条：

**`swift test` 必须 hermetic。**

含义：

1. 不依赖真实 backend、真实网络、真实 Docker、本地 MySQL / Redis
2. 不依赖真实麦克风、真实 `AVAudioEngine.start()`、真实系统权限弹窗
3. 不依赖本机全局状态，如真实 Keychain、真实 `CommandLine.arguments`、宿主进程外的环境副作用
4. 同一测试在本机、CI、不同机器上都应得到同样结果

只有以下两类可以离开 hermetic 边界：

1. **runbook / smoke**：面向宿主 App、模拟器、物理设备的验证
2. **人工实测**：权限、音频路由、蓝牙、中断恢复、真机网络切换

---

## 2. 测试层级与允许依赖

| 层级 | 目标 | 允许依赖 | 禁止依赖 |
|---|---|---|---|
| Pure unit test | reducer、mapper、codec、projection | 纯 Swift 数据、固定时间、固定 ID | 网络、音频硬件、权限、文件系统副作用 |
| Middleware / feature integration test | 验证 action → middleware → reducer 链路 | `Container` override、stub client、in-memory store | 真实 backend、真实 `LiveAudioEngine.startCapture()`、真实 token issuance |
| Package-level service test | 验证 service 内部纯逻辑 | 纯 decoder、test hook、内存 double | 真实麦克风、真实 `AVAudioSession`、真实 socket |
| Simulator smoke | 验证宿主组装、导航、bootstrap、基础 UI | `xcodebuild`、iPhone 17 Pro 模拟器、静态 bootstrap | 真实语音会话、真实后端联调、不可控系统权限流程 |
| Manual device QA | 验证权限、音频路由、打断、蓝牙、局域网联调 | 真机、系统设置、真实后端 / gateway | 不可复现的随手验证替代正式自动化 |

结论：

1. **单测与集成测默认只做前 3 层**
2. **simulator smoke 只做宿主壳与稳定路径**
3. **硬件、权限、真网问题只放到第 5 层**

## 3. Bootstrap 相关规范

Bootstrap 是当前最容易被写成伪集成测试的部分。

### 3.1 必须做的方式

1. 用 `StaticBootstrapClient` 或 `SurfaceOnlyBootstrapClient`
2. 通过可注入 provider 传入 launch arguments / preferred surface
3. 断言最终状态，不断言短暂中间态

### 3.2 禁止做的方式

1. 在 `LaunchToNavigationEndToEndTests` 里走真实 `SessionAPIClient`
2. 依赖本机是否起了 backend
3. 直接读取全局 `CommandLine.arguments` 而不做注入

### 3.3 当前仓最佳实践

适用测试：

1. `LaunchToNavigationEndToEndTests`
2. `BootstrapSurfaceProviderTests`
3. `AppBootstrapMiddlewareTests`

推荐做法：

```swift
let container = Container()
container.bootstrapClient.register {
    StaticBootstrapClient(
        snapshot: BootstrapSnapshot(
            featureFlags: .firstWave,
            preferredSurface: .speakingRoom
        )
    )
}
```

对于重复启动这类竞争问题，不能只靠 reducer 状态推理，要补 middleware 级回归测试，覆盖真正的 in-flight 防重入行为。

## 4. AVAudio / SpeakingRoom 相关规范

音频链路是第二个高风险区。

### 4.1 `swift test` 中允许的内容

1. `LiveAudioEngine.play(frame:)`
2. `interruptNow()`
3. `_testConvertToPCM16(...)`
4. 纯 decoder / codec / gate / tracker 逻辑
5. `StubAudioEngine` / `ControllableAudioEngine`

### 4.2 `swift test` 中禁止的内容

1. 真实 `MicrophonePermission.request()`
2. 真实 `AVAudioEngine.start()`
3. 真实 `AVAudioSession.setActive(true)`
4. 依赖系统麦克风授权弹窗
5. 依赖当前机器是否接入音频设备

### 4.3 为什么

因为这些路径不再只是“代码逻辑”，而是：

1. 硬件存在性
2. 系统权限状态
3. 宿主进程音频上下文
4. 其他 App 是否占用音频会话

这些条件天然不可 hermetic。

### 4.4 当前仓推荐写法

测试 `speechSessionMiddleware` 时，必须显式覆盖：

```swift
let container = Container()
container.reset()
container.audioEngine.register { StubAudioEngine() }
container.speechSessionClient.register { StubSpeechSessionClient() }
```

不要只替换 transport，而让 middleware 默认 resolve 到真实 `LiveAudioEngine`。

## 5. 网络 / 存储 / 权限规范

### 5.1 网络

`swift test` 中：

1. 禁止真实 HTTP / WSS 请求
2. 禁止依赖 `LOCAL_HOST`
3. 禁止依赖本机 backend 是否已启动

应使用：

1. `StubNetworkMonitor`
2. `InMemorySocketTransport`
3. `StubSpeechSessionClient`
4. 各 feature 自带 mock / static client

### 5.2 存储

默认优先：

1. in-memory store
2. capturing logger / tracker
3. test-local fake token store

避免：

1. 真实 Keychain
2. 跨测试共享全局容器状态
3. 依赖上一个测试留下的缓存

### 5.3 权限

所有权限读取必须可注入。

已经明确的模式：

1. `DebugBootstrapConfiguration` 不直读全局 launch arguments
2. `SpeakingRoomView` 权限 gate 可注入

后续新增权限型能力时，必须保持同样模式：

1. 生产实现走系统 API
2. 测试实现走 provider / stub

## 6. 什么时候需要 simulator / 真机实测

以下问题不属于 `swift test` 的职责：

1. 麦克风授权首次弹窗
2. `AVAudioSession` 与系统音频冲突
3. 蓝牙耳机切换
4. 前后台切换导致的音频中断
5. 真机局域网访问 backend / gateway
6. 宿主 App 的 Launch / Bootstrap / Navigation 壳是否能正常拉起

这些场景应分别放到：

1. `docs/09_I10_smoke_test_runbook.md`
2. `docs/10_I12_audio_engine_decoder_pitfalls.md`
3. `docs/11_I13_iOS_backend_wss联调_runbook.md`
4. `docs/12_mock_device_测试支持说明.md`

## 7. 新测试编写检查单

新写测试前，按顺序检查：

1. 这条测试是否必须进 `swift test`？
2. 是否碰到真实网络、真实权限、真实硬件？
3. 对应依赖是否已经有 `Container` override？
4. 断言的是最终状态，还是瞬时中间态？
5. 是否依赖外部环境已经启动某个服务？
6. 是否会因为并发调度差异而产生 flaky？
7. 是否已有 runbook 更适合承接这类验证？

如果第 2、5 任一项回答为“是”，默认说明测试边界错了。

---

## 8. 当前项目的固定约束

1. `swift test` 必须保持 hermetic
2. bootstrap 测试必须优先用静态 client
3. `SpeakingRoom` / `AudioEngine` 测试必须优先用 stub engine
4. 真实网络联调只能进 runbook / smoke
5. iOS 宿主验证统一使用 **iPhone 17 Pro 模拟器**

这 5 条是后续新增测试的默认门禁，不再重复讨论。
