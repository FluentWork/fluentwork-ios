## 1. Redux 的形状（实测）

### Store

```swift
public typealias AppStore = Store<AppState, AppAction>          // AppStore.swift:5
public static func make(container: Container = .shared) -> AppStore   // :7-18
```

`Store(initialState: .initial, reducer: appReducer, middlewares: makeAppMiddlewares(container:))`。初始态就是 `AppState()`（`AppState.swift:100`）。

### State：13 个字段，全部 `Sendable`，无 `nonisolated`

| 字段 | 归属 |
|---|---|
| `bootstrapStatus`、`lastErrorMessage` | **跨切片**（由 `appCrossCuttingReducer` 写） |
| `featureFlags`、`auth`、`speakingRoom`、`review`、`corpus`、`dailyRead`、`sessionHistory`、`workspace`、`badgeFeedback`、`network`、`navigation` | 11 个 feature 切片 |

`AppState` 上还有一个**计算属性** `usesVoiceVadAuto`（`AppState.swift:103-105`），读 `featureFlags`。它是派生的、不是存的——这是对的。

### Action：12 个顶层 case

`lifecycle` + 11 个 feature 切片，每个关联一个子 Action 枚举（`AppState.swift:115-128`）。

### Reducer：11 个 pullback + 1 个跨切片

`appReducer` 由 `combineReducers` 组装（`AppReducer.swift:6-107`）：11 个 `pullback`（`extract` 用 `guard case .xxx(let action) = $0 else { return nil }`）+ `appCrossCuttingReducer`（`:109-186`，**78 行**）。

`appCrossCuttingReducer` 直接 `switch action`，处理 `lifecycle`、`featureFlags(.applyRemoteSnapshot)`、`speakingRoom(.badgeHit)`、`auth(.signedInAsGuest/.mergedIntoRegistered)`。

### Effect：只有 3 种操作

TGReduxKit 的 `Effect.Operation` 只有 `.none` / `.task(id:)` / `.cancel(id:)` / `.merge`（`.build/checkouts/TGReduxKit/Sources/TGReduxKitCore/Effect.swift:6-15`）。本仓的使用分布：

| 构造器 | 次数 | 分布 |
|---|---|---|
| `.task(id:)` | 26 | AppBootstrap 11、SpeechSession 8、DailyRead 5、SessionHistory 3 |
| `.task {`（无 id） | 22 | SpeechSession 为主 |
| `.merge(` | 34 | AppBootstrap 为主 |
| `.cancel(id:)` | 18 | SpeechSession 为主 |
| `.fireAndForget` | 12 | SpeechSession 为主 |
| `.debounce(` | **0** | — |

**没有 `.debounce` 的使用**，尽管框架提供了（`Effect.swift:63`）。所有防抖/去重都是手写的（`OnceFlag`、`BootstrapLoadGate`、`EvaluationArrivalBox` 等）。见 §4.4。

## 3. 好在哪里

### 3.1 状态机是纯函数（G2）

```swift
@discardableResult
public static func reduce(
    _ state: inout SpeechSessionState,
    event: SpeechSessionEvent
) -> [SpeechSessionSideEffect]                                  // SpeechSessionMachine.swift:8-12
```

- 签名**无 `async`、无 `throws`**（`:9-12`）。
- 文件头注释明言「Zero IO … do not call AudioEngine / Transport from here」（`:3-6`）。
- 全文件 grep `Date(|await|async|Task|Clock|sleep|DispatchQueue|URLSession` **只命中一处注释里的 `await` 字样**（`:111`），无任何实际 IO。
- 非法转换**显式回滚状态并返回 `[]`**（`:342-346`）；合法跃迁由 `isValidTransition` 白名单保证（`:369-396`）。

**这是本仓最强的一处设计。** 它让 9 个 phase × 28 个 event 的整个组合空间可以被穷举测试，而不用起任何设备。

### 3.2 状态只能经 reducer 改（G3）

- `Store.state` 与 `ScopedStore.state` 都是 `public private(set)`（`Store.swift:8`、`ScopedStore.swift:9`）。
- 全仓 grep `store.state.<field> =` → **0 处真实赋值**；命中的全是 `==`/`!=` 比较或测试断言。
- 唯一的状态写入口是 `Store.applyReducer`（`Store.swift:138-144`）。
- 唯一用了 `@Observable` 的类型是 TGReduxKit 的 `Store` 本身；`Shared/`、`App/` 里没有第二个 `@Observable`、也没有 `@Bindable`。

**Redux 的纪律是真的守住了**，而且不是靠约定——`private(set)` 让它在编译期就成立。

### 3.3 Feature 切片整齐

`Architecture/Features/` 下 11 个文件，每个都是「`XxxState` + `XxxAction` + `xxxReducer`」三件套（外加必要的辅助类型）。唯一的例外是 `SessionHistoryFormatting.swift`（83 行，纯格式化静态方法，无 State/Action/Reducer）——它是**工具**放在切片目录里，不是切片。

### 3.4 DI 是真正可注入的

34 个 factory，`AppStoreFactory.make(container:)` 与每个 middleware 工厂都收 `container: Container? = nil`。测试传本地 `Container()` 就能完全隔离（`AppDependencies.swift:735-740` 的注释专门解释了为什么 `tracker` 是 per-container 而不是进程单例：「Tests can register a CapturingTracker on a local `Container()` without racing other suites' `reset()`」）。

**本轮修 D6/D11 时这一点直接受益**：`makeProductionRouter(tracker:)` 能注入 `CapturingTracker` 并观察到埋点，不需要任何全局状态。这是好的 DI 设计带来的实际回报。

## 4. 不好在哪里

### 4.1 DI 的默认值是全局单例（B3）

**每个**容器参数都是 `container ?? Container.shared`，共 **11 处**生产代码：

| 位置 | 数量 |
|---|---|
| `AppBootstrapMiddleware.swift` | 5（`:32, :46, :137, :189, :302`） |
| `SpeechSessionMiddleware.swift` | 1（`:56`） |
| `DailyReadMiddleware.swift` | 2（`:22, :122`） |
| `SessionHistoryMiddleware.swift` | 1（`:16`） |
| `AppStore.swift` | 1（`:13`） |
| `ClientASRTranscriber.swift` | 1（注释里） |

同时有 **7 个 factory 是 `.shared`（进程单例）**：

| factory | 行 |
|---|---|
| `audioEngine` | `:652` |
| `speechSessionClient` | `:685` |
| `corpusClient` | `:695` |
| `dailyReadClient` | `:705` |
| `dailyReadAudioPlayer` | `:714` |
| `sessionHistoryClient` | `:724` |
| `tracker` | `:739` |

**为什么这是问题：**

1. **「忘了传 container」在生产不会报错。** 它只是静默地拿到全局单例。测试永远会传，所以测试发现不了这条路径。
2. **`.shared` 是「每容器一个」还是「每进程一个」取决于调用者。** `AppDependencies.swift:736-738` 的注释说 `.shared` 在 `Container.shared` 下等于进程单例，在测试的本地 `Container()` 下等于「那个容器一个」。所以同一个 factory 在不同上下文里有两种生命周期语义。
3. **`audioEngine` 是 `.shared`。** 意味着如果哪天有人建了第二个 Store（比如 preview、或将来做多会话），两个 Store 会**共享同一个音频引擎实例**。而 `LiveAudioEngine` 是 `actor`，共享不会崩，但会串音——正是这个项目历史上踩过的 P0-11。
4. `processingTimeouts`（`:755-763`）是**唯一**没有 scope 的 factory，注释解释了为什么（要能被测试改），这反证了作者知道 scope 选择是个真问题——只是其他 33 个没有逐条论证。

**确定性：【实测】+【推断】（第 3 点的后果是推出来的，当前没有第二个 Store）。**

**建议**：把 `Container.shared` 从生产默认值改成**必须显式传**（去掉 `?? Container.shared`），在 `FluentWorkHostApp` 里传一次 `Container.shared`。这样「忘了传」变成编译错误，而测试路径不受影响。这是一处**编译期就能拿到的保护**，成本很低。

### 4.2 文件名与内容不符：`AppBootstrapMiddleware.swift` 定义 4 个 middleware

836 行里装了 `appBootstrapMiddleware`、`appNetworkMonitorMiddleware`、`reviewMiddleware`、`corpusMiddleware`——**4 个互不相关的 middleware**，加上 `makeAppMiddlewares`、`reviewAccept`、以及 `BootstrapLoadGate`、`MainActorDispatchBox` 两个盒子类型。

**后果**：`grep -l reviewMiddleware` 找不到 `ReviewMiddleware.swift`（不存在）；想改 review 的加载逻辑，得先知道它住在 bootstrap 的文件里。这与 `01` §4.4 是同一类问题——**目录结构没有表达真实结构**。

**确定性：【实测】。建议**：拆成 `ReviewMiddleware.swift` / `CorpusMiddleware.swift` / `NetworkMonitorMiddleware.swift`，`AppBootstrapMiddleware.swift` 只留 bootstrap 与 `makeAppMiddlewares`。

### 4.3 `appCrossCuttingReducer` 是「第二套 reducer」

`AppReducer.swift:109-186`，78 行，直接 `switch action` 处理 12 类顶层 action 中的 4 类。它与 11 个 pullback 是**两套并存的分派机制**：

- pullback 是「一个 action 属于一个切片」；
- `appCrossCuttingReducer` 是「某些 action 要影响别人的状态」。

第二套机制本身是必要的（badge 命中要同时动 `badgeFeedback` 和 `speakingRoom`）。**但它没有名字**：它叫 `appCrossCutting`，而它处理的其中一条是 `speakingRoom(.badgeHit)`——那明明是 speakingRoom 切片的 action。

**确定性：【读码】。建议**：把它的每条分支写明「为什么它不能留在原切片」，或者改成显式的 `CrossCuttingRule` 列表。今天读它的人只能靠猜。

### 4.4 手写的去重/闸门有 5 个，而框架提供了 `.debounce`

`Effect` 有 `.debounce`（`Effect.swift:63`），本仓使用 **0 次**。取而代之的是 5 个手写盒子：

| 类型 | 行 | 作用 |
|---|---|---|
| `BootstrapLoadGate` | `AppBootstrapMiddleware.swift:116` | 防止 bootstrap 重入 |
| `ObserverStartedBox` | `DailyReadMiddleware.swift:162` | 观察者只启动一次 |
| `OnceFlag` | `SpeechSessionMiddleware.swift:36` | 一次性闸门 |
| `EvaluationArrivalBox` | `:359` | 评测到达标记（`consume()` 语义） |
| `TurnTimeoutTracking` | `:384` | 超时任务跟踪 |

其中 `EvaluationArrivalBox` 的 `consume()`（读一次就清）语义**比 `.debounce` 更合适**——它要的是「一次性事件」，不是「防抖」。所以不是所有手写都该被替换。

**判断：不是缺陷，但值得记。** 5 个手写盒子各有各的语义（重入闸门 / 只启动一次 / 一次性 / 可消费标记 / 任务跟踪），说明 `.debounce` 确实不覆盖这些场景。真正的成本是**每个盒子都要自己处理线程安全**——`OSAllocatedUnfairLock` 在生产代码里出现 **11 处**（`AppBootstrapMiddleware.swift:117`、`DailyReadMiddleware.swift:163`、`SpeechSessionMiddleware.swift:37/243/256/301/360/385/1539/1550`、`SpeechSessionTimingsRecorder.swift:58`），其中 **8 处在 `SpeechSessionMiddleware.swift`**。

**确定性：【实测】。**

### 4.5 隔离策略：三种并存，无统一规则

| 策略 | 数量 | 例子 |
|---|---|---|
| `actor` | 17 | `LiveAudioEngine`(`:221`)、`URLSessionSocketTransport`(`:7`)、`TTSPlaybackCoordinator`(`:46`)、`AuthenticatedNetworkClient`、`TokenRefreshCoordinator`、三个 corpus store、`InMemorySocketTransport` |
| `@MainActor` 类型 | 5 | `AppStoreFactory.make`、`AppRootTabView`、`FluentWorkHostApp`、`HostRootView`、`DebugBootstrapConfiguration` |
| `Sendable` `final class` + `OSAllocatedUnfairLock`（多为 `@unchecked Sendable`） | 11 | 见 §4.4 的盒子清单 + `SpeechSessionTimingsRecorder`、`TTSStreamTrace` |

**好在**：`NSLock` 在生产代码里 **0 处**（仓规禁止，`AGENTS.md` Local Rules #5），实际用的是 `OSAllocatedUnfairLock`。纪律被守住了。（`grep NSLock` 会给你 4 个命中，**全部是注释**——三处解释「`OSAllocatedUnfairLock` 取代了 `NSLock`」，在 `DailyReadMiddleware.swift:156`、`SpeechSessionMiddleware.swift:238-239`、`SpeechSessionTimingsRecorder.swift:20`。）

**不好在**：**「什么时候该用 actor、什么时候用锁」没有成文规则。** 同一层里两种都有：

- `TTSPlaybackCoordinator` 是 `actor`（`TTS/TTSPlaybackCoordinator.swift:46`）；
- `TTSStreamTrace` 是 `final class` + 锁（`SpeechSessionMiddleware.swift:1538`）。

两者都在 TTS 链路上、都是「每帧被调一次」的热路径。选 actor 的那个要付每帧一次跳转（见 `03` §4.2，D8），选锁的那个不用。**这个不一致本身就是 D8 的一部分。**

**确定性：【读码】。建议**：写一条规则——「热路径（每帧）用锁，冷路径用 actor；跨 `await` 的复合状态用 actor」。今天没有这条规则，所以每个新类型都要重新决定一次。
