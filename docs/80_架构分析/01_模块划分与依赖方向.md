## 3. 好在哪里

### 3.1 分层是真的，不是声明

`FluentWorkNetworking` 不知道 `FluentWorkCore` 存在——这不是纪律维持的，是**结构维持的**：`SocketTransportEventMapper` 需要把传输事件变成 feature 动作，它没有 import Core，而是定义了自己的动作面 `SpeakingRoomTransportAction`（`SocketTransportEventMapper.swift:106-122`），由 Core 侧的 `SpeakingRoomFeature.swift` 写 `init?(_ transportAction:)` 桥过去（`SpeakingRoomTransportBridge.swift`，37 行）。

**这个桥的存在方式是对的**：依赖方向倒过来写在**消费方**，而不是让底层去 import 上层。

### 3.2 底层的三个 target 都是「可被拿走」的

`FluentWorkDiagnostics`（133 行）、`FluentWorkFeatureFlags`（164 行）、`FluentWorkPluginSupport`（73 行）加起来 370 行，各自只依赖一个外部包或什么都不依赖，且**只被 Core 单向依赖**。它们可以原样搬去另一个 App。

## 4. 不好在哪里

### 4.1 `Modules/` 是一个空目录（B4）

```
$ find Modules -mindepth 1
Modules/.gitkeep
```

它承诺了一个不存在的分层。读 `Package.swift` 的人不会去找它，但读 `ls` 的人会——而他会花时间确认它是不是漏了。

**确定性：【实测】。建议：删掉，或在 `.gitkeep` 旁写一句它为什么空。**

### 4.2 Moya 钉在个人 fork 的 `master` 分支（B2）

```swift
// Package.swift:27
.package(url: "https://github.com/tangzzz-fan/Moya.git", branch: "master"),
```

三个问题叠在一起：

1. **不是 tag、不是 revision**，是一个移动的分支。`swift package update` 会静默拉到新提交。
2. `Package.resolved:22-30` 记了 `revision e340f5df1be8…`，但那只在你**不** update 时有效。
3. 它是**个人 fork**（`tangzzz-fan/Moya`），不是上游 `Moya/Moya`。

**确定性：【实测】。影响：可重现构建 + 供应链。建议：换成 fork 的具体 tag 或 `revision:`；或者若 fork 只为某个补丁，用 `branch` + 在 `Package.resolved` 上锁的同时写一句「为什么必须用 fork」。**

### 4.4 `FluentWorkObjCSupport`：一行 Swift 都没有，却被 Core 依赖

它只有 `FWExceptionCatcher.m` / `include/FWExceptionCatcher.h`，导出一个函数：

```objc
BOOL FWTryCatch(NS_NOESCAPE void(^block)(void), NSError **error);  // .h:20
```

用途是兜住 `AVAudioPlayerNode.play()` 抛的 `NSException`（Swift 的 `try/catch` 抓不到 ObjC 异常），调用点在 `LiveAudioEngine.swift:407,416,919,949,1595`。

**判断：这是好的决定，坏的信号。**

- **好**：它是唯一能让 `play()` 的异常不炸掉进程的办法，且被包成 SPM target 而不是散在文件里。
- **坏**：它被 `FluentWorkCore` 依赖（`Package.swift:79`），意味着**音频播放这条路径有 5 个点靠 ObjC 桥才能不崩**。这是一个「我们知道它会炸、所以包起来」的形状，不是「它不会炸」。
- 值得单独立项的问题：`AVAudioPlayerNode.play()` 在什么条件下抛？`16_`/`17_` 修的是测试进程里的假引擎，真机路径上这 5 处有没有被触发过、触发时 `error` 是什么——仓里没有记录。

**确定性：【读码】+【推断】（触发条件无证据）。**
