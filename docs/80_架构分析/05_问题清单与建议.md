**S1-9 是查 S1-4 时撞出来的，而它比 S1-4 本身更值钱**：那 8 个 mark 名（**数量更正为 11，见下**）是 `08_` §3 尚未进行的真机验证**唯一计划中的证据来源**（`captureKick` 的注释写着「'the fix did not work' and 'the fix was never installed' were indistinguishable — which is the failure mode this project keeps paying for」），而**没有任何测试钉住它们**——一次改名或拼写错误就能静默移掉整条诊断链。这与 `70_/16_`/`17_`（判据从不取真值）、`70_/19_` §6.3（判据被复制进替身）、`70_/22_`（保护对象不存在）同族，是本仓第四次撞到「看起来有保护、实际没有」。**它只改测试就能修**，是本清单里性价比最高的一条。

**S1-9 已关闭（2026-09-23，`70_/24_`）**：**11 条**埋点名（不是原文的 8 条，更正见 `80_/README` 自校「第五处」）已由 `captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys` 全部钉住，生产代码零改动。

**但本条的交付物不是「加了一条测试」，而是「证明了这条测试会咬」。**「钉住既有行为」的票有一条特有的失效模式：**它可能永远绿**——而一条永远绿的守卫比没有守卫更糟，因为它会让下一个人以为这件事被管住了。所以 `24_` §6.2 用**两次变异验证**（改掉一个埋点名 / 删掉一个属性键）确认它会红，且失败信息指名道姓（哪条埋点、缺哪个键）。这与 `70_/22_` §6.2 问的「守卫守的是**效果**还是**机制**」是同一类追问——**先验证前提，再决定动作**的又一种形态：这次要验证的是守卫本身。

**S1-10 是 2026-09-24 真机事故的残余（`70_/27_`）**：练习会话卡在 `.connecting` 直到 10s 看门狗失败，而**一行我们的代码都没执行**——`DailyReadAudioPlayer` 为了锁屏继续播报，把共享的 `AVAudioSession` 切成 `.playback`，拆掉了 input route，`AVAudioEngine` 于是自己停了。`27_` 的修法是**局部的**（切之前先看真实 category，`.playAndRecord` 时不动），因为 `AVPlayer` 在 `.playAndRecord` 下照样能放——**它只是不需要赢这场争夺，只需要不替对方输掉**。

**但结构问题没关**，所以留在 S1——而且它的准确形状是**「有 owner，但有人绕过它」**，不是「没有 owner」：本仓**已经**有 `AudioSessionManaging` / `DefaultAudioSessionManager` 这个归属点（`LiveAudioEngine` 老实地走它，`FeatureFlags.swift:21` 的注释也把它当作 `.playAndRecord`/`.voiceChat` 的设定者），**而 `DailyReadAudioPlayer` 根本没注入它**，直接拿 `AVAudioSession.sharedInstance()` 自己配。于是同一个语义有了两个实现点——这是 `AGENTS.md` R2 那一类问题。

唯一看起来像答案的 `DefaultAudioSessionManager.isActive` 还是个**永不取假值的判据**：它读的 `active` 只在 `configure()` 里置 `true`，而 `pause()` 在生产里无调用者，所以它会永远报「房间还活着」——照它做判断会**静默禁掉** Daily Read 的音频。`27_` 因此选择读**真实 category**而不是读那个标志位。这与 `70_/16_`/`17_` 的「判据从不取真值」是同一个形状，只是这次的判据**已经存在于生产代码里**。

> **顺带一条方法论**：S1-10 的第一版我写成「**没有任何东西拥有它**」——那是在读 `AudioSessionManaging.swift` **之前**下的判断。读过之后形状变了：owner 在，绕道才是问题。**先说结论再补证据的写法在这里会写错**，所以本条按「先读事实再下判断」重写过一次。

**S1-10 与 S1-3 的教训是同一条**：`27_` 加的三处诊断（`describeSession()`、`captureArmed` 的 `session` 键、`session_interrupted_by_system` 埋点）都不是「顺手加的日志」——**在真机上，一行都不执行的失败只能靠这类痕迹归因**，而本仓已经付过两次「两侧单测全绿而真机静音」的代价（`70_/08_` §3）。

**S2-4 值得解释一下**：`02` §4.4 统计出 5 处手写去重、11 处 `OSAllocatedUnfairLock`，而 TGReduxKit 的 Effect 提供了 `.debounce` 且**全仓 0 次使用**。这不必然是错的——手写版有时更精确——但**没有任何地方写下来为什么**。

**S2-9 的分类是错的，而它错的方式值得单独记（2026-09-25，`70_/28_`）。** 本条原先只写「`deinit` 无条件 `removeTap`」，归到 S2「卫生」。实测之后它不是卫生问题：`engine.inputNode` 的**求值本身**就是打开输入设备的那一步（`LiveAudioEngine` 自己的注释写着「Querying the input format forces lazy node creation」），而全量 `swift test` 期间这条 `deinit` 跑了 **28 次** —— **那就是「测试在调用真机麦克风」**。分级只按「不做会怎样」，而「测试持续打开音频输入设备」的后果显然不止「让下一个人多读一会儿」。

**更要紧的是 `70_/16_` §7.1 为什么没改它。** 那条诊断一字不差，判据也给对了，但当时的理由里有一句：

> §4 显示 39→0 之后这条路径在测试里已经不再发生

**这句不成立。** 39→0 说的是**容器**路径（接线测试不再解析出真引擎）；而 `LiveAudioEngineTests` 是**直接构造**真引擎 —— 它是引擎的测试，本来就该构造。那条路径**从来没被数过**。

| 票 | 形状 |
|---|---|
| `70_/18_` | 把「少了一道防线」当成「留下的那道是对的」 |
| **`70_/28_`** | **把「一条路径堵上了」当成「这个洞堵上了」** |

两次的错法一样：**用一个局部的事实去支撑一个全局的结论。** 判据：**报数的时候要问「我数的是哪条路径」** —— 一个数字只对它被采集的那个集合成立。

**顺带关掉了一处 flaky**：那 28 次硬件 I/O 会把进程卡住，使 `24_` 那道「等泵处理完」的屏障有时要 1.5–3.4s，而预算只有 2s。去掉设备访问后，全量测试从 8.1–8.7s（且抖）变成 **6.17s（±50ms）**，连跑 6 次全绿。**所以「屏障预算不够」是症状，不是根因** —— 这一点只有把设备访问去掉之后才看得出来。
