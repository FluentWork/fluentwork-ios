# 03 — 语音链路的所有权

> 基线 `2aa8795`。本轮的收敛过程与逐条论证在 [`docs/70_tts_wss_refactor/`](../70_tts_wss_refactor/README.md)，本文**不重复**，只做架构层面的归纳与判断。

## 1. 三层结构

```
┌──────────────────────────────────────────────────────────────────────┐
│ SpeechSessionMachine           纯函数。9 phase × 28 event → 12 副作用 │
│                               零 IO、零时钟、零 async                 │
├──────────────────────────────────────────────────────────────────────┤
│ SpeechSessionMiddleware        把副作用译成 Effect；两条事件泵；       │
│ (1725 行)                      路由表（7 控制帧 handler + 4 事件）    │
├──────────────────────────────────────────────────────────────────────┤
│ DefaultSpeechSessionClient     IO 门面：上行发帧、下行订阅             │
│ URLSessionSocketTransport      WSS：收/发/心跳/时钟偏移                │
│ LiveAudioEngine (1621 行)      采集 + 播放 + 打断 + 权限              │
└──────────────────────────────────────────────────────────────────────┘
```

**这个三层切分是清楚的**：状态机决定「该发生什么」，中间件决定「怎么发生」，客户端/传输/引擎决定「实际发生」。

## 2. 两条事件泵

| 泵 | 行 | 规模 | 输入 | 出口 |
|---|---|---|---|---|
| `audioEventPump`（上行） | `:436-699` | **264 行**，其中 switch 约 239 行、**14 个 case** | `audioEngine.events()` | 直接 dispatch，**不走路由表** |
| `transportEventPump`（下行） | `:1025-1133` | 109 行 | `speechClient.events()` | 交给 `TransportEventRouter` |

路由表本身（`makeTransportEventRouter`，`:700-1023`）是 **324 行**，装 7 个控制帧 handler + 4 个事件 handler。

**两条泵的形状不对称**：下行经过路由表（静态、可断言），上行是裸 switch。见 §4.3。

两条泵的**生命周期注释值得单独表扬**（`:407-435`）：它们解释了为什么泵是「每进程一个、永不取消」——`AsyncStream` 是单消费者序列，而 transport/engine 的流活得比会话长，所以按会话建迭代器会让垂死的消费者与下一个消费者抢同一批事件，而取消可能落在**下一个**会话的消费者身上。注释还给了一个真机测量值（「consumer started and exited 159ms later while the socket was up」）。

**这是好文档的样板**：它记的不是「我们这么写了」，而是「不这么写会怎样，以及实测到过」。

## 3. 三个单点所有权（本轮收敛的成果）

| 决策 | 唯一 owner | 轴 | 钉住它的测试 |
|---|---|---|---|
| **播还是丢** | `TTSPlaybackCoordinator`（`TTS/TTSPlaybackCoordinator.swift:46`，`actor`） | **轮次**（`ai.tts.start` 开、`ai.tts.end` 关；`turnRegistry` 带 `.active`/`.superseded`） | `TTSPlaybackCoordinatorTests.bareFrameBetweenInterruptAndEndIsDropped` |
| **打断** | `SpeechSessionClientProtocol.sendInterrupt()` | — | `sendInterruptPutsExactlyOneInterruptFrameOnTheWire`（客户端级，线上恰好一帧） |
| **轮次归属** | 同上协调器的 `attributionTurnID` | 轮次 | `TransportRoutingEquivalenceTests` 的两条 `aiFirstAudioChunk` 测试 |

**为什么这三条重要**：它们各自都曾是「多处各自决定同一件事」的形状——

- 播/丢曾是**两道序号水印**（引擎侧 `AudioPlaybackGate` + 传输层 `BargeInAudioGate`），两道都删了（`70_/18_`）；
- 打断曾是**四处**：传输层水印、协调器轮次注册表、魔法字符串 `"__interrupt__"`、状态机的 `.stopPlayback`/`.sendInterrupt` 效果（`70_/19_` §9）；
- 归属曾是「控制帧时序推断」被两处各推一次。

**这一轮的净效果**：决策点从 4 处收敛到 3 个单点，且**每一个都有一个只属于它的测试**。

### 3.1 一个值得记住的形状：两道门都删了，而不是合成一道

`70_/07_` 当时删掉引擎侧水印、保留传输层水印，并在**四处文档**里断言「现在只有一处」。**那个说法是错的**（`70_/README.md:25` 的补记）：两道门**同轴（序号）、同类（水位线）**，而保留的那一道恰恰是**唯一能无声吞掉整轮音频**的。

```
「少了一道防线」  ≠  「留下的那道是对的」
```

这是本仓出现过两次的形状（另一次见 `02` §4.4 的「从不取真值的判据」）。**判据**：删掉一道防线之后，要**重新论证剩下的那道**，而不是因为「只剩一道」就默认它对。

## 4. 不好在哪里

### 4.1 归属仍是「控制帧时序推断」，不是「数据帧自描述」（D7）

二进制帧格式是 `[4字节大端 seq][payload]`，**帧上没有 `turn_id`**（`WSAudioFrameCodec`；后端 `voiceproto/frames.go:179-203` 同）。归属靠「谁是这段 `ai.tts.start` / `ai.tts.end` 之间的帧」推断。

`70_/01_` §7 把根因定为：

> 轮次归属被放在了「控制帧时序推断」里，而不是「数据帧自描述」里。

而落地的协调器**仍然是控制帧时序推断**——只是行为更好的同一形状。原本的自我描述方案存在且被跳过：`70_/03_` §Stage 3「后端补 `turn_id`，切到单 sink」，`README.md:35` 记「S0/S1/S2/S4 落地、**S3 未走**」。

**残留风险**：帧不自带 id，所以「被取代轮 A 的迟到帧、在轮 B 的 `ai.tts.start` 之后到达」会被归属到 **B** 并**播出去**。WS 保序使这需要网关违约——但 Stage 3 的全部意义就是不再依赖网关顺序。

**确定性**：机制【读码】；触发条件【推断】。

**这是本仓最重要的未修架构问题**，且它**需要后端配合**（`70_/11_` §7 问题 2，仍在等决策）。

### 4.2 音频路径每帧两次 actor 跳转，而路由器文档明确反对其中一次（D8）

`TransportEventRouter` 刻意做成 `struct` 而非 `actor`，理由是（`TransportEventRouter.swift:18-24`）：

> actor 在这里只提供调用方已经自己保证了的串行性。代价却是**每个音频帧一次额外的 actor 跳转**，而音频是一帧一个事件：一个 250 帧的回合就是 250 次跳转、250 个挂起点，正压在延迟最敏感的那条路上。

而同一条路径往后一个 hop：

- `TTSPlaybackCoordinator` **就是** `actor`（`TTS/TTSPlaybackCoordinator.swift:46`）；
- 它的 sink `LiveAudioEngine` **也是** `actor`（`LiveAudioEngine.swift:221`）。

即：**同一个论证在三个点上只应用了一个。** 250 帧/轮 → 500 次 actor 跳转。

**确定性：【读码】。** 注意这条**不是**说路由器的决定错了——它的决定是对的；问题是同一个判据没有被用到后两个 hop。

**为什么难修**：`LiveAudioEngine` 是 High-Risk Path #1，且改动的影响是**延迟**而不是行为——单测测不出来，只能真机量。所以这条应当和 `P4`（真机验证）一起做，先量出基线，再决定值不值得改。

### 4.3 `audioEventPump` 未纳入路由（D9）

上行 264 行、14 个 case 的 switch 是**第二个大 switch**，不受路由表管。`70_/README.md:25` 已自认 P-E 未动。

**两张表的差别不只是行数**：

| | 下行 | 上行 |
|---|---|---|
| 结构 | 静态字典 `[WSControlFrameType: ControlFrameHandler]` + 兜底 | 裸 `switch` |
| 新增一类事件时 | 加一行注册；`wireType` 是穷尽 switch，会编译失败 | 加一个 `case`；**漏了会静默落 `default`** |
| 可断言性 | `TransportRoutingEquivalenceTests` 能用生产工厂驱动整张表 | 只能起 store + 假引擎做端到端 |
| 「没人接」的可见性 | 有（`20_` 补了留痕与带理由的名单） | **无**——`default` 分支没人看 |

**判断**：D9 的价值不在「少 264 行」，而在**让上行也有「谁接走了这个事件」这张可断言的表**。`20_`（D11）刚证明了这个形状能防住什么。

**确定性：【读码】。建议**：把 `audioEventPump` 的 switch 抽成 `AudioEventRouter`（与 `TransportEventRouter` 同形），并把「没有 handler 的 `AudioEngineEvent`」变成一条带理由的名单 + 集合相等断言。**这是低风险改动**（只搬路由、不动行为），且可以直接复用 `20_` 的手法。

### 4.4 两条泵的生命周期是「每进程一个」，而它们持有的是「每会话」的状态

注释（`:407-435`）解释了为什么泵不能按会话建。而泵里因此存着**跨会话**的可变局部量（改动前）：

```swift
private func audioEventPump(...) -> Effect<AppAction> {
    ...
    return .task {
        var pcmBuffer: [Data] = []          // 跨会话存活
        var isCapturingSpeech = false       // 跨会话存活
        for await event in audioEngine.events() { ... }
```

注释（`:430-435`）说明了为什么安全：「`.speechStarted` 会在打开 `speechCaptureGate` **之前**清空 buffer，所以上一会话残留的东西到不了线上」。

#### ⚠️ 本节的前提已被推翻（2026-09-22，`70_/22_`）

**上面这段分析——包括它的风险描述与两条建议——都建立在一个未经验证的前提上：`pcmBuffer` 是活的。它不是。**

把改动前 `pcmBuffer` / `isCapturingSpeech` 的 **9 个出现位置**逐个标出读写方向：

| 方向 | 次数 | 位置 |
|---|---|---|
| 声明 | 2 | `:451`、`:452` |
| 写 | 6 | `:461` `removeAll()`、`:462` 赋值、`:490` 赋值、`:494` `removeAll()`、`:544` `removeAll()`、`:554` `append` |
| **读** | **1** | `:553` `if isCapturingSpeech {` —— 而它的分支体只是**往这个死 buffer 里写** |

`pcmBuffer` **一次都没被读过**：没有 `.count`、没有 `joined()`、没有作为参数传进任何函数、没有出现在任何 `return` 里。**整条数据流是闭环，闭环外没有观察者。**

所以：

- **「靠清空时机保证的安全」这句话没有对象。** 串上一场的音频需要有东西**读到**这个 buffer；没有读点，就不存在「串」这个后果。
- **原文的风险描述（「任何一个新的 `case` 读到 `pcmBuffer` 就会串上一场」）无法成立**——它假设了读点存在。
- **原文的两条建议都不可行**：
  1. 「收进一个 `SpeechCaptureBuffer` 类型」——**会制造新缺陷**。给死存储一个有名字的类型，等于给「泵持有每会话状态」发一张通行证：下一个人会看到一个活组件的外观，而它什么都不做。**抽象一个空集合只会让它更难被发现。**
  2. 「加一条『两个会话之间不清空必须红』的测试」——**写不出来**。没有可观察后果；要红只能断言那个私有局部量的内容，而那既够不到、又等于把死代码重新编码进测试。

**实际处置**：**删掉**（`70_/22_`，D12）。删掉的 9 行没有一行会派发 action，外部可观测量一个都没变；放行判定仍是 `speechCaptureGate.takeForwardDecision()`。

#### 保留下来的那个形状

「靠清空时机而不是作用域来保证安全」**作为一个形状仍然是有效的**——它对**真的**跨会话状态成立，而本仓确实还有这类状态（两个泵都活得比会话长）。判断一个跨会话局部量安不安全，正确的问法不是「它被清得及时吗」，而是：

1. **它有读点吗？** 没有 → 它不该存在（本节的情形）。
2. 有读点 → **读点与清空点的相对顺序**是否被测试钉住？没有 → 那才是一条真的隐式不变量。

本节原来的错误，是把第 1 步跳过去直接做了第 2 步。这与 `70_/13_`（D5）推翻 D5 自身立论、`70_/16_`/`17_` 的「判据从不取真值」同族：**先验证前提，再决定动作。**

**确定性：【读码】**（读点为零是可枚举的事实，非推断）。**已修**，见 `70_/22_`。

### 4.5 真机从未验证（P4）

`70_/08_` §3 记录：barge-in 与断线重连**从未在真机上验证过**。而 `08_` 自己记着两次「两侧单测全绿而真机静音」的事故（2026-09-12、2026-09-20）。

**本轮把两件事各自收敛成了单点**（§3），这让真机验证**更必要**而不是更不必要——单点意味着「一次错就全错」。

`70_/11_` §7 问题 4 记着验证的前提：**需要一条 >5 秒的回复**（「500ms 的提示音看不出来，5 秒就能暴露」）。

**确定性：【实测】（这是已记录的事实，不是推断）。**
