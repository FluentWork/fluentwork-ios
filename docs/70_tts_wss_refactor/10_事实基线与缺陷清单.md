## 1. 拓扑

```
AVAudioEngine(tap 采集) ──pcmChunk──▶ audioEventPump ──▶ SpeechCaptureGate ──▶ client.asr.audio(binary)
                                                └─▶ SpeechSessionMachine ─▶ store

URLSessionWebSocketTask ──▶ receiveLoop ──▶ handle(message:)
                                             ├─ .string → WSControlFrameCodec.decode
                                             │             ├─ releaseInterruptWatermarkIfTurnEnded(frame)  ← ai.turn.end 清水位
                                             │             └─ emit(.control(frame))
                                             └─ .data   → WSAudioFrameCodec.decode
                                                           ├─ BargeInAudioGate.accept(sequence)   ← 传输层序号水印
                                                           └─ emit(.audio(frame))

transportEventPump (for await，逐事件串行)
   └─ TransportEventRouter.route(event:)
        ├─ .audio      → audioHandler    → TTSPlaybackCoordinator.onAudioFrame → AudioSink.play(pcm:)
        ├─ .control    → controlHandlers[frame.wireType]
        ├─ .diagnostic → diagnosticHandler
        └─ 其余        → fallbackHandler → SocketTransportEventMapper → store
```

关键：**下行音频的播/丢决策只有一个入口**（`TTSPlaybackCoordinator`），但**丢弃实现有两处**
（传输层 `BargeInAudioGate` 的序号水印 + 协调器的轮次注册表）。§9 的 D2 全部围绕这一点。

## 3. 二进制音频帧格式

`WSAudioFrameCodec.swift:29-53`：

```
[ 4 bytes ] UInt32 big-endian sequence  +  [ N bytes ] payload
```

- 帧头固定 4 字节，大端（`:47-49`）。
- `payload` 是「活跃的 `ai.tts.start` 的 codec 所说的东西」（`:5-8`）。
- 真机实测：`sequence 0..249 / payload_bytes 640 / socket size_bytes 644`（`08_` §2）——4 + 640 = 644，连续无缺。
- 字段名已从 `opusPayload` 改为 `payload`，旧名保留为 `@available(*, deprecated, renamed: "payload")` 的计算属性（`:18-22`）。

## 4. 采样率与 codec 的实际契约

| 来源 | 声明 |
|---|---|
| 网关 `ai.tts.start`（dev-echo 实测） | `codec:"pcm"`, `sample_rate:16000`（`08_` §2） |
| 网关 `ai.tts.start`（测试夹具） | `sample_rate:24000`, `codec:"opus"`（`AITTSFramesTests.swift:31`） |
| 客户端解码 seam | `RawPCM16FrameDecoder`：把 payload 当**已是 16k mono PCM16**（`AppDependencies.swift:210-223`），长度须为偶数 |
| 客户端播放 | `LiveAudioEngine.play(pcm:)` → `makePCMBuffer` → `AVAudioPlayerNode`（`LiveAudioEngine.swift:827-837`） |
| 契约草案 | 网关 `codec` **应当填 `pcm`**（`WSAudioFrameDecoderAdapter.swift:6-10` 引 `meta 83_` §4.1） |

**结论**：`codec` 与 `sample_rate` 被解析、被写进埋点，**没有任何消费者**——解码器不按它选路。
生产绑定是「payload 就是 PCM16」，与线上声明的 `codec` 无关。这条缺口已在 `07_Stage4_删除死路径.md` §3
被自认为「已知缺口，不在本次范围」。

## 5. 序号（sequence）的编号域

| 事实 | 出处 |
|---|---|
| 帧上只有 `sequence`，**没有 `turn_id`** | `WSAudioFrameCodec.swift:9-23` |
| 客户端按连接维护 `maxObservedSequence`，**只在 `connect()` 重置** | `URLSessionSocketTransport.swift:42, 108`；`AudioFrameDropGate.swift:89-106` |
| 策略注释断言「server sequences are monotonic」，并明确不支持回绕 | `AudioFrameDropPolicy` 文档注释（`AudioFrameDropGate.swift:15`） |
| **实测：dev harness 每轮从 0 开始** | `08_` §2：第一轮 25 帧、第二轮 250 帧，日志 `sequence 0..249`（`turn-2`） |
| 序号**可以回退**（历史事实） | `SocketTransportTests.swift:500-505`：F18「a transparent reopen restarted numbering at 1 while the watermark sat in the hundreds, and every frame after it was dropped **in silence**」 |
| 「网关不再重启编号」是**后端承诺**，不是客户端不变量 | 同上注释 + `URLSessionSocketTransport.swift:379-380` |

**结论**：**客户端假设的编号域（每连接单调）与实测的编号域（每轮从 0 起）不一致。**
这不是措辞问题——它是 D2 的直接根因。

## 9. 缺陷清单

> 每条给出：位置 / 证据 / 影响 / **确定性**。确定性分三档：
> **【实证】**有可复现输出或测试钉住 · **【读码】**从代码顺序直接读出 · **【推断】**有推断链，需真机或后端配合确认。

### D1 — `aiFirstAudioChunk` 早于归属判定，被丢弃的帧也会把会话推进到「AI 说话中」 ✅ 已修（2026-09-22）

> **修订（2026-09-22，`12_`）**：本条**已修**，见 [`12_D1_首块音频判定顺序修正.md`](./12_D1_首块音频判定顺序修正.md)（提交 `0436c27`）。修法是把 `dispatch(.aiFirstAudioChunk)` 与两条计时移到 `onAudioFrame` 返回 `.played` 之后，原文的机理与实证输出全部成立、无需修订。

- **位置**：`SpeechSessionMiddleware.swift:709-732`
- **证据【实证】**：本次复核实跑 `swift test` 的输出（原文，未改写）：

  ```
  timing_phase_transition ["from": "processing", "to": "aiSpeaking", "stage": "tts", ...]
  timing_ai_first_chunk ["sequence": "1", "payload_bytes": "1", "turn_id": "turn-1", ...]
  timing_first_response ["source": "audio", "first_response_ms": "12.851", "turn_id": "turn-1"]
  tts_frame_dropped ["reason": "unknownTurn", "turn_id": "nil", "phase": "feed",
                     "error": "no active turn (missing ai.tts.start)", "sequence": "1"]
  ```

  同一个 `sequence: 1` 的帧：先被记为「AI 第一块音频」「首响 12.851ms」，**紧接着被判为丢弃**。
- **机理**：handler 的顺序是
  `dispatch(.aiFirstAudioChunk)` → `timings.markTurnOnce("ai_first_chunk")` → `timings.markFirstResponse(nil, source:"audio")`
  → **然后才** `switch await ttsCoordinator.onAudioFrame(frame)`。
  而 `(.processing, .aiFirstAudioChunk) → .aiSpeaking`（`SpeechSessionMachine.swift:191-193`）。
- **影响**：
  1. UI 进入「AI 正在说话」，实际一声不响——这正是本链路历史失败模式「转写正常、没有声音」的用户可见形态。
  2. `first_response_ms`（产品生死线 P90 ≤ 1.5s 的口径）被污染。且 `markTurnOnce` / `markFirstResponse`
     **每轮只报一次**，真正的第一块音频永远无法纠正这条样本。
  3. `phaseBox` 变成 `.aiSpeaking`，于是下一次 `.speechStarted` 会命中
     `if phaseBox.get() == .aiSpeaking { submitTranscript("__interrupt__") }`（`:470-472`），
     **向网关发一次无来由的 interrupt**。
- **自相矛盾之处**：同一个 handler 里，`tts_first_audio` 是**有闸门的**（`case let .played` 且 `count == 1`，`:733-744`），
  而相位翻转与两条计时**没有闸门**。同一函数、两套规则——这说明顺序是漏改，不是决定。
- **确定性**：【实证】

### D2 — 传输层 `BargeInAudioGate` 既不做它被声称做的工作，又是唯一能无声吞掉整轮音频的机制 ✅ 已修（2026-09-22）

> 1. **D2b 的确定性从【推断】升到【实证】**。没有新增真机事实，而是把它的后果钉进了单元测试（`aBargeInMustNotSwallowTheNextTurnsAudio`）：脚本不给被打断轮发 `ai.turn.end`、下一轮编号从 0 重启。逐字红输出见 `18_` §6.1。**实证的是「客户端在这个脚本下确实吞帧」，不是「真机上必定发生」。**

分三条独立命题。

#### D2a — 它**不可能**丢弃被打断那一轮的后续帧 【实证】

- **位置**：`AudioFrameDropGate.swift:147-152` + `:16-24`
- **机理**：`markInterrupted()` 把水位设成 `maxObservedSequence`，即**已经收到的最高序号**；
  判定是 `shouldDrop(seq) = seq <= watermark`。WS 是保序流，所以打断之后到达的帧序号**必然大于**水位 → **一律放行**。
  也就是说：它只能挡住重复帧/乱序帧，**挡不住「被打断那一轮还在链路里的帧」**——而后者正是它被写在注释里的唯一职责。
- **测试亲手钉住了这一点**：`SocketTransportTests.swift:562-567`
  ```swift
  await transport.markInterrupted()                                    // maxObserved = 2
  #expect(await transport.emitAudio(sequence: 2) == false)             // 重复帧 → 丢
  #expect(await transport.emitAudio(sequence: 3) == true)              // 后续帧 → 放行（注释：「A later frame closes the run」）
  ```
- **推论**：真正让被打断那一轮停下来的是 `TTSPlaybackCoordinator.onInterrupt` → `.superseded` +
  `sink.interruptNow()`，**不是**传输层水印。于是三处文档断言是错的：
  `README.md:23`「今天 barge-in 的丢弃**只在传输层发生一次**（`BargeInAudioGate`）」、
  `LiveAudioEngine.swift:826`、`AppDependencies.swift:130-132` 的同一句话。
- **确定性**：【实证】

#### D2b — 它能在窗口期内把**下一整轮**音频吞掉，且无自愈 【推断】

- **机理**：水位从武装到 `ai.turn.end` 之间一直有效。而实测编号是**每轮从 0 起**（`08_` §2）。
  所以在窗口期内到达的下一轮帧（`0..N` ≤ 水位）会被**全部丢弃**。
- **这正是 F18 的形状**：`SocketTransportTests.swift:500-505` 记着「numbering restarted at 1 while the
  watermark sat in the hundreds, and every frame after it was dropped **in silence**——text kept arriving, audio was simply gone」。
- **现有的两道保险都是后端承诺，不是客户端不变量**：
  1. 被打断那一轮的 `ai.turn.end` 必须先于下一轮首帧到达（代码注释称「B15 guarantees it on every exit path」，`:382-385`）；
  2. 网关不得重启编号（`:379-380`「The gateway no longer restarts numbering」）。
- **无自愈**：清除水位的路径只有 `ai.turn.end` 与 `connect()`。若被打断的那一轮**永远收不到** `ai.turn.end`
  （连接断了、回合被放弃、后端把它当会话级中止），水印会一直武装到下一次 `connect()`，期间每一轮都可能整轮静音。
- **为什么只是【推断】**：dev harness 是一次性突发（250 帧 ~10ms 到齐）+ `ai.tts.end` 紧随，
  而 `08_` §3 明确记载「**没有在途帧可丢**」——barge-in 的端到端行为从未被验证过。
  要坐实 D2b 需要网关**流式**发送 + 一次人工打断，见 §10 待复核。
- **确定性**：【推断】
