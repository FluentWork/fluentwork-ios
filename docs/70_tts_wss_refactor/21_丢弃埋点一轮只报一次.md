# 21 — 实现说明：丢弃埋点一轮只报一次

> 对应缺陷：`10_事实基线与缺陷清单.md` **D6**（🟡【读码】）。
> 改动：`.dropped` 分支的上报按 **(轮次, 原因)** 去重，落在 `TTSStreamTrace` 里，与 `frames` 共用 `reset()` 的生命周期。
> 红：`aWholeDroppedTurnReportsTheReasonOnce`（`TransportRoutingEquivalenceTests.swift:325`）。

## 1. 这条改动守的是什么契约

**「这一轮在丢帧」是一个事实，不是一个时刻。**

一轮的音频有上百帧。逐帧上报同一个事实，会把那条真信号埋在自己的重复里——而这条链路的另一端**已经为同一件事改过一次**。

`08_真机验证记录_2026-09-20.md` §5.2 记着 `ai_first_chunk` 的原状：**「每帧都打（250 帧 = 250 行），把真响应的第一条埋掉」**，由 `cacfdd2` 用 `markTurnOnce` 改成每轮只报一次。

改动前的丢弃路径（`SpeechSessionMiddleware.swift:751-762`）留着同一个问题：`.dropped` 分支对**每一帧**调一次 `tracker.track`。在真正要紧的形状里（`10_` D2b：一整轮无归属）那是每轮上百条 `tts_frame_dropped`。

## 2. 根因

一句话：**丢弃的判定是逐帧的，但「在丢帧」这个结论是逐轮的，而上报跟着判定走了。**

| 子命题 | 确定性 | 证据 |
|---|---|---|
| `.dropped` 分支对每一帧 track 一次 | 【读码】 | `SpeechSessionMiddleware.swift:751-762`（改动前）；实测 250 帧 → 250 条 |
| 同一条链路的 `ai_first_chunk` 有同一形状，已被 `markTurnOnce` 修掉 | 【实证】 | `08_` §5.2 逐字记录；`cacfdd2` |
| D2b（一整轮无归属）是「真正要紧的形状」 | 【推断】 | `10_` D2 的论证：整轮被吞时用户听到的是安静；`18_` 已删掉能造成它的那道门 |

第三条标【推断】：**「一整轮被丢弃」今天已经不再由客户端的门造成**（`18_` 删了传输层水印）。剩下的成因是网关不发 `ai.tts.start`、或 `start` 丢失/乱序。本仓无法证伪网关不会这样，也没有真机样本。所以这条改动的定位是**可观测性**，不是修一个已发生的故障。

## 3. 改法

| 位置 | 改动 |
|---|---|
| `SpeechSessionMiddleware.swift:751-762` | `.dropped` 分支加 `guard ttsTrace.shouldReportDrop(reason: reason) else { return }` |
| `SpeechSessionMiddleware.swift:1538-1577` | `TTSStreamTrace` 新增 `reportedDropReasons: OSAllocatedUnfairLock<Set<TTSDropReason>>`、`shouldReportDrop(reason:)`；`reset()` 一并清空 |

### 3.1 为什么台账放在 `TTSStreamTrace`

它是这条链路**已经存在的**每轮账本：`ai.tts.start` 处 `ttsTrace.reset()`、每播一帧 `recordAudio()`、`ai.tts.end` 读 `audioFrameCount()`。

丢弃上报需要的生命周期与它**逐字相同**——「这一轮报过了没有」和「这一轮播了几帧」是同一轮的两个计数器。放进新类型就得把 `reset()` 的调用点复制一份，而复制出来的那一个会在下一次有人改 `tts.start` 时漂移。

### 3.2 为什么去重键是 `(轮次, 原因)` 而不是只用轮次

一轮里可以有**不止一种**丢弃原因：`.superseded`（旧轮的迟到帧）与 `.unknownTurn`（无归属）可以同时发生。只用轮次做键，第二种原因会被第一种吃掉——那等于用「少报」换掉「多报」。

键里的「轮次」不是显式字段，而是 `reset()` 的**代际**：集合在 `tts.start` 处清空，所以同一轮的同类丢弃折叠成一条，下一轮的同类丢弃仍然报。

### 3.3 事件名与属性一个都没改

`tts_frame_dropped` / `tts_decoder_failed` 这两个名字**必须保住**：`08_` §4 的真机核对表有一行是

> | 无 `tts_decoder_failed` / `tts_frame_dropped` / `transport_audio_dropped` | 一帧都没被丢 |

那份核对表还没执行（真机验证仍未做）。改名会让它按旧名字 grep 出空结果，而空结果读起来正是「一帧都没被丢」——**改名会把一次「没验到」伪装成一次「验过了」**。

属性集（`phase` / `turn_id` / `sequence` / `reason` / `error`）也全部保留。

### 3.4 有意**不做**：不走计时通道

仓内最顺手的「每轮一次」是 `SpeechSessionTimingsRecorder.markTurnOnce`，`ai_first_chunk` 用的就是它。**没有采用**，因为它会把事件改名成 `timing_<event>`（`markTurnAnchored` 的固定前缀）并附加 `delta_ms` / `total_ms` / `prev_event` / `since_turn_start_ms`。

两个理由：

1. **丢弃不是计时事件。** `timing_` 前缀在这个仓里表示「一个时刻距上一个时刻多久」。丢弃没有这个语义。
2. **§3.3 的改名问题**——`markTurnOnce` 强制前缀，等于绕不过改名。

代价是这里出现了第二个「每轮一次」的实现（`markTurnOnce` 之外）。这是本次有意付的代价，记在 §7。

## 4. 为什么这样改，而不是别的方案

### 4.1 方案 A：`markTurnOnce`（复用计时通道）

见 §3.4。改名会毁掉真机核对表。

### 4.2 方案 B：announce + close，把丢弃**数量**也报出来

`18_` 删掉的 `AudioDropReport` 就是这个形状（`recordDrop` / `closeRun`，测试名 `audioDropReportAnnouncesTheRunThenClosesWithTheLoss`）。**本次不采用**，但**这是本次最有价值的一条遗留**，理由如下：

它确实比本方案多一个信息——**丢了多**少**帧**。本方案只报「丢了、原因是什么」。

不做的理由：

1. **评审给这张票定的范围是「去重」。** `11_` §6.3 第 6 行的原文是「丢弃路径埋点**去重**」。
2. **它需要 run 的生命周期**：announce 在 run 开头、close 在 run 结尾，于是要有「run 结束了」的触发点（下一帧播成功、或 `ai.tts.end`）。本方案的触发点是 `reset()`，已经存在；run 方案要新加至少两处接线。
3. **`AudioDropReport` 是 `18_` 刚删掉的代码。** 同一个形状删了又加，会让下一次读 `18_` 的人无法判断「删它是不是错的」。

所以本次**只做去重**，并把「丢弃数量」单列为 §7 的后续项。这是一个**明确的取舍**，不是遗漏。

### 4.3 方案 C：把丢弃数量挂到 `ai.tts.end` 的属性上

看起来最省事（`tts_end` 已经有 `audio_frames`）。**没有采用**，因为 `unknownTurn` 的丢弃发生在**任何轮次之外**——没有 `tts.start` 可以给计数器归零。挂到 `tts.end` 上，这些帧要么被算进**下一轮**（错误归属），要么在 `reset()` 时被清掉（丢失）。两个结果都比现在差。

## 5. 影响面

- **状态机**：无影响。
- **协议（线上）**：无影响。
- **音频**：**行为零变化**。播/丢决策一个字没动——改的只是「丢弃之后报几条」。
- **可观测性**：`tts_frame_dropped` / `tts_decoder_failed` 的**条数**从「每帧一条」变成「每轮每因一条」。事件名、属性、触发条件（哪些帧算丢弃）全未变。
  - **这是一次埋点语义的收紧**：如果已有看板按「条数 = 丢弃帧数」统计，它会失准。本仓没有这样的看板（`08_` §4 的核对表是按**有无** grep，不是按条数）。
- **回滚**：`git revert` 该提交即可。

`250` 与 `10` 这两个数字本身就是证据：**条数等于帧数**。失败点落在条数上，不是落在事件名或属性上——真因就是「逐帧上报」。

### 6.2 为什么必须有第二条

第一条只断言「1 条」。**「第一帧报完之后就再也不报」也能让它变绿**——而那会让第二次丢帧事故完全看不见。

第二条钉的是去重的**粒度**：两段丢弃之间隔着一次完整的 `ai.tts.start` / `ai.tts.end`，去重台账在那里重置，所以第二段必须再报一条。这与 `12_` §6.2 那对测试是同一个手法（`droppedAudioFrameDoesNotAnnounceFirstChunk` 的反面 `playedAudioFrameStillAnnouncesFirstChunk`）。

## 7. 顺带记录：本次没做、但值得单独立项的一条

**丢弃的「数量」没有被上报。**

今天能看到的：`tts_frame_dropped` 一条（含 `reason`、`turn_id`、首个被丢帧的 `sequence`），加上 `ai.tts.end` 的 `audio_frames`（**播了**几帧）。

看不到的：**丢了几帧**。

对「整轮静音」这个形状这不影响诊断——`audio_frames: 0` 加上 `reason=unknownTurn` 已经把话说完了。对「回复回了一半」这个形状（`77_` P1-22 原本的关切）它不够：半丢时 `audio_frames` 是个非零的正常数字，而丢了多少无从得知。

要补它，形状是 **announce + close**（§4.2），与 `18_` 删掉的 `AudioDropReport` 同形。**建议单独一张票**，因为：

1. 它要新加 run 的结束触发点（至少两处接线）；
2. 它需要先定「run」的定义——「连续被丢的帧」在 `.superseded` 与 `.unknownTurn` 混在一起时算几段；
3. 它是**加信息**，不是**修缺陷**，与 D6 的性质不同。
