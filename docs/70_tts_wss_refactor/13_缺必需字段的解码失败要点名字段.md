# 13 — 实现说明：缺必需字段的致命解码失败要点名字段

> 相关缺陷：`10_事实基线与缺陷清单.md` **D5**——但 D5 需要**重判**，理由见 §7。
> 改动：`WSControlFrameCodec.decode` 归类 `DecodingError.keyNotFound`；两条新测试；一条既有测试的断言更新。

## 1. 这条改动守的是什么契约

**一个致命解码失败的文案，必须点出是哪个字段坏了。** 否则它只是「线上有东西不对」，而排查的人得先猜。

这条契约不是本文发明的，它写在被改的那个函数自己的注释里（`URLSessionSocketTransport.swift`）：

> Pretty-prints a `WSControlFrameCodingError` so the iOS log doesn't fall back to
> NSError's default "the operation couldn't be completed" bridge
> (`framecodingerror error 0`) for a *fatal* decode failure.
>
> No longer reached for `unknownType` — that case is a version difference and is
> skipped rather than failed (see `handle`). **It stays in the switch because the
> enum is closed and the remaining case must keep its readable message.**

「那个 remaining case」就是 `missingField`。所以契约是：

```
缺必需字段 ⇒ 致命（策略不变）
            ∧ 文案里有字段名（本文要修的）
```

改动前，这条契约的**后半句是空的**——前半句成立，后半句从未成立过。

## 2. 根因

`WSControlFrameCodingError.missingField` 是**死码**：声明了、在 `describe(_:)` 里有专属文案、在 `mapError` 链上有分支，但**全仓没有一个 `throw`**。

`WSControlFrame.init(from:)` 里唯一的 `throw` 是 `:351` 的 `.unknownType(type)`。缺必需字段抛的是 `KeyedDecodingContainer` 的 `DecodingError.keyNotFound`，它**不是** `WSControlFrameCodingError`，于是在 `handle(message:)` 里：

```swift
} catch let error as WSControlFrameCodingError {
    if case let .unknownType(type) = error { ...skip... }
    throw SocketTransportError.decodingFailed("... \(describe(error)) ...")   // ← missingField 本该走这里
} catch {
    throw SocketTransportError.decodingFailed("... \(error.localizedDescription) ...")  // ← 实际走这里
}
```

泛化 catch 走 `error.localizedDescription`，对 `DecodingError` 就是 NSError 桥接的
`The data couldn't be read because it is missing.`

**即：`describe(_:)` 只收 `WSControlFrameCodingError`，而它声明自己为之存在的那个 case，永远到不了它手里。** 同一文件里 `unknownType` 那条注释（「客户端不该把自己从更新的服务端上断开」）说明作者是认真想过失败语义的——只是这条路径没接上。

## 3. 改法与被谁拥有

| 文件 | 改了什么 |
|---|---|
| `Shared/FluentWorkNetworking/Socket/WSControlFrame.swift` | 新增 `WSControlFrameCodingError.classify(_:)`——只认领 `keyNotFound`，返回 `.missingField(key.stringValue)`；`WSControlFrameCodec.decode` 用它归类，认领不了的原样重抛 |
| `Shared/FluentWorkNetworking/Socket/URLSessionSocketTransport.swift` | **仅注释**：指出归类发生在 codec，因此 `missingField` 才是 `describe(_:)` 的活路径 |
| `Tests/FluentWorkCoreTests/Networking/SocketTransportTests.swift` | 新增 2 条测试（编解码器层 + 可观测层）；更新 `controlFrameCodecRejectsErrorFrameMissingCode` 的断言 |

**没有新类型、没有新错误 case、没有新接缝。** `classify` 复用的是早已声明好的 `.missingField`。

只认领 `keyNotFound`：`typeMismatch` / `dataCorrupted` 用 `DecodingError` 自己的描述已经够用，为它们再造一个名字只会得到同一个失败的两套拼写。`key.stringValue` 取的是**线上名**（`sample_rate`，不是 `sampleRate`），也就是读者要拿去和后端 schema 对照的那个名字。

## 4. 为什么归类放在 codec，而不是放进 `init(from:)`

更「正统」的位置是 `WSControlFrame.init(from:)`——`WSControlFrameCodingError` 已经在那里抛（`unknownType`），归类放一起更内聚。**没这么做，原因是代价：**

枚举的 `init(from:)` 必须恰好给 `self` 赋值一次，所以它没法把那段 115 行的 switch 抽成 `mutating` 辅助方法；要做只能把它重写成返回 `WSControlFrame` 的 `private static func`，整段 switch 的 `self = .x(...)` 全部改成 `return .x(...)`。**为一条诊断改进动 115 行机械改写，评审面远大于收益。**

而 codec 层并不因此变得不合适：`WSControlFrameCodec.decode` 是调用方实际使用的边界，且**所有** `WSControlFrameCodingError` 本来就都在那里浮出（`unknownType` 由帧解码器抛出、原样穿过 codec）。在 codec 归类不是「把同一件事拆到两层」，而是**在这条边界上把归类补完**。

留作后续（不在本次范围）：若将来 `init(from:)` 因为别的理由被重构成静态工厂，`classify` 应随之搬进去。

## 5. 影响面

- **状态机**：无影响。
- **协议**：无影响。线上一个字节没变，解码的**接受/拒绝集合**也一个没变——变的只是拒绝时报出的错误类型与文案。
- **音频**：无影响。
- **失败策略**：**不变。** 缺必需字段仍然致命、仍然拆连接（这与冻结 schema 的 `required` 一致，见 §7）。本次只改「失败怎么说」，不改「失败与否」。
- **错误面**：`WSControlFrameCodec.decode` 对缺必需字段抛出的类型由 `DecodingError` 变为 `WSControlFrameCodingError.missingField`。这是**公开 API 的错误面变化**，已核对全仓调用方：只有传输层（两种都处理）与测试。
- **回滚**：`git revert` 该提交即可。

## 6. 测试

### 6.1 先红：改动前的失败输出（原文）

```
✘ Test missingRequiredFieldIsClassifiedAsMissingField() recorded an issue at
    SocketTransportTests.swift:67:5: Expectation failed: expected error ".missingField("codec")"
    of type WSControlFrameCodingError, but "DecodingError.keyNotFound: Key 'codec' not found in
    keyed decoding container. Debug description: No value associated with key
    CodingKeys(stringValue: "codec", intValue: nil) ("codec")." was thrown instead
```

可观测层那条更直白——**这就是操作员实际读到的东西**：

```
✘ Test receiveLoopNamesTheMissingRequiredField() recorded an issue at
    SocketTransportTests.swift:434:5: Expectation failed: message?.contains("codec") == true
↳ 失败文案没点名缺的字段，排查无从下手：
  control frame decode failed: The data couldn’t be read because it is missing. (bytes=77)
```

`codec` 三个字不在里面。

### 6.2 新测试

| 测试 | 层 | 断言 |
|---|---|---|
| `missingRequiredFieldIsClassifiedAsMissingField` | 编解码器 | 缺 `codec` 的 `ai.tts.start` 抛 `WSControlFrameCodingError.missingField("codec")` |
| `receiveLoopNamesTheMissingRequiredField` | 可观测 | 同一条帧过真接收循环，`.failure(.decodingFailed)` 的**文案里含 `codec`** |

第二条是必要的，因为**既有测试只钉「循环会死」、从不钉文案**（`receiveLoopStillDiesOnAMalformedControlFrame`）——这正是本缺陷能活到现在的原因。一个「会死但说不清为什么死」的循环，测试与线上都看不出区别。

### 6.3 更新的既有测试：`controlFrameCodecRejectsErrorFrameMissingCode`

它的断言是 `#expect(throws: DecodingError.self)`，本次必须改，理由记在这里而不是默默改掉：

- 该测试的**注释**自称在描述实现细节：「Swift's KeyedDecodingContainer surfaces a missing required field as `DecodingError.keyNotFound`, **which the Codec propagates unchanged**.」——它把「原样透传」当事实陈述，而不是当要求。
- 它的**要求**是「缺 `code` 必须被拒绝」，这一点**没变**。
- 被改掉的正是那个「原样透传」——因为透传本身就是本缺陷。

所以新断言是 `WSControlFrameCodingError.missingField("code")`：要求保留，失败的名字换成编解码器自己的。

已核对**不受影响**的两条（都是 `dataCorrupted`，不在 `classify` 的认领范围）：`feedbackBadgeRejectsMisspelledTier`（`"Soft"`）、`clientTurnAbortRejectsOkOutcome`（`"ok"`）。

## 7. 与 D5 的关系：`10_事实基线与缺陷清单.md` 的 D5 需要重判

**本文之所以是这张票而不是 D5 本身，是因为 D5 的立论前提在读码后被推翻了两处。** 摊开：

| D5 的说法 | 读码结果 |
|---|---|
| 「`voice_id`、`sample_rate`、`codec` **没有任何消费者**」 | ❌ **不准确。** 三者在 `SpeechSessionMiddleware.swift:780-782` 都被读走，作为 `tts_start` 的埋点属性。准确的说法是「没有任何代码**按它们的值分支**」——功能性论证成立，字面表述不成立。 |
| 「同一条推理没有被应用到字段缺失」 | ⚠️ **不成立。** 作者在 `handle(message:)` 注释里明确表过态：`unknown type` 是版本差异（跳过），`missing required field` 是契约违规（失败）。这是**画过线**的，不是漏改。 |
| （基线未记）冻结 schema 对这些字段的要求 | 🔴 **决定性，且方向相反。** `wss-control-frames-v2.json` 写着 `aiTTSStart.required = ["type","turn_id","voice_id","sample_rate","codec"]`。客户端的严格**与后端自己发布的契约逐字一致**，不是客户端擅自加严。 |

结论：**D5 不是「客户端要求了不该要求的字段」。** 客户端要求的正是契约要求的。它剩下的是一个**失败策略**问题，而且是一个真问题：

> 一个只被用来打日志的字段缺失，代价是**整条会话拆掉**。契约说它 required 是对的，但「契约违规 ⇒ 拆连接」这个换算关系，是拿最大的爆炸半径去执行一条最低价值的约束。

这属于策略选择，**需要产品/后端一起定**，不是我在单测里能替你拍板的。三个可选方向：

1. **保持现状**（契约违规就拆）——理由是严格解码是契约漂移的唯一运行期信号。**反对意见**：漂移检测已经由 `PackageBaselineTests` 在构建期覆盖，运行期拆连接不增加检测能力，只增加爆炸半径。
2. **只对无分支消费的字段宽松**（`voice_id` / `sample_rate` / `codec` 改 `decodeIfPresent`）——`turn_id` 仍然必需。
3. **对 `ai.tts.start` 整帧宽松**：字段缺失只丢这一帧、留连接 + 埋点（与未知 `type` 同策）。

**本文的改动与这三条都正交**：无论选哪条，失败一旦发生，文案都该点名字段。所以这次先把诊断修好，策略留给 §7 的决定。
