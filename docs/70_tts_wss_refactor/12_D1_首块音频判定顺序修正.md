# 12 — D1 实现说明：把「首块音频」的判定排到归属判定之后

> 对应缺陷：`10_事实基线与缺陷清单.md` **D1**（🔴 实证）。
> 改动：`SpeechSessionMiddleware.swift` 的音频 handler 重排 + 两条新测试 + 一条既有测试的夹具修正。

## 1. 这条改动守的是什么契约

**「AI 开始说话了」这句话，只能由一帧真的会被播出去的音频说出。**

`TTSFrameOutcome` 已经把「这一帧会不会出声」回答得很清楚：`.played` 会，`.dropped` 不会
（三种原因：`superseded` / `unknownTurn` / `decodeFailed`）。而 `.aiFirstAudioChunk` 是
`.aiSpeaking` 的**唯一入口**（`SpeechSessionMachine.swift:191`）。两者之间的关系因此必须是蕴含关系：

```
dispatch(.aiFirstAudioChunk)  ⟹  刚刚发生的是 .played
```

改动前这个蕴含关系是**反的**——先宣告，后判定，于是被丢弃的帧也会宣告。

## 2. 改法与被谁拥有

| 文件 | 改了什么 |
|---|---|
| `Shared/FluentWorkCore/Architecture/Middleware/SpeechSessionMiddleware.swift` | `makeTransportEventRouter` 的 `audioHandler`：把 `dispatch(.aiFirstAudioChunk)`、`markTurnOnce("ai_first_chunk")`、`markFirstResponse` 三件事从 `switch` **之前**移到 `case .played` **之内**。`.dropped` 分支不动。 |
| `Tests/FluentWorkCoreTests/Architecture/TransportRoutingEquivalenceTests.swift` | 新增两条测试（一正一反），`ProductionRoutingWiringTests` 套件内 |
| `Tests/FluentWorkCoreTests/Architecture/SpeechSessionMiddlewareTests.swift` | `turnCounterSyncedWithMachineState` 的夹具修正（见 §5） |

**没有新类型、没有新协议、没有新接缝。** 决策点仍然只有一个（`TTSPlaybackCoordinator`），
这条改动只是把已有的判定结果**先取回来再用**。

## 3. 根因

埋点与相位翻转写在判定之前：

```swift
// 改动前
await dispatchBox.dispatch(.speakingRoom(.session(.aiFirstAudioChunk)))   // ← 先宣告
timings.markTurnOnce("ai_first_chunk", ...)
timings.markFirstResponse(nil, source: "audio")
switch await ttsCoordinator.onAudioFrame(frame) {                          // ← 后判定
case let .played(turnID): ...
case let .dropped(...): ...
}
```

同一个函数里 `tts_first_audio` **是有闸门的**（`case let .played` 且 `count == 1`），
相位翻转与两条计时没有闸门——**同一函数、两套规则**，所以这是漏改而不是有意为之。

## 4. 为什么是「重排」而不是「折叠进既有路径」

三条路都试过：

1. **在 `.dropped` 分支里补一次「撤销」**（回退相位、撤销埋点）——需要给状态机加一个反向事件，
   而 `.aiSpeaking` 的出口是 `.aiTurnEnd`，撤销语义与 B15 的轮次收尾撞车。**否决。**
2. **让 `aiFirstAudioChunk` 由引擎在真的排进播放器之后回报**——这是更正确的形状（`play(pcm:)`
   的返回值已经在表达「排进去了没有」），但它把「播/丢判定」与「引擎是否在跑」两件事绑在一起，
   而 `startPlaybackIfNeeded()` 返回 `false` 的路径（引擎没起来）本来就是另一条已埋点的失败。
   **留作后续**，本次不扩面。
3. **重排**——判定先做，`case .played` 里再做那三件事。改动最小，且不引入新语义。**采用。**

## 5. 影响面

- **状态机**：无新事件、无新转换。但**行为有变**：一个 `.dropped` 的音频帧不再把会话推进到
  `.aiSpeaking`。这正是本次要修的东西。
- **协议**：无影响。
- **音频**：无影响。播放口、解码 seam、`BargeInAudioGate` 全未动。
  > **修订（2026-09-22，`18_`）**：`BargeInAudioGate` 此后**已被删除**，与本条的「未动」无关——本条改动时它还在。见 [`18_`](./18_删除传输层序号水印.md)。
- **埋点**：`ai_first_chunk` / `first_response` 不再由被丢弃的帧产生。
  两者都是「每轮一次」的样本（`markTurnOnce`），所以**这修掉的是永久性污染**——
  改动前，若一轮的第一帧被丢，这一轮的 `first_response_ms` 就永远错了。
- **副作用**：`phaseBox` 不再因丢弃帧变成 `.aiSpeaking`，于是
  `audioEventPump` 里 `if phaseBox.get() == .aiSpeaking { submitTranscript("__interrupt__") }`
  不会再发出无来由的 interrupt。**这是 D3 的一部分症状被顺带消掉**，但 D3 本身（一次打断两次 interrupt）
  未修，仍待处理。
- **回滚**：`git revert` 该提交即可。

## 6. 测试

### 6.1 先红：改动前的失败输出（原文）

新增的第一条测试对改动前的实现是红的：

```
✘ Test "无归属的音频帧不得宣告 aiFirstAudioChunk" recorded an issue at
    TransportRoutingEquivalenceTests.swift:228:9:
    Expectation failed: !recorder.actions.contains(where: isFirstAudioChunk)
✘ Test "无归属的音频帧不得宣告 aiFirstAudioChunk" failed after 0.002 seconds with 1 issue.
```

失败点正是要修的那一步：帧被丢弃，而 `aiFirstAudioChunk` 已经被 dispatch。

同一条缺陷在**接线级**的旁证，是改动前一次全量 `swift test` 的 tracker 输出（原文，未改写）：

```
[Tracker] timing_phase_transition [... "from": "processing", "to": "aiSpeaking", "stage": "tts"]
[Tracker] timing_ai_first_chunk ["sequence": "1", "payload_bytes": "1", "turn_id": "turn-1", ...]
[Tracker] timing_first_response ["source": "audio", "first_response_ms": "12.851", "turn_id": "turn-1"]
[Tracker] tts_frame_dropped ["reason": "unknownTurn", "turn_id": "nil", "phase": "feed",
                             "error": "no active turn (missing ai.tts.start)", "sequence": "1"]
```

同一个 `sequence: 1`：先被记为「AI 第一块音频」「首响 12.851ms」，紧接着被判为丢弃。

### 6.2 新测试

| 测试 | 断言 |
|---|---|
| `droppedAudioFrameDoesNotAnnounceFirstChunk` | 无 `ai.tts.start` 的帧到达后，`recorder.actions` 里**没有** `.aiFirstAudioChunk` |
| `playedAudioFrameStillAnnouncesFirstChunk` | 先 `ai.tts.start` 再帧，`recorder.actions` 里**有** `.aiFirstAudioChunk` |

第二条是第一条的反面：少了它，「干脆不发 `aiFirstAudioChunk`」也能让第一条变绿，
而那样房间永远不会离开 `.processing`——等于用另一种静音换掉这一种。

两条都走**生产工厂** `makeTransportEventRouter`，与 `ProductionRoutingWiringTests` 的既有做法一致：
测的是接线本身，不建 store、不起泵。

### 6.3 改动暴露的第二处问题：既有测试的夹具同时依赖了两件事

`turnCounterSyncedWithMachineState` 在重排后变红，**两次**：

**第一次**（缺 `ai.tts.start`）——测试发了一个无归属的帧就等 `.aiSpeaking`：

```
✘ Test turnCounterSyncedWithMachineState() recorded an issue at
    SpeechSessionMiddlewareTests.swift:1162:6: Caught error: TimeoutError()
```

补上 `ai.tts.start` 之后**第二次**红，且这次暴露了更隐蔽的一件事：

```
[Tracker] tts_start ["turn_id": "turn-1", "sample_rate": "16000", "voice_id": "mock_voice_01", "codec": "pcm"]
[Tracker] tts_decoder_failed ["sequence": "1", "error": "oddSampleCount(1)", "turn_id": "turn-1",
                              "reason": "decodeFailed", "phase": "feed"]
✘ Test turnCounterSyncedWithMachineState() recorded an issue at
    SpeechSessionMiddlewareTests.swift:1162:6: Caught error: TimeoutError()
```

夹具的 payload 是 `Data([0x01])`——**1 字节，奇数**。解码 seam 是 `RawPCM16FrameDecoder`，
奇数长度直接抛 `oddSampleCount`。也就是说：**这条测试里的那帧音频从来没有真的播过**，
它此前只是被「先宣告、后判定」掩盖了。夹具已改为 `Data([0x01, 0x02])`。

这一条值得单独记：它说明这个缺陷的**伪装能力**——测试看起来在验证「AI 回话了」，
实际上验证的是「有人宣告了 AI 回话」，而帧本身是畸形的。
