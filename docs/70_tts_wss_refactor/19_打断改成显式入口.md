# 19 — 实现说明：打断改成显式入口

> 对应缺陷：`10_事实基线与缺陷清单.md` **D10**（🟡【读码】）。
> 改动：`SpeechSessionClientProtocol.submitTranscript(_:)` → `sendInterrupt()`，删掉 `"__interrupt__"` 哨兵（生产 4 处 + 测试 6 处）。
> **⚠️ 本条没有「先红」**——D10 是纯 API 形状缺陷，改动前后**线上行为完全相同**，不存在可失败的测试。按 `AGENTS.md` 的三条例外之第一条（新能力 / 无失败态），改为**钉住期望行为**。理由见 §6.1，这是本次最需要交代的一点。

## 1. 这条改动守的是什么契约

**一次打断只有一个入口，而且那个入口的名字就是它做的事。**

契约的反面是改动前的形状（`DefaultSpeechSessionClient.swift:139-144`，改动前）：

```swift
public func submitTranscript(_ text: String) async {
    guard text == "__interrupt__" else { return }
    try? await transport.send(control: .interrupt)
}
```

一个叫「提交转写」的方法，**对任何不是哨兵的字符串静默返回**。它不是「顺手也支持打断的转写接口」，它是**一个伪装的打断接口**——因为除哨兵之外它什么都不做。

## 2. 为什么这是缺陷，不是风格问题

### 2.1 它把「传错参数」从编译错误降级成静默无操作

`submitTranscript("interrupt")`（少两个下划线）、`submitTranscript("__interrupt")`、`submitTranscript("打断")`——**全部编译通过，全部什么都不做**。没有返回值、没有日志、没有断言。调用方拿到的是「成功」。

删掉这个方法之后，同一个错误变成**编译错误**。这是本次改动的主要价值，也正是它无法用测试钉住的原因（§6.1）。

### 2.2 真正的转写载体不是它

客户端转写（B13）的载体是 `sendSpeechBoundary(started: false, turnID:text:)` 的 `text` 参数（`DefaultSpeechSessionClient.swift:171-178`），它走 `user.speech.end` 上线。**那个参数一直存在。**

所以 `submitTranscript` 不是「一条冗余的转写路径」——它是**一条误导的路径**：将来接 B13 的人会先看到它，然后发现传什么都被丢掉。

### 2.3 它让第二个副作用藏起来了

改动前（直到 `79e0ffc`）它做**两**件事：`transport.markInterrupted()`（武装传输层序号水印）与 `send(control: .interrupt)`。**方法名只提到转写，两个副作用一个都没提。**

后果在别处记着：

- `14_`（D3）之所以存在，是因为两个触发点走同一条字符串却语义不同（一个武装水位、一个不武装）；
- `11_` §6.2 把它列为「四处各自决定同一件事」的第三处。

**水印在 `79e0ffc` 删了，但形状还在**——这才是本次要修的。一个方法名不提它做的事，下一个副作用还会藏进去。

## 3. 改法

| 位置 | 改动 |
|---|---|
| `SpeechSessionClientProtocol`（`AppDependencies.swift:282-294`） | `func submitTranscript(_ text: String) async` → `func sendInterrupt() async`，带契约注释 |
| `DefaultSpeechSessionClient.swift:139-169` | 实现 `sendInterrupt()`；删掉 `guard text == "__interrupt__"` |
| `PlaceholderSpeechSessionClient`（`AppDependencies.swift:447`） | 同步 |
| `SpeechSessionMiddleware.swift:471`（`audioEventPump`，VAD 路径） | `submitTranscript("__interrupt__")` → `sendInterrupt()` |
| `SpeechSessionMiddleware.swift:1221`（`.sendInterrupt` effect） | 同上 |
| 6 处测试替身 | 同步（详见 §6.3） |

### 3.1 两处**有意不动**的语义

1. **`try?` 仍然吞掉发送失败。** barge-in 不该在 socket 已死时额外报一次会话失败——socket 自己会报断连。它属于另一个问题（与 D6/D8 同族的「失败路径静默」），**不在 D10 范围**，本次不夹带（§7）。
2. **两个触发点都保留。** D3 修的是「不要发两次」，不是「合并成一处」：pump 那次**必须**在 `user.speech.start` 之前（否则网关重置打断记账，2026-09-12 那个失败），状态机那次是 effect 的落点。位置不同，职责不同。

## 4. 为什么是「删」而不是「改名 + 保留文本参数」

另一种改法是留着 `submitTranscript(_ text: String)`，只在内部把哨兵换成常量或枚举。**那会保留 §2.1 的陷阱**：任何字符串仍然编译通过，仍然静默无操作。

只有把「提交转写」这个能力**整个撤掉**，编译器才能替我们守住它。B13 落地时应当扩展的是 `sendSpeechBoundary` 的 `text`（它已经有这个参数），而不是复活一个名字与行为不符的方法。

## 5. 影响面

- **状态机**：无影响。
- **协议（线上）**：无影响。`control.interrupt` 帧本身、发送时机、顺序全未变。
- **音频**：无影响。
- **打断路径**：**行为零变化**。改动前后，一次 barge-in 在线上都是恰好一帧 `control.interrupt`。
- **API（源码级）**：`SpeechSessionClientProtocol` 有一处**破坏性变更**。仓内 6 处替身已同步；这是客户端内部协议，不是对外 SDK。
- **可观测性**：无变化。
- **回滚**：`git revert` 该提交即可。

## 6. 测试

### 6.1 为什么这一条没有「先红」（`AGENTS.md` 例外条款）

`AGENTS.md` 要求「每个修复都从一条会失败的测试开始」，并给了三条例外。**本条适用第一条：新能力（不存在失败态）——改为钉住期望行为。**

为什么不存在失败态，说清楚：

1. **行为没变。** 改动前后，一次 barge-in 的线上行为完全相同（一帧 `control.interrupt`）。唯一变化的是「能不能在编译期发现传错参数」——那是**编译期**性质，单元测试断言不了。
2. **测试本身写不出来。** 改动前要断言「客户端发了一次 interrupt」，只能写成「传哨兵，再检查替身记录的字符串」——**那就是把缺陷重新编码进测试**。这跟 `14_` §6.3 处理 `vadDuringAISpeakingTriggersInterruptSideEffects` 是同一类判断：一条测试若必须复述被删掉的机制才能存在，它就该跟着机制一起走。

### 6.2 新增的测试（钉住期望行为）

`sendInterruptPutsExactlyOneInterruptFrameOnTheWire`（`SpeechSessionClientTests.swift:417`）：真的 `DefaultSpeechSessionClient` + `InMemorySocketTransport`，调一次 `sendInterrupt()`，断言

- `sentControlFrames == [.interrupt]`（**恰好一帧**，且是它）；
- `sentAudioPayloads.isEmpty`。

**这是这条路径第一次有客户端级覆盖。** 既有那两条（`speakingRoomInterruptsPlayback`、`bargeInFromTheVADPathSendsExactlyOneInterrupt`）观察的是**替身**的调用计数——被测的是中间件，不是客户端。**客户端拿到调用之后做了什么，一直没人断言。**

它拦两类回归：

1. **偷偷加回第二个副作用**——被删掉的 `transport.markInterrupted()` 正是这样，而它之所以不可见，就是因为方法名说的是「提交转写」、没提任何副作用；
2. **打断路径上多一帧**——例如多一个 `user.speech.start`，网关会读成「新的一轮开始了」并重置上一轮的打断记账，正是 2026-09-12 那个失败。

### 6.3 改动的既有测试

| 测试 / 替身 | 改动 | 理由 |
|---|---|---|
| `StubSpeechSessionClient`（`SpeakingRoomSessionWiringTests`） | `transcripts: [String]` → `interruptCalls: Int`；`recordTranscript(_:)` → `recordInterrupt()`；`snapshotTranscripts()` → `snapshotInterruptCalls()` | 没有字符串可记了。计数是同一种观察、少一层间接——而且**不会因为调用方传了别的字符串而静默失效**（没有字符串） |
| `speakingRoomInterruptsPlayback` | `transcripts == ["__interrupt__"]` → `snapshotInterruptCalls() == 1` | 同上 |
| `bargeInFromTheVADPathSendsExactlyOneInterrupt` | 同上 | 同上 |
| `RecordingSpeechSessionClient`（`SpeechSessionMiddlewareTests`） | 去掉 `if text == "__interrupt__"` 过滤 | 见下 |
| `FailingSessionStartTransport` 之外的 3 处空实现 | 直接改名 | — |

> **第四条值得单说。** `if text == "__interrupt__"` 出现在**测试替身**里，意味着生产侧的哨兵字面量被**复制了一份**。若只改生产侧而漏了替身，测试会**全绿而打断实际没发出去**——替身会安静地不记录。这类「判据被复制到替身」是本次顺带清掉的。

## 7. 顺带记录：本次唯一没动、但值得单独立项的东西

**`sendInterrupt()` 的错误处理。** `try?` 让「打断根本没发出去」完全不可观测：socket 没连上、写失败、被取消——三种情况都变成一个静默的 no-op，而中间件那边 `.fireAndForget` 也不看结果。

它不是 D10（D10 是入口的形状，不是失败的可见性），但和 **D6**（逐帧丢弃埋点）、**D8**（actor hop）同族：**失败路径静默**。建议将来给它一条诊断，与 `tts_frame_dropped` 同一个思路——谁决定失败，谁负责上报。

本次不夹带，因为修它需要**先定一个新语义**（打断失败要不要影响会话相位？还是只埋点？），那是产品问题，不是实现问题。
