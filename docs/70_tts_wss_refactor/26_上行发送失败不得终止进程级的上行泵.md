# 26 — 实现说明：上行发送失败不得终止进程级的上行泵

> 对应条目：`70_/23_` §7 记录的 **3 处 `catch` 的 `return nil`**；本轮立为 **D15**。
> 决定来源：`25_` §2 第 5 条。
> 改动：`SpeechSessionMiddleware.swift` 的 `audioEventPump`，**3 处** `catch` 块（各 +1 行、−1 行）。
> 测试数：`589 → 590`。
> **有「先红」**，逐字输出见 §5。

## 1. 这条改动守的是什么契约

**一次会话的上行发送失败，不能终止进程级的事件读取者。**

它与 **D14 是同一条契约**，只是触发路径不同：D14 是引擎报错（`.failed`），
本条是**发送抛错**（`sendSpeechBoundary` / `sendAudioPCM`）。

## 2. 为什么这是缺陷

### 2.1 三处 `catch` 与 D14 的 `.failed` 分支逐字同形

`audioEventPump` 里三个会抛的发送点，`catch` 块完全一样：

| 行 | 触发事件 | 抛出的调用 |
|---|---|---|
| `:480-483` | `.speechStarted` | `sendSpeechBoundary(started: true, …)` |
| `:537-540` | `.speechEnded` | `sendSpeechBoundary(started: false, …)` |
| `:551-554` | `.pcmChunk` | `sendAudioPCM(data)` |

改动前，三处都是：

```swift
} catch {
    await dispatchBox.dispatch(.speakingRoom(.session(.failed(error.localizedDescription))))
    return nil
}
```

那个 `return nil` 跳出的是 `for await event in audioEngine.events()` 循环——
**而这条流是进程级的**。`endSession` 的注释写着它**刻意不取消**这个 reader：

> `No .cancel(id: audioEngineEvents): that reader belongs to the engine, not to this session.`

`LiveAudioEngine` 的那条 continuation 也**只在 `deinit` 里 `finish()`**（`stopCapture()` 不动它）。
所以 `return nil` 做的正是注释禁止的事，后果与 D14 逐字相同：

> 泵死后下一次会话完全没有上行（`beginSpeech()` 不跑、`user.speech.start` 不发、PCM 不转发、
> `.captureFirstBuffer` 没人接），房间卡在「连接中」，10 秒后报「连接超时，请重试」——
> **一次日常故障换来本次进程内所有后续会话失效，而错误信息指向网络。**

### 2.2 触发它的全是日常情形

三个发送点覆盖了上行**全部**的三类报文。任何一次 socket 抖动、任何一次写失败，
都会落进其中一个。而且 `.pcmChunk` 那条是**每帧**路径（每秒约 86 帧），
所以它不是「罕见路径」——它是**最可能先失败的那条**。

## 3. 改法：关闸，不返回

```swift
} catch {
    speechCaptureGate.abort()
    await dispatchBox.dispatch(.speakingRoom(.session(.failed(error.localizedDescription))))
}
```

删掉 `return nil`（泵继续读），补 `abort()`（先关闸，再报）。

### 3.1 `abort()` 不是修饰——它同时解决了「报几次」

`23_` §7 说修这条要「**先定『每会话报一次』的语义**」，因为 `.pcmChunk` 是每帧路径，
没有抑制就会把一次断连放大成每秒约 86 次 `.failed` 派发。

**实施时发现不需要任何新的去重结构——闸门本身就是抑制器：**

1. 发送失败 → `abort()` 关闸；
2. 之后每个 `.pcmChunk` 都被 `takeForwardDecision()` 拒绝，**且计入 `droppedOutside`**
   （所以「整段被丢」仍然可读，不是静默）；
3. `.speechEnded` 也被闸门挡住（它开头是 `guard speechCaptureGate.isOpen else { continue }`）。

于是**一次失败只报一次**，且**不需要新类型、不需要新标志位**。

### 3.2 语义从「每会话一次」变成「每句话一次」——而这更准

代价是：下一次 `.speechStarted` 会 `beginSpeech()` 重新开闸，若发送再次失败，会**再报一次**。
所以实际语义是**每句话报一次**，不是每会话报一次。

**这是有意的，不是妥协**：每一次发送尝试都是一次**独立的失败**，合并掉反而丢信息——
「这一句失败了」和「这个会话从第 3 句开始一直失败」是两个不同的诊断结论。
`21_` 的去重判据（「它说的是一个时刻，还是一个事实」）在这里给出同样的答案：
**每句话的失败是一个事实，不是同一个事实的重复。**

### 3.3 为什么先关闸、后派发（与 D14 同序）

派发 `.failed` 会推进相位并触发 `endSession`，而 `endSession` 在关 socket。
先关闸，保证在 socket 关闭之前**已经没有新帧被放行**——否则会往一个正在关闭的传输里写，
而那正是 `18_`/`D2b` 那类「写进已关闭的 socket」的窗口。

## 4. 为什么没有合并进 D14 的改动

`23_` §7 已经给过理由，这里重申并补一条：

1. **触发条件不同**：D14 是**引擎**报错，本条是**传输**发送失败。两者的诊断结论不同
   （一个查音频图，一个查网络），分开提交才能分开回滚。
2. **`.pcmChunk` 那处需要先定抑制语义**（§3.1），而 D14 不需要——D14 的 `.failed` 本身
   就是一次性事件。
3. **`AGENTS.md` Local Rule #6**：一次一张票。D14 与本条是两张票。

### 5.2 改动后（逐字）


同一轮日志里出现了会话二的 `timing_audio_capture_first_buffer` 与 `connecting → aiSpeaking`：
**泵活着，且交付了**。

### 5.3 为什么不用 `makeSessionLive` 造会话二

`makeSessionLive` 直接 dispatch `.socketReady` / `.captureLive`，**会绕过泵**——
用它造会话二，这条测试就永远绿。所以会话二走真实路径：
`socketReady`（socket 那一半）+ `.captureFirstBuffer`（**只能由泵交付的那一半**）。
会话一用 `makeSessionLive` 是允许的——它是**前提**，不是被测对象。
