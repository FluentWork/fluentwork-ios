# 17 — 实现说明：测试进程里的麦克风替身恒开

> 触发：用户要求「把麦克风部分 mock 掉，然后放入测试」。
> 改动：`MockDeviceMode.isMicrophoneMocked` 一处 + 两条新测试 + 替身文档。
> 前置：`16_测试进程不再构造真的音频引擎.md`（同一根轴的另一半）。

## 1. 这条改动守的是什么契约

**测试进程里，麦克风必须被视为「已被替身接管」。**

`09_麦克风替身.md` §3 写明麦克风在客户端有**三个**入口，替身要把三处都接过来：

| 入口 | 判据 | 16_ 之前的状态 |
|---|---|---|
| 引擎采集（`LiveAudioEngine`） | `AppDependencies.audioEngine` 的守卫 | ✗ 死码 → 真引擎 |
| **UI 权限（`MicrophonePermission.request()`）** | **`MockDeviceMode.isMicrophoneMocked`** | ✗ 恒假（本票修的就是它） |
| 音频会话（`AudioSessionManaging`） | 由前两者间接决定 | 跟随 |

`16_` 修了第一处。本票修第二处——**三个入口里唯一一个还有生产消费者、且判据在测试里恒假的**。

## 2. 根因：判据只读环境变量，而测试进程不设它

```swift
public static var isMicrophoneMocked: Bool {
    MockAudioEngine.Script.fromEnvironment() != nil   // ← 只读 FW_MOCK_MIC
}
```

`Script.fromEnvironment()` 读的是 `FW_MOCK_MIC`。真机验证时由 Xcode scheme 注入这个变量，所以**在那条路上它是对的**；但 `swift test` 跑起来时没人设它，于是：

- `MockDeviceMode.isMicrophoneMocked` 恒为 `false`；
- `MicrophonePermission.request()` 的第一道分支不生效，一路走到真 `AVAudioSession`：

```swift
public static func request() async -> Bool {
    #if DEBUG
    if MockDeviceMode.isMicrophoneMocked { return true }   // ← 恒不成立
    #endif
    #if os(iOS)
    return await withCheckedContinuation { continuation in
        AVAudioSession.sharedInstance().requestRecordPermission { granted in   // ← 真系统权限
            continuation.resume(returning: granted)
        }
    }
    #else
    return true
    #endif
}
```

**在 macOS 上这条路的后果被 `#else` 挡住了**（直接返回 `true`），所以 `swift test` 在本机看不出来；**在 iOS 模拟器上跑测试会真的去问系统** —— 那就是「测试在调用真机的麦克风」。

这与 `16_` 是同一个病：**判据读的是一个本仓实际运行方式下取不到真值的条件。** `16_` 那处判的是 XCTest 运行器才设的环境变量，本处判的是真机验证才设的环境变量。

### 2.1 反证（这条测试为什么能红）

新测试里有一句反证，先钉住「环境里确实没有 `FW_MOCK_MIC`」：

```swift
#expect(MockAudioEngine.Script.fromEnvironment() == nil)
```

这条为真，才说明「只读环境变量」那条路上替身是关的 —— 于是下一条断言（`isMicrophoneMocked` 为真）**必然**要求另一个判据存在。没有这句反证，测试可能因为环境里恰好设了变量而假绿。

## 3. 改法

```swift
public static var isMicrophoneMocked: Bool {
    if TestProcess.isRunning { return true }
    return MockAudioEngine.Script.fromEnvironment() != nil
}
```

与 `AppDependencies.TestProcess`（`16_` 引入）**共用同一个判据**，避免两处对「这是不是测试」给出不同答案 —— 这正是 `16_` 的教训。

| 文件 | 改了什么 |
|---|---|
| `Shared/FluentWorkCore/Audio/MockAudioEngine.swift` | `MockDeviceMode.isMicrophoneMocked` 加测试进程判据 |
| `Tests/FluentWorkCoreTests/Audio/MockAudioEngineTests.swift` | 新增 2 条（替身恒开、权限请求成功） |
| `docs/70_tts_wss_refactor/09_麦克风替身.md` | §3 补「测试进程里恒开」；§6 契约 8 条 → 10 条 |

**没有改 `MicrophonePermission` 本身，没有改 `MockAudioEngine` 的采集脚本，没有改真机验证路径。**

## 4. 为什么不动 `MicrophonePermission` 的另外四个成员

`MicrophonePermission` 还有 `isAuthorized` / `isDenied` / `isNotDetermined` / `status`，它们直接读 `AVAudioSession.sharedInstance().recordPermission`，**同样不看替身**。

本次**不改**，理由是它们**全仓零消费者**（`Grep` 可验：只有声明处，没有任何调用点）。给死码加替身判断只会增加表面积。这与 `13_` 记的「死码的三种表现」同类，**建议随该成员的首次真实使用一起处理**，或者直接删掉。

## 5. 影响面

- **生产行为：零变化。** 生产 app 不加载 XCTest，`TestProcess.isRunning` 为 `false`，`isMicrophoneMocked` 仍由 `FW_MOCK_MIC` 决定。
- **真机验证：零变化。** 替身仍由 `FW_MOCK_MIC=1` 打开；`TestProcess.isRunning` 在真机 app 里恒为 `false`，不会越过 scheme 的开关。
- **测试行为：权限请求不再有走真 `AVAudioSession` 的可能。** 在 macOS 上结果不变（本来就是 `true`），在 iOS 模拟器上是真实的行为修正。
- **`16_` 的效果不被回退**：`audioEngine` 的替身分支走的是 `MockAudioEngine.Script.fromEnvironment()`（在守卫**之前**），不经过 `MockDeviceMode`，所以测试仍拿 `PlaceholderAudioEngine`、真引擎构造次数仍为 0。
- **高风险区**：不碰 High-Risk Path #1（引擎本身）。
- **回滚**：`git revert` 该提交即可。

## 6. 先红：改动前的失败输出（原文）

```
✘ Test "测试进程里替身恒开：不依赖 FW_MOCK_MIC" recorded an issue at MockAudioEngineTests.swift:128:9: Expectation failed: MockDeviceMode.isMicrophoneMocked
↳ MockDeviceMode.isMicrophoneMocked → false
↳   isMicrophoneMocked → false
```

同一次运行里那条「权限请求必须成功」是**绿**的 —— 它挡不住这个缺陷，因为 macOS 上 `#else` 那一支本来就返回 `true`。这正是本缺陷能在 macOS 上长期存活的原因，也是新测试必须断言 `isMicrophoneMocked`（**机制**）而不只是 `request()` 的返回值（**结果**）的原因。
