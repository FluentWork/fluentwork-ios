# 16 — 实现说明：测试进程不再构造真的音频引擎

> 触发：用户报告「有一个测试在调用真机的麦克风」。
> 改动：`AppDependencies.swift` 三处「是不是在测试里」的判据 + 一条新测试。
> **结论与原始描述不同**：有问题的不是某一个测试，而是那三处**从不生效的判据**。

## 1. 这条改动守的是什么契约

**测试进程不得触碰真实音频硬件。**

这条契约在代码里是写着的。`AppDependencies.audioEngine` 的守卫注释原文：

> XCTest path: keep `PlaceholderAudioEngine` so unit tests that exercise
> reducer/middleware wiring without AVFoundation can still resolve
> `audioEngine()` without spinning up an `AVAudioEngine` graph.

「测试里解析 `audioEngine()` 不该构造 `AVAudioEngine` 图」是**明确声明过的意图**。本次不是引入新规则，是让这条既有声明**真的成立**。

## 2. 根因：判据用的是 XCTest 才设的环境变量，而本仓跑 Swift Testing

三处守卫都判同一个东西：

```swift
if ProcessInfo.processInfo.environment["XCTestConfigurationFilePath"] != nil {
```

| 位置 | 守卫意图 | 失效后果 |
|---|---|---|
| `audioEngine` | 测试给 `PlaceholderAudioEngine` | 测试拿到真 `LiveAudioEngine`（真 `AVAudioSession`、真麦克风；`deinit` 还无条件碰输入节点） |
| `dailyReadAudioPlayer` | 测试给 `StubDailyReadAudioPlayer` | 测试拿到真播放器，而它直接操作真 `AVAudioSession` |
| `backgroundTaskPort` | iOS 测试给 `NoOpBackgroundTaskPort` | iOS 测试拿到 `UIKitBackgroundTaskPort` |

`XCTestConfigurationFilePath` 由 **XCTest 的运行器**设置。本仓的测试用的是 Swift Testing（`import Testing`、`@Test`），门禁跑法是 `swift test` —— 走 `swiftpm-testing-helper`，**不设这个变量**。

### 2.1 实测（不是推断）

在测试进程里打一行探针：

```
TMP_PROBE XCTestConfigurationFilePath = <nil>
TMP_PROBE keys-with-XCTest = []
```

补一次更宽的探针，找可用的替代判据：

```
TMP2 XCTestConfigurationFilePath = <nil>          ← 三处守卫判的东西，不存在
TMP2 XCTestCase class = true                      ← XCTest 已加载
TMP2 processName = swiftpm-testing-helper         ← SwiftPM 的测试运行器
TMP2 xctest-bundles = []                          ← allBundles 里没有 .xctest
TMP2 testBundle = …/.build/out/Products/Debug/FluentWorkCoreTests.xctest
```

所以：**三道守卫全是死码。**

### 2.2 后果的量级

在 `audioEngine` 返回真引擎之前打一行探针，跑全量测试：

```
39
```

**39 次**真 `LiveAudioEngine` 构造，分布在 **37 条**测试里。它们全都与音频无关 —— corpus / review / dailyRead / launch / sessionHistory 的接线测试，只是解析整个依赖图时顺手拿到了 `audioEngine`：

```
◇ Test reviewMiddlewareLoadsFullReviewPayload() started.
◇ Test launchBootstrapsFlagsThenPresentsSpeakingRoom() started.
◇ Test dailyReadMiddlewarePlayTappedLoadsAndStartsPlayback() started.
◇ Test corpusMiddlewareHydratesCacheThenRefreshesRemote() started.
…（共 37 条）
```

**为什么这不是「多构造一个对象」**：

- 真的 `LiveAudioEngine` 的 `deinit`（`LiveAudioEngine.swift:444-448`）**无条件**执行
  `engine.inputNode.removeTap(onBus: 0)` —— 去碰真输入节点。对比 `stopCapture()`：它只在
  `hasInstalledTap` 为真时才走 `.removeTap`（`PlaybackTeardown.steps` 的 `tapInstalled` 参数）。
  **`deinit` 与 `stopCapture()` 对同一件事给了两种判据**，`deinit` 那种没有条件。
- 它带着 `DefaultAudioSessionManager`（`.playAndRecord` + `.voiceChat`）与真的
  `MicrophonePermission`，只要有一条路径真的走到 `startCapture()`，开的就是真麦克风。

### 2.3 我排除了什么（避免改错地方）

先按「哪个测试在开麦」逐个查过，**全部排除**：

| 检查 | 结果 |
|---|---|
| `LiveAudioEngineTests` 里所有 `startCapture()` 调用点（6 处） | 全部注入 `requestMicrophonePermission` / `startCaptureEngine` / `installCaptureTap`，无一触及真硬件 |
| 串行跑全量、给 `startCapture()` 加探针 | 触发的 6 条测试全是上述已注入的那 6 条 |
| `AudioSessionManagingTests` 用真 `DefaultAudioSessionManager` | `#if os(macOS)` 且 `configure` 在 macOS 是空实现 |
| `MockAudioEngineTests`（8 条） | 全部用 `RecordingPlaybackEngine` 替身 |
| `DailyReadAudioPlayerTests` | 全部注册 `StubDailyReadAudioPlayer` |
| `AudioInterruptionObserverTests` | 注入 `NotificationCenter()` |
| 测试里 `reconfigureForRouteChange()` 的唯一调用点 | 被 `guard hasInstalledTap else { return }` 挡住 |
| 测试里 `installTap` / `AVAudioEngine()` / `setCategory` 的出现 | 只在 `Shared/` 生产代码里，`Tests/` 一处都没有 |

**所以「某个测试写错了」这个前提不成立** —— 是判据写错了，而它的影响面是 37 条测试。改测试会改 37 处且治不了根；改判据一处即可。

## 3. 改法

新增一个具名判据，三处共用：

```swift
enum TestProcess {
    static var isRunning: Bool {
        if ProcessInfo.processInfo.environment["XCTestConfigurationFilePath"] != nil {
            return true
        }
        return NSClassFromString("XCTestCase") != nil
    }
}
```

- **为什么加 `NSClassFromString("XCTestCase")`**：`swift test` 与 `xcodebuild test` 都会把 XCTest 载入测试进程（实测 `true`），而生产 app 不链接 XCTest（`nil`）。这是**跨两种运行器都成立**的信号。
- **为什么两条都留**：环境变量那条覆盖「运行器已在、但类还没加载」的极早时刻。任一条为真即可，判据是**或**关系，不引入新的失败模式。
- **为什么不用 `processName == "swiftpm-testing-helper"`**：它只覆盖 SwiftPM，`xcodebuild test` 下不是这个名字。用它会把「测试」等价于「SwiftPM 测试」，比需要的窄。
- **为什么不用 `Bundle.allBundles`**：实测 `allBundles` 里**没有** `.xctest`（只有 toolchain 的 `swift/pm`），这条判据在本仓根本不成立。

| 文件 | 改了什么 |
|---|---|
| `Shared/FluentWorkCore/Dependencies/AppDependencies.swift` | 新增 `TestProcess`；`audioEngine` / `dailyReadAudioPlayer` / `backgroundTaskPort` 三处改用它 |
| `Tests/FluentWorkCoreTests/Architecture/AudioEngineResolutionTests.swift` | 新增 `testsResolveThePlaceholderAudioEngineRatherThanTheRealOne` |

**没有改任何测试的写法，没有改 `LiveAudioEngine`，没有改 DI 的注册形状。**

## 4. 效果（实测，非推断）

| 指标 | 改动前 | 改动后 |
|---|---|---|
| 全量测试里真 `LiveAudioEngine` 构造次数 | **39** | **0** |
| `swift test` | 587 tests / 28 suites | **588 tests / 28 suites 全通过** |

## 5. 影响面

- **生产行为：零变化。** 生产 app 不加载 XCTest，`TestProcess.isRunning` 为 `false`，三处都走原来的真实现分支。
- **`FW_MOCK_MIC`：不受影响。** 替身分支在 `audioEngine` 里排在守卫**之前**（`MockAudioEngine.Script.fromEnvironment()`），先判先返回。真机验证照旧。
- **测试行为：三处按原本声明的意图生效。** `audioEngine` → `PlaceholderAudioEngine`；`dailyReadAudioPlayer` → `StubDailyReadAudioPlayer`；iOS 上 `backgroundTaskPort` → `NoOpBackgroundTaskPort`。
- **高风险区**：本次**不碰** High-Risk Path #1（音频引擎本身）—— 改的是 DI 里「给谁」的选择，引擎一行未动。
- **回滚**：`git revert` 该提交即可。

## 6. 先红：改动前的失败输出（原文）


## 7. 本次**没有**做，但建议单独跟进的两件事

### 7.1 `LiveAudioEngine.deinit` 无条件碰输入节点

```swift
deinit {
    engine.inputNode.removeTap(onBus: 0)   // ← 没有 hasInstalledTap 判断
    engine.stop()
    continuation.finish()
}
```

`stopCapture()` 走的是 `PlaybackTeardown.steps(tapInstalled: hasInstalledTap)`，**有**条件；`deinit` 没有。同一个决定（「要不要去动输入节点」）两处判据不一致，而 `deinit` 那种会在从未采集过的实例上碰硬件。

本次没改，理由有两条：一是它属音频引擎本身（High-Risk Path #1），而本次的目标是「测试别拿到真引擎」——§4 显示 39→0 之后这条路径在测试里已经不再发生；二是 `deinit` 是 `nonisolated`，读 actor 状态需要确认 Swift 6 的规则，值得单独一轮做。**建议单独立项**，判据取「只移除自己装过的 tap」，与 `stopCapture()` 对齐。

### 7.2 用死环境变量判「是不是在测试里」是这个仓库的一个模式

`XCTestConfigurationFilePath` 在本仓三处出现、三处全死。同类的还有 `07_` §2 的 `AudioPlaybackGate`（声明的入口无调用点）与 `13_` 的 `WSControlFrameCodingError.missingField`（声明的 case 无 throw）。

**可复用的检查**：看到「按环境/平台/配置分流」的判据，先问「这个条件在本仓的实际运行方式下**取过真值吗**」——写一行探针打印它，比读代码可靠。本次三处守卫读起来都完全合理，只有打印出来才知道是 `nil`。
