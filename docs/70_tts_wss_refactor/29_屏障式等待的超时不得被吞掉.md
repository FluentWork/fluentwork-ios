# 29 — 实现说明：屏障式等待的超时不得被吞掉

> 对应条目：`70_/24_` §3.1 的更正（那道「兼作屏障」的等待）。
> 现象：`captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys` 约 2/3 概率红，失败信息指向「埋点不见了——它是真机验证要读的行之一」。
> 改动：`SpeakingRoomSessionWiringTests.swift`（屏障改用 `try`；`waitUntil` 加 `label`；`TimeoutError` 携带 label 与预算）。
> 测试数：`591 → 591`（不新增断言）。
> **本条不修那个 flaky 本身。** flaky 的根因是 `70_/28_`（测试在打开真机输入设备），已由它关掉。本条修的是**超时被吞掉**：它把一个测试自身的失败伪装成对生产代码的指控。

## 1. 守的是什么契约

**等待超时必须在超时的那一点让测试失败，而不是被 `try?` 吞掉之后在别处失败。**

## 2. 根因：屏障与预算不是一回事

`waitUntil` 轮询等待，超时抛 `TimeoutError`。调用方有两种写法，区别只在**超时之后会发生什么**：

| 写法 | 超时之后 | 诊断质量 |
|---|---|---|
| `try? await waitUntil { C }` 紧跟 `#expect(C)` | 超时被吞，但紧接着的 `#expect` 报「C 不成立」 | **准确**——报的是事实 |
| `try? await waitUntil { C }` 后面没有 `#expect(C)` | 超时被吞，测试继续往下跑 | **错误**——失败在别处出现，指向另一个东西 |

本条改的是第二类，而它的最坏实例就是 `24_` 那道屏障。它的后继**不是**同条件的断言，而是对 **11 条别的埋点**的 `#require`：

```swift
try? await waitUntil(timeoutNanoseconds: 2_000_000_000) {
    tracker.events.contains { $0.name == "timing_audio_engine_failed" }
}

for (name, keys) in expected {
    let hit = try #require(
        tracker.events.first { $0.name == name },
        "埋点 \(name) 不见了——它是真机验证要读的行之一（`70_/08_` §3 尚未做）"
    )
    for key in keys { … }
}
```

超时被吞 → 断言循环照跑 → 循环里第一条没到的埋点报出「**埋点 X 不见了——它是真机验证要读的行之一**」。**这句话是在指控生产代码停止发埋点了**，而真实原因是测试自己的等待没等到。

这就是那个 flaky 看起来像「生产缺陷」的原因，也是它值得单独记的原因：**一个测试脚手架的问题，被写成了对生产代码的指控。**

**这一条是实测的，不是推断。** 我制造了一次「这条埋点没到」（删掉最后一条 `emit`），把两种写法跑出来对照——差别不在「红不红」，在**红在哪一行、指控谁**。逐字输出见 §8.1。

## 3. 「预算式用法」不是本仓的通行做法

我一开始把这件事写成了「`try?` 是预算式用法，和 `try` 各有各的正当性」。**那是我在给现状找理由，不是从证据来的。** 数一遍就发现不成立：

| 文件 | `try?` | `try` |
|---|---|---|
| `SpeakingRoomSessionWiringTests.swift` | **81** | 1（本条） |
| `CorpusFeatureTests.swift` | 0 | 7 |
| `DailyReadAudioPlayerTests.swift` | 0 | 6 |
| `DailyReadMiddlewareTests.swift` | 0 | 6 |
| `ForceCloseMiddlewareTests.swift` | 0 | 2 |
| `ReviewFeatureTests.swift` | 0 | 4 |
| `SessionHistoryMiddlewareTests.swift` | 0 | 10 |
| `SpeechSessionMiddlewareTests.swift` | 0 | 32 |

**全仓只有这一个文件用 `try?`。** 另外 7 个文件的 **67 处一律 `try`**。所以「预算式用法」不是本仓的做法，是这一个文件的孤例。

### 3.1 而且这 81 处也不是「每处都紧跟同条件断言」

我按「闭包里的条件是否在随后 12 行内被重新断言」逐处判定（跳过条件里含内层闭包的 4 处，那些判定不可靠）：

| | 处数 |
|---|---|
| 随后有同条件断言 | 25 |
| **随后没有** | **52** |

抽查了其中 4 处（`:432`、`:491`、`:689`、`:747`），逐处读原文，**4 处都确实没有同条件断言**。例如 `:689`：

```swift
try? await waitUntil(timeoutNanoseconds: 1_000_000_000) {
    await speechClient.snapshotStartCalls() == 1     // ← 这个条件之后再没被断言过
}
```

所以「预算式用法」这个说法本身也站不住：那 52 处不是「预算 + 报告事实」，是**等一个条件、然后把超时丢掉**。

**这条数字要连带方法一起读**：它是按「随后 12 行」这个窗口算的，窗口外的重新断言会被算成「没有」。抽查的 4 处都支持它，但它不是逐处人工确认过的 52。

## 4. 改法

```swift
try await waitUntil(
    timeoutNanoseconds: 15_000_000_000,
    label: "屏障：等泵处理完前面 11 个事件（`timing_audio_engine_failed` 是最后一条）"
) {
    tracker.events.contains { $0.name == "timing_audio_engine_failed" }
}
```

`waitUntil` 加 `label: String = "未命名等待"`；`TimeoutError` 变成 `Error, CustomStringConvertible`，携带 label 与预算毫秒：

```swift
private struct TimeoutError: Error, CustomStringConvertible {
    let label: String
    let milliseconds: Int

    var description: String { "\(label) —— 超时（预算 \(milliseconds)ms）" }
}
```

现在超时会就地抛出一条自述的失败：`屏障：等泵处理完前面 11 个事件（…）—— 超时（预算 15000ms）`。

### 4.1 为什么不选「保留 `try?`，再补一条同条件 `#expect`」

那是「与本文件其余 80 处保持一致」的改法，也说得通。不选它的两条理由：

- **语义不同。** 预算是「系统应当在合理时间内到达状态 X，到不了我报状态」；屏障是「在我断言之前，泵必须已经把队列排空」。屏障超时说明**测试脚手架自己没跑完**，这时应当**就地中止**——后继那些断言的诊断信息是关于**生产埋点**的，在脚手架没跑完的情况下没有意义，继续跑只会产出一条错误的指控（§2）。
- **`try` 才是全仓的主流**（§3：另外 7 个文件 **67 : 0**）。选 `try` 是回到主流，不是偏离。

### 4.2 为什么预算是 15s

实测（本条落地后）：这个测试**整条**——两次 1s 预算的前置等待 + 12 次 `emit` + 屏障——耗时 **0.021 s**。屏障在一个轮询周期（10ms）内就满足了。所以 15s 是**纯安全网**，不是性能门限。

定这个数的依据：本仓观测到的最坏等待是 **3.4s**（`70_/28_` 记录，而且那还是硬件停顿造成的，不是屏障本身需要的），15s ≈ 4.4×。**代价不对称**——预算偏大只在真失败时多花几秒；预算偏小会造成一次假红，而假红要人来查。

### 4.3 `label` 的默认值对那 81 处是死代码

81 处用 `try?`，抛出的 `TimeoutError` 立刻被吞，label 永远显示不出来。只有这一处 `try` 会把它打出来。所以 `"未命名等待"` 这个默认值实际是留给「将来有人把某处改成 `try`」的。**本轮不改那 81 处**，理由见 §6 第 1 条。

## 5. 影响面

- **生产代码**：零改动。
- **测试**：一处 `try?` → `try`；一处加 `label`；`TimeoutError` 加两个字段。其余 81 处因默认参数不受影响。
- **回滚**：`git revert` 该提交。

## 6. 未覆盖 / 未决

1. **52 处「等一个条件然后丢掉超时」未处置。** 这是比本条大一个量级的改动：改成 `try` 会改变 52 个失败现场的中止点，可能把目前被吞掉的超时暴露出来（那也可能正是它们现在看起来稳的原因之一）。**建议单独立项，不要在追一个 flaky 的过程中顺手做。**
2. **`waitUntil` 在本仓有 8 份私有副本**（8 个文件各一份，`SpeakingRoomSessionWiringTests.swift:1432` 是其中之一）。`label` 只加在这一份上，其余 7 份没有。这属于 S1-2 / S1-3（测试助手与超时理由的合并）的范畴。
3. **15s 这个数没有东西会在它变得不合理时报警。** 它是我按 §4.2 的理由定的，没有自动校验。
4. **`24_` §3.1 的原文保留**，只在其后追加更正块——那句「也就少了一处 flaky 面」留着，因为它是这条判断被推翻的现场。

## 7. 被本条推翻的现场

### 7.1 `24_` §3.1 那句「也就少了一处 flaky 面」

原文保留，只在其后追加更正块。见 §6 第 4 条。

### 7.2 `2c365bb` 的提交信息

`2c365bb`（S1-10，`70_/27_`）的信息里写着：

> 根因是 82 处 `try? await waitUntil(…)` 吞掉 TimeoutError，于是测试侧的 1 秒超时伪装成一条对生产代码的指控。已单列一票修（S1-2 / S1-3）

**「根因」这个词用错了，而且同一段里还有一处判断也没跟上**：

- **那个 flaky 的根因不是 `try?`，是 `70_/28_`**（测试在打开真机输入设备）。`try?` 决定的是「超时之后失败信息长什么样」，不是「会不会超时」。把这两件事分开，是 `70_/28_` 落地、`8.1–8.7s（抖）→ 6.17s（±50ms）` 出来之后才看得出来的。
- **「82 处」是个总数**（81 处 `try?` + 1 处 `try`），而真正有问题的写法是其中那 **52 处**「等一个条件然后丢掉超时」（§3.1）。总数不是判据。
- **「已单列一票修（S1-2 / S1-3）」也不准**：S1-2 / S1-3 是「测试助手与超时理由的合并」，与本条不是同一件事。本条是**新立的一票**（`70_/29_`），S1-2 / S1-3 仍然开着。

**不改 `2c365bb` 的信息**——提交信息是当时的判断，改了就把「哪一步是什么时候想明白的」抹掉了。这条记录的作用是：**下一个人读 `2c365bb` 时，知道那句话后来被推翻了。**

| 构建（macOS） | `swift build --disable-sandbox` | `Build complete!` |

| Debug 构建（iOS） | `xcodebuild -project FluentWorkHost.xcodeproj -scheme FluentWorkHost -configuration Debug -destination 'generic/platform=iOS Simulator' build` | `** BUILD SUCCEEDED **` |

### 8.1 本条没有「先红」，改用变异验证（两次，A/B 对照）

**为什么没有先红**：这个 flaky 的失败态只在**超时**时出现，而超时的根因是 `70_/28_`（测试在打开真机输入设备），已经修掉了。所以改动后的树里**没法自然地复现**它——这一点我不打算含糊过去：**那段历史红输出我没有留存，也不在这里编造。**

**改成做变异验证**：制造一次「这条埋点没到」（把最后一条 `emit(.failed(…))` 删掉），让屏障的条件**永远不为真**，然后把两种写法各跑一遍。

**变异 A —— `try?` + 2s（改动前的写法）**

```
✘ Test captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys() recorded an issue at SpeakingRoomSessionWiringTests.swift:661:23: Expectation failed: tracker.events.first { $0.name == name }
↳ 埋点 timing_audio_engine_failed 不见了——它是真机验证要读的行之一（`70_/08_` §3 尚未做）
✘ Test captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys() failed after 2.017 seconds with 1 issue.
```

**变异 B —— `try` + 2s + label（本条的写法）**

```
✘ Test captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys() recorded an issue at SpeakingRoomSessionWiringTests.swift:605:2: Caught error: 屏障：等泵处理完前面 11 个事件（`timing_audio_engine_failed` 是最后一条） —— 超时（预算 2000ms）
✘ Test captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys() failed after 2.019 seconds with 1 issue.
```

**两行的差别就是本条的全部内容**：

| | A（`try?`） | B（`try`） |
|---|---|---|
| 红在哪 | **`:661`** —— `#require` 循环**里面** | **`:605`** —— **屏障本身** |
| 说的是什么 | 「埋点 `timing_audio_engine_failed` **不见了**——它是真机验证要读的行之一」 | 「屏障：等泵处理完前面 11 个事件 —— **超时**（预算 2000ms）」 |
| 指控谁 | **生产代码**（它不再发埋点了） | **测试脚手架**（它没等到） |
| 代价 | 2.017s | 2.019s |

两者都红、耗时一样。**唯一的差别是失败落在哪一行**——而这就是「把测试自己的超时写成对生产代码的指控」的全部含义。

**注意变异 A 并不是假绿**：因为屏障的条件恰好也是那 11 条埋点之一，所以超时之后 `#require` 仍会咬住它。这是**运气，不是设计**——如果哪天有人把屏障的条件换成一个**不在这张表里**的东西，`try?` 就会把超时彻底吞掉，测试**变绿**。这是 `try?` 在屏障上比在预算上更危险的原因。

### 8.2 顺带测出的一件事：这道屏障现在不可能超时

变异过程中我先把预算压到 **1ms**（保留真实条件），期望它超时——**它通过了**。

原因：`waitUntil` 是「先检查条件、再睡」的循环，而这道屏障的条件在**第一次检查时就已经为真**——泵在测试走到屏障之前就把 12 条事件都交付完了。所以：

- **2s 预算从来没有不够过**（这也印证了 `70_/28_` §8.1 的判断：那个 flaky 的根因是硬件停顿，不是预算）。
- **15s 是纯安全网**，与 §4.2 的说法一致。

**这条同时是本条的一个限制**：因为屏障在正常路径上不可能超时，**本条的改动在正常路径上也观察不到任何差别**——它的全部价值都在失败路径上，而那只能靠变异验证来展示。
