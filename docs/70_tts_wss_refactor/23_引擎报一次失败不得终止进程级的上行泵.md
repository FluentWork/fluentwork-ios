# 23 — 实现说明：引擎报一次失败，不得终止进程级的上行泵

> 对应缺陷：`10_事实基线与缺陷清单.md` **D14**（🟠 新立，本次修）。
> 改动：`SpeechSessionMiddleware.swift` 的 `audioEventPump` 在 `.failed` 分支上删掉 `return nil`，并补上 `speechCaptureGate.abort()`。
> 测试：`anEngineFailureDoesNotRetireTheUplinkPump`（`SpeakingRoomSessionWiringTests.swift:420`）——**本条有「先红」，红输出见 §6.1**。
> 关系：本条是**在查 D9 的过程中撞出来的**。D9 的推荐改法经查不成立（§10），而它旁边这条是真缺陷。

## 1. 这条改动守的是什么契约

**泵不是会话资源。** 两个泵读的是两条**进程级**的流，所以任何**会话级**的失败都不得终止它们。

这条契约在本仓被写死了**两处**，而且是改动前就有的：

**（1）`endSession` 的 handler 明写不取消它**（`SpeechSessionMiddleware.swift:1328-1329`）：

```swift
// No `.cancel(id: audioEngineEvents)`: that reader belongs to the
// engine, not to this session. See `audioEventPump`.
```

**（2）`stopCapture()` 里 `playbackRetired` 的存在理由之一就是保护它**（`LiveAudioEngine.swift:740-745`）：

```swift
// Retire before anything that yields or mutates the graph. Leftover
// TTS frames from a socket that has not closed yet still call
// `play(pcm:)`; once this flag is set they drop instead of
// restarting the player (and instead of `.failed`, which would kill
// the process-lifetime audio pump).
playbackRetired = true
```

引擎侧那句注释**直接点名了本条的机制**：`.failed` 会杀死进程级的上行泵。引擎因此加了一道工作区（先退休再产出）。**而中间件侧仍然是坏的**——`audioEventPump` 在 `.failed` 上 `return nil`，正好做了那件被两边注释禁止的事。

## 2. 为什么这是缺陷，不是风格问题

### 2.1 两条流和两个泵都是进程级的，可枚举

| 事实 | 证据 |
|---|---|
| 引擎的事件流进程级 | `LiveAudioEngine.swift:432-437` 建一条 stream；`continuation.finish()` **只在 `:447` 的 `deinit` 里**，`stopCapture()` 不动它 |
| 两个泵每进程只起一次 | `SpeechSessionMiddleware.swift:109` `eventPumpsStarted.take()`；`OnceFlag.take()`（`:36-46`）**只返回一次 `true`** |
| 泵不随会话取消 | `:1324-1329` 的注释，两处都明写不 cancel |

所以泵的寿命 = 进程的寿命。**终止它，就是终止到进程结束为止。**

### 2.2 `.failed` 的触发条件是日常情形，而引擎侧的工作区盖不住

引擎从 **8 处**产出 `.failed`（`LiveAudioEngine.swift`）。`playbackRetired` 只能盖住**在 `stopCapture()` 之后**到达的播放帧，所以下面这三处它盖不住：

| 位置 | 消息 | 触发 |
|---|---|---|
| `:723` | `could not reinstall the capture tap after a route change` | **路由变化**（拔插耳机）——与播放无关，`playbackRetired` 完全不涉及 |
| `:834` | `scheduling dropped: PCM length … not multiple of 2` | 一个长度非偶数的 TTS 帧 |
| `:1044` | `音频被系统中断，本轮练习已停止` | **系统中断**（来电等） |

而 `:881-883` 的注释进一步说明这类路径在正常操作里就会被走到：

> That is reachable whenever an audio frame outlives the session playing it: `stopCapture()` runs on `endSession`, the socket still holds frames in flight, and **the next one to arrive used to take the process down.**

即：**这不是「引擎报废」的终局宣告，而是日常可恢复情形**。用一次日常故障换掉进程级的上行读取者，代价完全不对称。

### 2.3 后果：下一次会话完全没有上行，而错误信息指向网络

泵一死，`audioEventPump` 里**所有** case 都不再执行。下一次会话因此：

| 应该发生的 | 实际 |
|---|---|
| `.speechStarted` → `beginSpeech()` + `user.speech.start` | 不发生 |
| `.pcmChunk` → `sendAudioPCM` | 一帧都不转发 |
| `.captureFirstBuffer` → `.captureLive` | 不发生 |

而 `.connecting` 等的正是最后那一半（`SpeechSessionMachine.swift:43-47`：socket 与 capture 两半都要），于是房间卡在「连接中」，10 秒后死在 `connectWait` 看门狗上：

```swift
:1519  return .speakingRoom(.session(.failed("连接超时，请重试")))
```

**用户看到的是「连接超时，请重试」——一个指向网络的错误信息，而真实原因是麦克风上行在本次进程里已经没有了。** 这也正是 `:121-124` 那段注释当初把两个泵改成进程级时要消灭的失败形态：「the engine's leaves 「开始说话」 doing nothing」——被 `return nil` 重新引了回来，而且是**永久**的。

## 3. 改法

| 位置 | 改动 |
|---|---|
| `:660` `case let .failed(message):` | 删掉 `return nil`；先 `speechCaptureGate.abort()`，再照旧 `timings.mark` + dispatch |

改动后该分支：

```swift
case let .failed(message):
    timings.mark(event: "audio_engine_failed", properties: ["message": message])
    speechCaptureGate.abort()
    await dispatchBox.dispatch(.speakingRoom(.session(.failed(message))))
```

### 3.1 为什么同时要 `abort()`（不是可选的修饰）

只删 `return nil` 会留下第二个问题：**会话已经失败，而闸门还开着**。`SpeechCaptureGate` 的关闭只有两个入口——`endSpeech()`（`.speechEnded`）与 `abort()`（录音超时）——**`.failed` 不在其中**。所以失败之后闸门保持打开，循环继续读的话：

- `.pcmChunk` 会**继续转发**（`takeForwardDecision()` 为真）→ 往一个 `endSession` 正在关闭的 socket 里写 → 每帧抛一次；
- 而 `catch` 里那个 `return nil` **还在**（§4），于是泵还是死——**修一半等于没修**。

`abort()` 一次解决两件事：闸门关上，后续 `.pcmChunk` 走 `continue`（不发、不抛），`.speechEnded` 被 `guard speechCaptureGate.isOpen` 吞掉（与录音中止路径同一语义，`:322-324` 的注释写明了这个用法）。**下一会话的 `.speechStarted` 会重新 `beginSpeech()`，闸门是可重开的。**

## 4. 为什么不是「把 4 处 `return nil` 一起去掉」

泵里改动前有 **4 处** `return nil`（不含 `Task.isCancelled` 那处）：`.failed` 一处 + 三个 `catch` 各一处。**它们的触发条件不同，不能一起改**：

| 处 | 触发 | 去掉安全吗 |
|---|---|---|
| `.failed` | 引擎的日常故障（§2.2） | **安全**——闸门已由 `abort()` 关上，后续 chunk 不发送 |
| `.speechStarted` 的 `catch` | `sendSpeechBoundary` 抛（socket 死） | 需另议 |
| `.speechEnded` 的 `catch` | 同上 | 需另议 |
| `.pcmChunk` 的 `catch` | `sendAudioPCM` 抛 | **危险**：这是**每帧**路径。socket 死 + 闸门开 = 48 kHz 下每秒约 86 次 `.failed` 派发 |

**共同形状相同**（会话级失败终止进程级泵），但 `.pcmChunk` 那处需要先有「每会话只报一次」的抑制，否则会把一次断连放大成一次派发风暴。那是另一个设计决定，**不在本条范围**（§7）。

## 5. 影响面

- **状态机**：无影响（未改 `SpeechSessionMachine`）。
- **协议（线上）**：无影响。上行 PCM 的放行判据仍是 `speechCaptureGate.takeForwardDecision()`。
- **音频**：**这正是本条的意义**——引擎侧的播放路径不变；改的是**中间件在引擎报错之后还活着**。
- **`speechCaptureGate` 生命周期**：新增一个关闭点（`.failed`）。语义与 `abort()` 既有的两个调用点一致（`:1273` 录音中止、`:1624` 超时）。
- **行为变化**：**仅在被改动前就已损坏的那条路径上**。改动前 `.failed` 之后泵已死，所以「失败后发生什么」在改动前是**空集**；改动后是「继续读、闸门关闭、不转发」。
- **回滚**：`git revert` 该提交即可。

## 7. 顺带记录：三条 `catch` 的 `return nil`（同形状，不在本条范围）

§4 已说明为什么不能一起改。它们的**共同形状与本条完全相同**：会话级的发送失败终止进程级的泵。建议单独立项，修法与 `21_` 同族——**先定「每会话报一次」的语义**（`21_` 是 `(轮次, 原因)` 去重），再动 `return nil`。

不夹带的原因：`.pcmChunk` 那处是**每帧**路径，没有抑制就会把一次断连放大成每秒约 86 次派发。那需要先定语义，属于设计决定。

## 10. D9 的更正：它的推荐改法不成立

本条是**在查 D9 时撞出来的**。查证结论如下，已同步改 `10_` 的 D9 条目与 `80_/05_` S1-4。

D9 的推荐改法是「抽成路由表，复用 `20_` 的手法」。**这条改法在本仓不成立**，四条证据：

1. **`AudioEngineEvent` 没有 discriminator。** 它是纯 Swift enum（14 个 case，只有关联值），没有任何 `wireType` 式的字符串键。**建不出字典表。**
2. **建了反而更不安全。** 下行 `TransportEventRouter.controlHandlers` 是 `[WSControlFrameType: ControlFrameHandler]`，键是字符串原始值——**漏一个键是运行时静默落到 `fallbackHandler`**，这正是 `20_` 要补的那类缺口。而上行 switch **没有 `default:`**（已核），所以今天「新增一个 `AudioEngineEvent` case」是**编译错误**。换成字典 = **把编译期保证换成运行时缺口**。
3. **控制流表达不了。** 上行 switch 用 `continue`（2 处：`.speechEnded` / `.pcmChunk` 的 guard）与 `return nil`（4 处）——**这些是跳出 switch、进入外层循环的转移**，闭包表表达不了。而 `TransportEventRouter.route` 刻意返回 `Void`，理由是「路由不产生决定」——**那个理由对上行是假的**：上行存在一个真实的二值决定（继续读 / 终止）。
4. **所以 D9 真正的问题不是「没路由」，是「文件 1713 行」。** 而切缝的选择是一个设计决定（6 个纯 `timings.mark` 的采集诊断？3 条会抛的上行路径？`makeTransportEventRouter` 那 341 行？），不该按「对称性」选。

**D9 的一半确实是对的**，而且顺手撞出了另一件事：那 8 个采集诊断的 mark 名**没有任何测试钉住**（`grep` 全部为空），而它们是设备验证唯一计划中的证据来源（`08_` §3 的真机验证尚未做）。**一个拼写错误就能静默移掉它。** 已记入 `80_/05_`，待与切缝选择一并决定。
