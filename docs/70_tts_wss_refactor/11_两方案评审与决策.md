## 0. 一句话结论

> **两方案都不作为 TTS/WSS 的实施依据。main 的方向是对的，缺的是收尾。**
>
> 两份文档都把「重写这条链路」当成前提，但它们的协议层**与线上逐字对不上**：
> 甲有两套互不兼容的 `MessageType`（文档内部就没有可实施的单一版本），
> 乙的帧名**一个都不存在**、且音频帧**不带 `turn_id`**——采纳乙等于把刚关掉的 P0-11（打断串音）重新打开。
> 而 main 的缺陷是可定位、可小步修的，不需要重写：核心问题是「归属/丢弃」这一件事被实现了两遍，
> 多出来的那一遍（传输层序号水印）既不做它被声称做的工作，又是唯一能无声吞掉整轮音频的机制。

## 3. 架构级错配：把「端到端」当成「多阶段流水线」

crosscheck 的高频模式，在乙里出现了**五到七次**，且每次的段数与数字都不同：

| 出处 | 段数 | 总计 | 阶段 |
|---|---|---|---|
| `README:254-264` | 6 | 1500ms | WebSocket 连接 200 + 音频录制启动 100 + ASR 首词 300 + LLM 首 token 500 + TTS 首块 300 + 播放启动 100 |
| `README:186` | 5 | 1400ms | 同上，去掉「音频录制启动」 |
| `01:641-649` | 6 | 1500ms | 同 `README:254-264` |
| `15:38-43` | 5 | 无总计 | WebSocket ≤200 + ASR ≤300 + LLM ≤500 + TTS ≤300 + 播放 ≤100 |
| `04:379-406` | 7 | P50 1400 / P90 1500 | 客户端处理 50 + 网络 100 + ASR 300 + LLM 500 + TTS 300 + 网络下载 100 + 播放 50 |
| `04:767-777` | 6 | 1.5s | WebSocket 连接 **0ms**（预连接）+ 音频上传 200 + ASR 300 + LLM 500 + TTS 300 + 网络 200 |
| `13:32-47` | 6 | 1000ms + 500ms 缓冲 | 静音检测 100 + 网络 50 + ASR 300 + LLM+TTS 400 + 网络 50 + 解码播放 100 |

**为什么这是架构级错配，而不是数字不准**：

1. **`WebSocket 连接 200ms` 被算进了「每轮首响」的分母。** 连接是**每会话一次**，不是每轮一次。
   口径是 `用户松开按钮 → 首个音频块播放`（`04:604`）——第一轮之后，这个阶段恒为 0。
   于是 `README:254-264` 的 1500ms「预算」里有 200ms 是**不存在的阶段**。
   （`04:767-777` 自己把它改成 `0ms | 预连接`，与 `README` 直接冲突——文档内部已经发现过这个错，但没回改。）
2. **`音频录制启动 100ms` 不在回复路径上。** 它发生在用户**开始**说话时，而不是「松开按钮 → 听到回复」之间。
   `README:186` 把它删了（1400ms），`README:254-264` 又加回来（1500ms）——同一份 README 两套。
3. **分母里的 ASR / LLM / TTS 三段不是串行阶段。** `13:32-47` 把 ASR 300 与「LLM+TTS 400」串起来，
   而 `04:379-406` 把 LLM 500 与 TTS 300 串起来。真实链路是 Volcengine duplex 单次前向的流式回传
   （`01_现状架构审计.md` §1 的时序图：`V->>G: ASR + LLM + TTS (duplex)`）——**这三个计时点在真实系统里不可观测**。
   这就是「分母不存在」：不是数字不准，是那三个观测点根本没有对应的时刻。
4. **所有「优化收益」数字都是从这套错误分解推出来的**：
   `WebSocket 预连接 -200ms`（`13:672`）、`音频会话预热 -50ms`（`13:673`）、`音频缓冲区最小化 -30ms`（`13:674`）、
   `流式播放首块音频 -200ms`（`13:675`）、`服务端模型预热 -500ms`（`13:676`）——相加 980ms，
   而其中至少 200ms（连接）与 100ms（录制启动）不属于每轮路径，另外 500ms（服务端预热）是后端工作。
   在这些数字上做排期（`15:352`「W2 末压测不达标 → 重估整体排期」）等于在一个错的分母上定验收线。

**甲也有同一类问题，但轻**：`03:742-750` 给了一张 7 段表（采集缓冲 20-64 + 重采样 1-5 + Opus 编码 1-3 +
网络 10-100 + Opus 解码 1-3 + 播放队列 20-60，合计 53-235ms），那是**单帧的流水线延迟**，
与 `01:78-84` 的「首帧延迟 <300ms / 端到端 <1.5s」是不同量纲的两件事。文档没有区分，
于是 `03:958`「端到端延迟 <200ms（采集到播放）」与 `01:81`「端到端延迟 <1.5s（松开 → 完整回复开始）」
成了同一个指标名的两个定义。

## 6. 决策

### 6.1 判定

| 方案 | 判定 | 理由 |
|---|---|---|
| **甲** `docs/200_tts_wss_architecture_design/` | **不采用（作为实施依据）** | ① 协议层逐条冲突，且文档内部有两套不可兼容的 `MessageType`——**没有可实施的单一版本**；② 音频承载从二进制退到 JSON+Base64，实测倒退；③ 27 组内部矛盾 + 4 个断裂引用 + 16 处代码桩；④ 模块布局等于另起一个 app。**可取走的只有一条**：`turn_id` 上音频帧（`04:395`）——见 6.2 |
| **乙** `docs/300_fluentwork_architecture/`（实时链路部分） | **不采用** | ① 12 个帧名无一存在，信封字段结构不同；② **音频帧不带 `turn_id`，采纳即重开 P0-11**；③ `12_actor_concurrency.md` 的「旧代码」基线（`AudioRecorder` + `NSLock`、`WebSocketManager` + KVO）**在仓内不存在**——论证建立在一个虚构的现状上；④ 32 处断裂引用 + 6 节整段重复 + 5–7 套互不相同的延迟预算；⑤ 延迟预算把「WebSocket 连接」「音频录制启动」算进每轮分母，所有优化收益数字建立在这个错的分母上 |
| **main** | **保留方向，补齐收尾** | 缺陷集中在「同一件事实现了两遍」与「顺序错了一处」，都是小步可修。见 6.2 |

### 6.2 该做什么

**第一件（唯一需要后端配合的）**：把 `turn_id` 放到二进制帧上——也就是 `03_重构建议与迁移路径.md` 的 **Stage 3**，
`README.md:35` 记为「S3 未走」的那一步。它是：

- **D7 的唯一正解**：让归属从「控制帧时序推断」变成「数据帧自描述」，即 `01_现状架构审计.md` §7 定下的根因修法；
- **D2 的根治**：帧自带轮次之后，序号水印的存在理由彻底消失；
- **甲唯一可取的一条**：甲 `04:395` 的 `ai.audio` 帧带 `turn_id` 正是这个形状——**但不需要甲的任何其他改动**。

**第二件（不需要后端，纯客户端，建议立刻做）**：D1 —— 把 `dispatch(.aiFirstAudioChunk)` 与两条计时
**移到 `onAudioFrame` 返回 `.played` 之后**。依据：
- 它是**实证**缺陷（本次 `swift test` 的日志直接打出「先记为第一块音频 → 紧接着判为丢弃」）；
- 同一函数里 `tts_first_audio` 已经是有闸门的（`count == 1`），**只是相位翻转与计时漏了**；
- 影响面是本链路最贵的那个指标（`first_response_ms`）与最贵的那个症状（「AI 在说话但没声音」）；
- 修法不引入新语义，符合 `AGENTS.md` 的「先写一条失败的测试」纪律——测试可以直接断言
  「无归属的帧不得把 phase 推进到 `.aiSpeaking`，也不得产生 `ai_first_chunk`」。

**第三件（收口）**：把「归属/丢弃」收敛成一处 owner。当前有四处各自决定同一件事：
传输层序号水印、协调器轮次注册表、`submitTranscript("__interrupt__")` 魔法字符串、状态机的 `.stopPlayback`/`.sendInterrupt`。
推荐顺序：先删传输层水印（D2c 的论证已备），再合并两个 interrupt 触发点（D3），最后给打断一个显式入口（D10）。

### 6.3 为什么不是「重写」

1. 两份文档都**没有一条协议能对上线**。重写的前提是有一份比现状更接近真实的规格——这个前提不成立。
2. 乙会**回退**已关闭的缺陷（P0-11）。重写最贵的代价不是工时，是把付过学费的东西退回去。
3. 甲的音频承载方式是**实测倒退**：现网 644B/帧二进制 → Base64 后 ≥860B 且每帧一次 JSON 解析。
   这条链路的失败模式历来是静音/串音，不是吞吐；在一个已经能出声的链路上引入解析开销，风险收益是负的。
4. main 的缺陷都是**可定位、可小步修、可单测钉住**的。D1 有仓内可复现日志；D2a 有测试已钉住其行为；
   D3/D4/D5 都是读码即得的顺序或字段问题。
