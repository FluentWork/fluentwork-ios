## 2. 排在 D15 之后的四条（按依赖排序）

顺序不是按重要性，是按**依赖**：

### 2.1 第 1 位：Stage 3（见 §3）

它排在最前，因为它是**唯一跨仓**的一条，而 `AGENTS.md` Local Rule #7 要求跨仓工作串行——
越晚启动，它与后端其它改动的冲突面越大。它也是唯一能真正关掉 **D7** 的动作。

### 2.2 第 2 位：D13 删除（279 行）

**决定：删除。放弃 B13 客户端 ASR。**

我本轮**独立复核过**零引用（没有采信 `22_` 的结论）：

```
$ grep -rn "ASRTranscriber" Shared/ Tests/ App/
（除三个文件自身的定义外，零命中）
```

四条理由：

1. **全域零引用**：无实例化点、无 DI 注册（`AppDependencies.swift` 无对应 factory）、无测试。
2. **唯一的具体实现永不兑现**：`VolcengineClientASRTranscriber.transcribe(pcm:)` 直接
   `throw ClientASRError.notAvailable`，注释写 `TODO(B14)`；而 **B14 最终走了服务端 ASR**。
   这个占位不是「待实现」，是**指向一条已经不存在的路线**。
3. **它的入口已被 D12 删掉**：`pcmBuffer` 是这条路的唯一上游（buffer 存在的唯一理由是喂它），
   已随 `22_` 删除。今天即使有人注册它，也没有 PCM 喂进来。
4. **不可复用**：若将来重做客户端 ASR，面对的会是 **Stage 3 之后**的协议，这 279 行要重写。

**为什么不与 Stage 3 一起做**：删 279 行 `public` API 与改线上帧格式是两件独立的事，
混在一个提交里，将来要回滚其中一件就得拆。**分开做，分开提交。**

### 2.3 第 3 位：D5 选项 2（放宽无分支消费的字段）

**决定：`ai.tts.start` 的 `voice_id` / `sample_rate` / `codec` 改 `decodeIfPresent`；
`turn_id` 保持必需。**

为什么是选项 2 而不是 1 或 3：

- **不是选项 1（保持严格）**：`13_` §7 的反对意见成立且未被反驳——漂移检测**已经由
  `PackageBaselineTests` 在构建期覆盖**，运行期拆连接不增加检测能力，只增加爆炸半径。
- **不是选项 3（整帧宽松）**：那会把契约违规降级成「丢一帧」，连信号都没了。
- **是选项 2**：三个字段**没有任何按值分支的消费者**（`13_` §5 逐条核过，它们只被读进埋点），
  而 `turn_id` **有**（归属）。这是唯一能消除「**拿最大爆炸半径执行最低价值约束**」这个倒挂、
  又不削弱唯一有消费者的字段的选项。

**注意这不是「一行改动」**：`WSControlFrame.aiTTSStart` 的关联值要从
`(turnID: String, voiceID: String, sampleRate: Int, codec: String)` 变成三个可选，
波及**编码器**（`WSControlFrame.swift:421`）与**埋点消费点**（`SpeechSessionMiddleware.swift:780-782`）。
所以它有自己的先红与自己的实现说明。

### 2.4 第 4 位：D9 切缝 = 「纯采集诊断」那一族

**决定：抽出 6 个只做 `timings.mark`、无 dispatch、无 IO 的 case。**

`23_` §10 列的三个候选，我本轮**逐个数过**（避免第四次计数错）：

| 候选 | 实际 | 能否安全抽 |
|---|---|---|
| 纯 `timings.mark` 的采集诊断 | **6 个**：`captureKick` / `captureInterruptionLifted` / `voiceProcessing` / `captureDropped` / `captureArmed` / `speechEndpointed` | ✅ 无控制流转移、无 IO |
| 3 条会抛的上行路径 | `speechStarted` / `speechEnded` / `pcmChunk` | ❌ 它们**就是**闸门与控制流的所在地 |
| `makeTransportEventRouter` 341 行 | 下行路由 | ⚠️ 收益大，但它是**下行**，与 D9 的原始关切（上行 switch 纳不进路由）无关 |

选第一条的三个理由：

1. **只有它不含控制流转移。** 那 6 个 case 既不 `continue` 也不 `return nil`，抽出去**不可能改变行为**——
   这正是 `23_` §10 第 3 条证据（闭包表表达不了转移）唯一能绕开的形状。
2. **S1-9 刚给这一族建了回归网。** `24_` 的断言钉的是这 6 个（连同另 5 个）埋点的**名字与属性键**，
   所以「抽出去之后埋点还在不在」有东西会红。
3. **`routeChanged` 不算**：它 mark 之后还有 `await audioEngine.reconfigureForRouteChange()`，
   有 IO，所以是 **6 不是 7**。

**为什么不做 `makeTransportEventRouter`**：它更大，但它是下行；`20_` 已为它建过集合相等断言。
把它卷进来，是拿一个**已有关切之外**的重构去换行数——`23_` §10 第 4 条说的正是这件事：
「切缝的选择是一个设计决定，不该按对称性选」。

## 3. 第 1 位：Stage 3 的契约草案

### 3.1 为什么现在才轮到它

`11_` §7 第 1 条给的两个选项是「(a) 排期」与「(b) 不排，先把客户端侧收干净（D1 + D2 + D3），
接受继续替网关的时序背书」。**(b) 的前置条件已经满足**：

| (b) 要求先收干净的 | 状态 |
|---|---|
| D1 首块音频判定顺序 | ✅ `0436c27` |
| D2 传输层序号水印 | ✅ `79e0ffc`（整道机制删除） |
| D3 一次打断两次 interrupt | ✅ `bfc8fc2` |

而且此后又关掉了 D4 / D5(诊断) / D6 / D10 / D11 / D12 / D14 / S1-9。
所以 **(b) 不再是 (a) 的替代方案，(a) 是唯一还能推进的事**。

### 3.2 现状（两侧逐字核对过，不是转述）

| 侧 | 位置 | 布局 |
|---|---|---|
| iOS | `WSAudioFrameCodec` | `[4 字节 UInt32 大端 sequence] + payload` |
| 后端 | `internal/voiceproto/frames.go:179-218` | `Encode()`：`out[:4] = seq`，`out[4:] = payload`；`DecodeAITTSAudio` 要求 `len >= 5` |

后端那句注释自己写明了这个耦合：

> `// Wire layout matches iOS WSAudioFrameCodec: 4-byte big-endian seq + payload.`

**两边都没有 `turn_id`。** 所以客户端只能**看控制帧什么时候到**来推断一帧音频属于哪一轮——
这就是 D7。而 D7 是 D2b（整轮静音）的根因面之一。

### 3.3 推荐形状

**给二进制帧加一个固定宽度的「轮次引用」，由网关在 `ai.tts.start` 里宣告。**

```
现在： [4B sequence][payload]
建议： [4B sequence][4B turn_ref][payload]
```

- `turn_ref` 是**网关按会话分配的单增 uint32**，不是 `turn_id` 字符串——
  固定 4 字节，头部保持定长，每帧不浪费。
- `ai.tts.start` 增加一个 `turn_ref` 字段，客户端据此建立 `turn_ref → turn_id` 的映射，
  再转成它自己的 `TTSPlaybackCoordinator` 轮次轴（**那部分已经是按 turn 轴的，不用改**）。
- `ai.tts.end` 同样带上 `turn_ref`，用来**关闭**映射项（否则映射会按会话无限增长）。

**关键收益**：归属从「控制帧时序推断」变成「数据帧自描述」。D7 关闭；
D2b 的整轮静音**在原理上不再可能**——一帧音频自己说得出它属于哪一轮，就不存在
「被推断成别轮」这条路径。

### 3.4 需要后端一起定的三个问题（我不单方面决定）

1. **`turn_ref` 的编号域**：每会话从 0 起，还是每连接？这决定客户端映射表的清空时机。
2. **`ai.tts.start` 的 `turn_ref` 是否必需**。若必需，它是**新的**必需字段——
   而 D5 的教训正是「必需字段的爆炸半径」。建议：**`turn_ref` 必需**（没有它帧就没法归属，
   与 `voice_id` 那类纯日志字段性质不同），但要接受这是对 `13_` 那套推理的**一次有意例外**。
3. **过渡期**。两端必须同时上；若不能，需要一个版本协商（`handshake` 里声明）。
   **注意**：`10_` §2 已记「`handshake` 是 iOS 侧的死面」（iOS 从不构造它），
   所以走协商就要先把 `handshake` 复活——这是**额外的**工作量，要算进去。

## 4. 两条「决定即落地」的

### 4.1 第 5 条：3 处 `catch` 的 `return nil`（D15）

**决定：修，并把语义定为「每句话报一次」。** 本轮已实施，见 [`26_`](./26_上行发送失败不得终止进程级的上行泵.md)。

`23_` §7 说「先定『每会话报一次』的语义」。**实施时发现不需要新语义**：
闸门本身就是抑制器——发送失败时 `abort()` 关闸，之后每个 `.pcmChunk` 都被
`takeForwardDecision()` 拒绝（且**计数**），于是不需要任何新的去重结构。
代价是语义从「每会话一次」变成「**每句话一次**」，而这**更准**：
每一次尝试都是一次独立的失败，合并掉反而会丢信息。

### 4.2 第 6 条：两份设计文档的处置

**决定：选项 (b)。**

- **不 merge** `docs/200_*` / `docs/300_*` 进 `main`。它们与真实协议的冲突清单**已经**落在
  本系列（`11_` §4 逐条列过），这就是 (b)。
- **不采用 (a)**（在两个分支的 README 顶部再加一段冲突清单）：那会造出**第二份副本**，
  而两份会漂移——本仓已经反复撞到「判据被复制」这一类（`19_` §6.3、`20_` 的名单）。
  一份清单，一个位置。
- 两个分支**原样保留**，作为历史产出物，不删。

## 5. 第 8 条：需要你动手的一件事（我执行不了）

远端 `main` 的分支保护要求 **PR + 3 项状态检查**，而 `AGENTS.md` Local Rule #8 写着
「**Develop on `main`**，`--ff-only`，**no PRs unless asked**」。两者只能改一个。

现在每次推送都成功，但带一条告警：

```
remote: Bypassed rule violations for refs/heads/main:
remote: - Changes must be made through a pull request.
remote: - 3 of 3 required status checks are expected.
```

**「bypassed」意味着有人有 bypass 权限，规则实际上没有拦住任何人。** 这比它看起来更值得处理：
一条**看起来有保护、实际没有**的规则，正是本系列反复命名的那个形状
（`16_`/`17_` 的「判据从不取真值」、`22_` 的「保护对象不存在」、`24_` 的「守卫可能不会咬」）。

**我的建议**：让远端与 `AGENTS.md` 一致——对 `main` 关掉 *Require a pull request before merging*。
理由：本仓的纪律是成文的、被遵守的，而这条远端规则**既没有被遵守、也没有拦住任何东西**，
它唯一的作用是让每次推送都打印一段谁也不会读的告警。若组织层面要求 PR，那就该改 `AGENTS.md`，
而不是维持一个双向都名不副实的状态。

**这条我做不了**：需要仓库管理员权限，且它是对流程的改动，不是代码。
