# 22 — 实现说明：删除跨会话残留的音频缓冲

> 对应缺陷：`10_事实基线与缺陷清单.md` **D12**（🟡【读码】→ 查证后实为**死代码**）。
> 改动：`SpeechSessionMiddleware.swift` 的 `audioEventPump` 删掉 `pcmBuffer` / `isCapturingSpeech` 两个跨会话局部量（9 行代码 + 注释），并改写 `:429-438` 的说明注释。
> **⚠️ 本条没有「先红」**——删掉的是**从未被读过的存储**，改动前后行为完全相同，不存在可失败的测试。按 `AGENTS.md` 的三条例外之第一条（新能力 / 无失败态），改为**钉住期望行为**。理由见 §6.1，这是本次最需要交代的一点。

## 1. 这条改动守的是什么契约

**泵不持有任何自己的每会话状态；「此刻是否在一次话里」只有一个答案，而那个答案在 `speechCaptureGate` 里。**

`SpeechCaptureGate`（`:282-405`）是这个问题的唯一 owner：

| 成员 | 行 | 作用 |
|---|---|---|
| `beginSpeech()` | `:303` | 打开窗口 |
| `endSpeech() -> TurnCounts` | `:315` | 关闭窗口并交回本轮计数 |
| `isOpen` | `:333` | 查询 |
| `takeForwardDecision() -> Bool` | `:345` | **放行判定**，并把拒绝计进 `droppedOutside` |

`audioEventPump` 里唯一决定「这块 PCM 上不上线」的是 `:548`：

```swift
guard speechCaptureGate.takeForwardDecision() else { continue }
```

**这一行没动。** 本次要删的是它旁边那套**看起来在回答同一个问题、实际不参与回答**的状态。

## 2. 为什么这是缺陷，不是风格问题

### 2.1 它不是「隐式不变量」，它是死代码

`80_架构分析/03_语音链路的所有权.md` §4.4 把这两个局部量记成一条**隐式不变量**：靠「`.speechStarted` 在 `beginSpeech()` **之前**清空 buffer」来保证上一会话的音频串不到这一会话，而这个保证**没有任何测试会红**。

按那条描述，结论应该是「加一条测试把它钉住」。查完发现**前提不成立——`pcmBuffer` 从来没有被读过。**

改动前它在生产代码里出现 **9 次**（`git show HEAD:Shared/.../SpeechSessionMiddleware.swift | grep -n`）：

| 行 | 语句 | 方向 |
|---|---|---|
| `:451` | `var pcmBuffer: [Data] = []` | 声明 |
| `:452` | `var isCapturingSpeech = false` | 声明 |
| `:461` | `pcmBuffer.removeAll()` | 写 |
| `:462` | `isCapturingSpeech = true` | 写 |
| `:490` | `isCapturingSpeech = false` | 写 |
| `:494` | `pcmBuffer.removeAll()` | 写 |
| `:544` | `pcmBuffer.removeAll()` | 写 |
| `:553` | `if isCapturingSpeech {` | **读**（唯一一次） |
| `:554` | `pcmBuffer.append(data)` | 写 |

`isCapturingSpeech` 唯一一次被读，是为了决定**要不要往 `pcmBuffer` 里写**；而 `pcmBuffer` 一次都没被读——没有 `.count`、没有 `joined()`、没有作为参数传进任何函数、没有出现在任何 `return` 里。

**整条数据流因此是一个闭环，而闭环外面没有观察者。** 删掉它，外部世界不变。

> 这一步是本次最关键的推理：`80_/03_` §4.4 与 D12 原文的**立论都建立在一个未经验证的前提上**（「buffer 是活的，只是安全靠时机」）。把 9 个出现位置逐个标出读写方向之后，前提塌了——**不是「不变量没被测试保护」，而是「没有被保护的东西」**。这与 `13_`（D5）推翻 D5 自身立论是同一类结果。

### 2.2 它为什么看起来像活的

因为它身上有**四条描述用途的注释**，而且写得很具体：

```swift
// B13: Buffer PCM chunks during speech for client ASR transcription
// Reset PCM buffer at the start of each turn
// Clear buffer after use
// B13: Buffer PCM during speech capture for client ASR
```

注释说的是 **B13（客户端 ASR）**，而生产走的是 **B14（服务端 ASR）**。同一文件 `:507-509` 就写着：

> B14 change: Server-side ASR (Volcengine Duplex relay) now provides the authoritative transcript via WSS `client.asr.transcription` frame. We no longer run local Apple Speech ASR here.

B14 切走之后，喂给 B13 的那条路**上游断了**：buffer 还在被写、被清，但**下游的消费者从来没接上**（下游那 279 行也是死的，见 §7）。

这是「**看起来有保护、实际没有**」的又一个实例，与 `16_`/`17_`（判据从不取真值）、`19_` §6.3（判据被复制进替身）同族。区别在于：那两条是**保护失效**，这条是**保护对象不存在**。前者要修判据，后者要删代码。

### 2.3 为什么它必须删，而不是「收进一个类型」

`80_/03_` §4.4 的建议是「把 `pcmBuffer` / `isCapturingSpeech` 收进一个 `SpeechCaptureBuffer` 类型，让 `beginSpeech()` 与 `pcm()` 成为同一个人维护的一对」。

**照这个建议做会制造一个新缺陷。** 把死存储包成一个有名字、有 API 的类型，等于给「泵持有每会话状态」这件事**发了一张通行证**：下一个读代码的人会看到一个 `SpeechCaptureBuffer`，合理地认为它是活的、需要维护的、需要论证生命周期的——而它其实什么都不做。**抽象一个空集合，只会让它更难被发现。**

同理，§4.4 的第二个建议（「加一条测试：两个会话之间不清空 → 必须红」）**写不出来**：见 §5。

- **状态机**：无影响。

- **音频**：无影响。

## 5. 为什么不是「加一条测试」而是「删」

`80_/03_` §4.4 的第二个建议是「加一条测试：两个会话之间不清空 → 必须红」。**这条测试写不出来**：

1. **没有可观察的后果。** 两个会话之间不清空，唯一的后果是一个没人读的数组里多了几个 `Data`。要让测试红，只能去断言那个数组的内容。
2. **而它是私有局部量，测试够不到。** 就算够得到，写出来的断言也是「断言一个死变量在某时刻是空的」——**等于把死代码重新编码进测试**。这与 `19_` §6.1 的第二个理由同形：一条测试若必须复述被删掉的机制才能存在，它就该跟着机制一起走。

## 6. 测试

### 6.1 为什么这一条没有「先红」（`AGENTS.md` 例外条款）

`AGENTS.md` 要求「每个修复都从一条会失败的测试开始」，并给了三条例外。**本条适用第一条：新能力（不存在失败态）——改为钉住期望行为。**

为什么不存在失败态，说清楚：

1. **改动前后行为完全相同。** §2.1 给了数据流证明：删掉的是闭环内的写，闭环外无观察者。唯一的变化是「少了一个永远为空的数组」——**没有任何外部可观测量改变**。
2. **改动前根本写不出这条测试。** 唯一能红的断言是「这个私有局部量在某时刻是空的」，而它既够不到、又不描述任何行为（同 §5）。

### 6.2 钉住的守卫（既有，本次未改一行）

本条**不新增测试**，因为守卫已经存在，而且它守的正是**活的那一半**：

`pcmOutsideAnOpenUtteranceNeverReachesTheClient`（`SpeakingRoomSessionWiringTests.swift:925`）——三段式：**开口前**的 chunk 必须丢、**开口内**的必须转发、**收口后**的必须再丢。它断言的是 `speechClient.snapshotAudioPayloads()`，即**线上真正收到了什么**，而不是某个内部变量。

它的文档注释（`:910-923`）已经把这条契约写死了：

> "No PCM leaves the device outside an open utterance" is what keeps the gateway from committing inter-turn audio into the *next* turn's transcript — a measured defect, not a hypothetical: an 83-character transcript came back from a 2.9s tap because the tap runs for the whole session while turns do not.

**这条测试在改动前后都通过，且未修改一行。** 它就是本次要钉住的期望行为：删掉死缓冲之后，「窗口外不外发」依然成立——因为放行判定从来不在被删的那套状态里。

> §5 的「写不出测试」与这里的「不需要写测试」是同一件事的两面：D12 的守卫必须落在 `takeForwardDecision()` 的**效果**上，而不是落在某个内部数组上。既有测试恰好已经在正确的位置。

## 7. 顺带记录：这条死路的另外 279 行（已立为新缺陷 D13，不在本条范围）

判据（`Shared/`、`Tests/`、`App/` 全域，除去这三个文件自身的定义）：

### 8.1 门禁里那次唯一的失败：既有 flaky，不是本改动

第一轮全量 `swift test` 报 `✘ Test run with 587 tests in 28 suites failed after 27.222 seconds with 25 issues`，失败集中在 `speechSessionMiddlewareConsumesAudioEngineEvents`（`SpeakingRoomSessionWiringTests.swift:849`）：`:906` 期望 `.processing`、实际 `.failed`。

**判定：不是本改动引入的。** 三条独立证据：

**(1) 因果上不可能。** 被删的 9 行是声明、`removeAll()`、`append`、`isCapturingSpeech = ...`——**没有一行会派发任何 action**。而 `.failed` 的全部 **13** 个派发点只有三类：

| 类别 | 行号 | 个数 |
|---|---|---|
| `catch { ... .failed(error.localizedDescription) }` | `:481`、`:538`、`:552`、`:1236`、`:1238`、`:1257`、`:1385` | 7 |
| 音频引擎错误透传 | `:662`（`case let .failed(message)`）、`:1217`（麦克风权限） | 2 |
| 看门狗定时器 | `:867`（`outcome == .timeout`）、`:1312`（turnTimeoutExpired）、`:1519`（connectWait）、`:1629`（totalCap） | 4 |

**三类全未改动。**

> 这里也顺手踩了一次本系列记过的坑：`grep -c "session(.failed"` 给出 **14**，但其中 `:991` 是**注释**，实际派发点是 **13**。与 `80_/README.md`「定稿前的自校」里 `OSAllocatedUnfairLock` 13→11（14 个文本命中里 3 个是注释）是**同一个错法**。凡是拿 `grep` 计数，都要再问一句「命中的是不是都算数」。

**(2) 症状与机理对得上。** 该测试断言的相位迁移（`.speechEnded → .processing`、`ai.tts.start → .aiSpeaking`、`ai.turn.end → .evaluation`）全部走 `transportEventPump` 那条路，与 `audioEventPump` 无关。而 `.failed` 的看门狗里，`:1519` 的 `connectWait` 默认 **10 秒**（`ProcessingTimeouts.swift:22`）。**失败那轮墙钟 27.2 秒 = 正常值的 3.4 倍**——在一个被饿到 3.4 倍的进程里，10 秒的 `connectWait` 完全够得着；它一响，相位就变 `.failed`，下游 11 条 `#expect` 连带失败。这正好解释「一条测试报 25 个 issue」。

**(3) 可复现性数据。** 同一棵工作树连跑 9 轮：

| 轮次 | 结果 | 墙钟 |
|---|---|---|
| 1 | ✘ 25 issues（`speechSessionMiddlewareConsumesAudioEngineEvents`） | **27.222s** |
| 2–9（含门禁当轮） | ✔ 587 tests / 28 suites | **7.494 – 8.064s**（门禁当轮 7.659s） |

**失败的唯一那轮恰好是慢 3.4 倍的那轮**；把失败测试单独跑，`0.070s` 通过。这与 `15_` §7 记的既有 flaky 同族——那一节明确写着「**每次失败的测试都不同**」，且**在未改动的 `bfc8fc2` 基线上同样复现**。共同形状是：全量并行 + 机器负载 → `waitUntil` 的固定预算不够。

> 本条比 `15_` §7 多出的一个数据点：那次症状是 `TimeoutError()`（测试直接抛），本条症状是**断言失败**。原因是该测试的 8 处 `waitUntil` 全部写成 `try? await waitUntil(...)`——**超时被吞掉**，于是「等不到」表现为「相位值不对」，看起来完全不像超时。同一个根因，两种症状。
>
> `15_` §7 已把这条列为「既有问题，不在本次范围，但值得单独立项」，判断是「**门禁可不可信**比某一条测试更值钱」。本次不改，维持该结论；`80_架构分析/04_测试架构.md` §3.1/§3.2 与 `80_架构分析/05_问题清单与建议.md` S1-2/S1-3 已把它升级为结构问题（11 个等待助手、5 类漂移、超时理由只有一份副本）。

## 10. 本次修正的文档

`80_架构分析/03_语音链路的所有权.md` §4.4 的**前提是错的**：它把 `pcmBuffer` 当作**活的**跨会话缓冲，据此论证「靠清空时机保证的安全是一条隐式不变量」，并建议收进 `SpeechCaptureBuffer`（§2.3 说明了为什么照做会更糟）。事实是它从未被读。§4.4 已改写为记录这次证伪，并保留「靠时机而非作用域」这个形状的一般性提醒——它对**真的**跨会话状态仍然成立。
