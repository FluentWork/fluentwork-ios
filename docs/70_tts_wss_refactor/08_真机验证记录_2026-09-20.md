# 08 — 真机验证记录（2026-09-20）

> Stage 2/3 接线之后的第一次真机验证。[`03_重构建议与迁移路径.md`](./03_重构建议与迁移路径.md) 把真机 smoke 定为这一步的落地判据，
> 本文件记录它实际验到了什么、没验到什么、以及过程中发现的既有问题。

## 1. 环境

- 后端：`fluentwork-backend` 本机 `./scripts/dev-up.sh`，provider = `dev-echo`
  - `HOST=192.168.2.156`（**必须**：iOS 用的是服务端返回的 `wss_url`，用默认的 `127.0.0.1` 时真机上指的是手机自己）
  - `VOICE_DEV_ECHO_TTS_MOCK=true`：发 `ai.tts.start{codec:"pcm",sample_rate:16000}` + 250 × 20ms + `ai.tts.end`
- 客户端：iOS 真机，`LOCAL_HOST=192.168.2.156`，keyed 路径 = 本次接线的产物
- 语料：按 app 自己的 guest device_id 播种过（否则 `feedback.badge` 永远不来，评估阶段会挂满 20s）

## 2. 验到了什么

**keyed 路径端到端走通**（第一轮 25 帧、第二轮 250 帧两次都是同一形状）：

| 日志 | 说明 |
|---|---|
| `tts_start {codec:"pcm", sample_rate:"16000", turn_id:"turn-2"}` | 协调器按 `ai.tts.start` 认领这一轮 |
| `sequence 0..249 / payload_bytes 640 / socket size_bytes 644` | 帧头 4 字节 + 640 字节 PCM，连续无缺 |
| `tts_first_audio {turn_id:"turn-2"}` | **改造前这条拿不到 turn_id**（生产绑 Mock、派发器从不 active） |
| `tts_end {audio_frames:"250", duration_ms:"5000"}` | 250 帧全部被认领并送进播放口 |
| 无 `tts_decoder_failed` / `tts_frame_dropped` / `transport_audio_dropped` | 一帧都没被丢 |

**打断（可听层）通过**：提示音播放中点击「开始说话」，正在播放的内容立即停止。
这对应 P0-11 的主症状「打断停不下还在说的那一轮」，走的是
`stopPlayback → TTSPlaybackCoordinator.onInterrupt → sink.interruptNow() → 引擎 stop+reset`。

## 3. 没验到什么（以及为什么）

**「打断后在途帧被丢弃」的端到端证据**。250 帧仍是一次性突发送达（~10ms 内到齐），
`ai.tts.end` 紧随其后，等人工打断时该轮已注销 —— **没有在途帧可丢**。
这半条目前只有单元层证据（`bareFrameBetweenInterruptAndEndIsDropped` + 变异验证，
见 `06` §4）。端到端要等网关**流式**发送（Stage 3 之后）才做得出来：dev harness
只能靠客户端音频驱动节奏，一次性突发做不到。

## 4. 与后端 `docs/93`（B8 救援梯子）四条假设的核对

后端已经把梯子音频接进 `ai.tts.*` 通道（协议零新增），并假设了客户端四条行为。
逐条核对本次重构后的客户端：

| # | 后端假设 | 重构后 |
|---|---|---|
| B1 | 二进制帧只在 `ai.tts.start` 之后播（`.idle` 直接丢） | **按契约保持**：无 start 的帧走 legacy 透传（契约 `83_` §2 要求保留这条回滚路径）。梯子帧自带 start，走 keyed ✓ |
| B2 | 播放缓冲是 16k 单声道 PCM16（`RawPCM16FrameDecoder`） | 未动 ✓（`audioFrameDecoder` 就是它的适配器，一个 codec 实现两个调用点） |
| B3 | 序号门按水位丢帧；梯子序号接在本会话已有序号之后；打断过一次仍能播 | **比假设更强**：keyed 帧根本不经过引擎的水位线，归属由轮次注册表判定，水位线管不到梯子帧，也拦不住它 |
| B4 | 新的 `ai.tts.start` 结束上一个流（梯子第二级接上第一级） | 未动，且新实现同样保证：`onStart` 自动 supersede 上一轮（`newStartSupersedesOldWindow` 系列测试） |

结论：**后端不需要为这次重构改任何东西**；梯子的「`ai.tts.start` 打断 AI 那一轮」正是
新协调器的默认行为（`03` §「要新写的只有一件事」那一条已经成立）。

## 5. 过程中发现的两处既有问题（不是本次重构引入）

1. **`.waitingUser` 下的打断不停播**。`SpeechSessionMachine.swift:81-84` 的注释说
   「barge-in stops it on both paths that mean it — from `.aiSpeaking` and from this phase」，
   但 `(.waitingUser, .vadSpeechStart)`（95-99 行）**没有** `.stopPlayback`。若 badge 命中、
   阶段已推进到 `.waitingUser`，而回复音频还在播，此时打断不会停播。500ms 的提示音看不出来，
   5 秒就能暴露。属于状态机（高风险区），建议单独立项。
2. **`timing_ai_first_chunk` 每帧都打**。名字是 first，实际每轮打 N 次（250 帧 = 250 行），
   把真响应的第一条埋掉。与重构无关，但重构后每轮帧数变多让它更吵。

## 6. 附带的一条运维事实

`AppEnvironment.local` 里硬编码的是 `192.168.2.156`（注释却写「默认 127.0.0.1」）。
真机联调要设 `LOCAL_HOST`；不设就会连到那个旧 IP。
