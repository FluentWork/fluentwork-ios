# 28 — 实现说明：测试进程不得打开真机的输入设备（`deinit` 的无条件 `removeTap`）

> 对应条目：`80_架构分析/05_问题清单与建议.md` 的 **S2-9** —— 本轮把它从「卫生」上调为**真问题**。
> 现象：**全量 `swift test` 期间，输入设备被打开 28 次。**
> 改动：`LiveAudioEngine.swift`（`deinit` 加 `hasInstalledTap` 判据；新增 `removeCaptureTap` 注入点；`stopCapture` 的 `.removeTap` 走同一注入点）、
> `LiveAudioEngineTests.swift`（4 处注入 `removeCaptureTap: { _ in }`）。
> 测试数：`591 → 591`（不新增断言，理由见 §6）。
> **「红」是实测计数，不是断言失败**：改动前 `deinit` 触碰输入节点 **28 次**，改动后 **0 次**。逐字见 §6。

## 1. 这条改动守的是什么契约

**测试进程不得打开真机的输入设备。**

这条契约本仓已经立过两次 —— `70_/16_`（测试进程不再构造真的音频引擎）与 `70_/17_`（测试进程里的麦克风替身恒开）。本条撞到的是**第三个洞**，而它一直在同一个文件里。

## 2. 根因

```swift
deinit {
    engine.inputNode.removeTap(onBus: 0)   // ← 无条件
    engine.stop()
    continuation.finish()
}
```

`engine.inputNode` 的**求值本身**就是打开设备的那一步。这不是我的推测 —— 本文件 `startCapture()` 里那段注释已经写明：

> Access inputNode FIRST so the audio graph has at least one node attached before `engine.start()`. On devices without an audio input … starting without an attached node asserts … **Querying the input format forces lazy node creation**

同一个决定（「要不要去动输入节点」）在这个文件里有**四处**，其中三处都有 `hasInstalledTap` 判据：

| 位置 | 判据 | 行 |
|---|---|---|
| `startCapture()` | `if hasInstalledTap` | ✅ `:526` |
| 采集重建（路由相关） | `if hasInstalledTap` | ✅ `:594` |
| `stopCapture()` | `PlaybackTeardown.steps(tapInstalled:)` | ✅ `:758` |
| **`deinit`** | **没有** | ❌ 原 `:445` |

于是**每一个** `LiveAudioEngine` 实例在销毁时都碰一次硬件 —— 包括那些**从未采集过**的。

## 3. 为什么是 28 次

`LiveAudioEngineTests.swift` 里有 **28 处**直接构造真 `LiveAudioEngine`。它们大多数与采集无关（播放、`stopCapture`、解码），本意只是拿一个引擎对象。

**这里要区分两条路径**：`70_/16_` 修的是**容器**那条（`container.audioEngine()` 从真引擎变成 `PlaceholderAudioEngine`，实测 37 → 0）。而 `LiveAudioEngineTests` 是**直接构造** —— 它是**引擎**的测试，本来就该构造真引擎。**那条路径从来没被数过。**

## 4. 为什么 `70_/16_` §7.1 没改它，而那个理由不成立

`70_/16_` §7.1 已经把这条诊断得**一字不差**（连 `stopCapture()` 有判据、`deinit` 没有都点出来了），并给出了正确判据：

> **建议单独立项**，判据取「只移除自己装过的 tap」，与 `stopCapture()` 对齐。

它当时没改的两条理由里，第二条是：

> §4 显示 39→0 之后这条路径在测试里已经不再发生

**这句不成立。** 39→0 说的是**容器**路径；而**直接构造**那条一次都没被数过。判据：**报数的时候要问「我数的是哪条路径」** —— 一个数字只对它被采集的那个集合成立。

这与本仓反复撞到的形状同族，而且是**同一个形状的第二次**：

| 票 | 形状 |
|---|---|
| `70_/18_` | 把「少了一道防线」当成「留下的那道是对的」 |
| **本条** | **把「一条路径堵上了」当成「这个洞堵上了」** |

两次的错法一样：**用一个局部的事实去支撑一个全局的结论。**

## 5. 改法

**第一步：`deinit` 加 `hasInstalledTap` 判据**（与 `stopCapture()` 对齐）。这一条单独就把 28 降到 **4**。

**第二步：新增 `removeCaptureTap` 注入点**，`deinit` 与 `stopCapture` 的 `.removeTap` 都走它。

```swift
private let removeCaptureTap: @Sendable (AVAudioEngine) -> Void
// init 默认值：
removeCaptureTap: @escaping @Sendable (AVAudioEngine) -> Void = { $0.inputNode.removeTap(onBus: 0) },
```

### 5.1 为什么参数取 `AVAudioEngine` 而不是 `AVAudioInputNode`

这是本条**唯一容易做错**的地方。

`engine.inputNode` 的**求值**才是打开设备那一步。如果签名收 `AVAudioInputNode`，那么求值发生在**调用方**（`deinit` 里），也就是在调用注入实现**之前** —— 替身就白注入了，测试照样打开设备。所以节点必须在**默认实现内部**取。

写这条的目的是留一个可检查的形状：**替身要盖住的是「求值」这件事本身，不是「求值之后拿到的对象」。** 任何「先取硬件句柄、再交给替身」的注入都是假替身。

### 5.2 为什么必须有第二步

第一步之后还剩 4 次，都来自那批**采集**测试：它们注入 `installCaptureTap: { _, _, _ in nil }`（`nil` = 安装成功），于是引擎相信真节点上有一个 tap，`hasInstalledTap == true`，`deinit` 就会去真节点上摘。要让它们彻底不碰硬件，**拆除也必须是可注入的**。

### 5.3 这是同一组里的第三个口子

`installCaptureTap` 与 `startCaptureEngine` 的注释写着它们为什么分成两个而不是一个：

> 与 `installCaptureTap` 分成两个口子而不是一个：只堵住 tap，`engine.start()` 仍会因为输入节点被访问而打开设备 —— **半堵的替身比不堵更糟，因为它看起来已经安全了**。

而**拆除**这条路径一直是直接碰 `engine.inputNode` 的。所以那对替身其实一直是半堵的 —— 这正是它自己警告过的形状。

## 6. 测试：为什么没有新增断言，以及「红」是什么

本条的「红」不是断言失败，是**实测计数**：

| 阶段 | `deinit` 触碰 `inputNode` |
|---|---|
| 改动前 | **28** |
| 只加 `hasInstalledTap` 判据 | **4** |
| 再加注入点 + 4 处测试注入 | **0** |

计数方法：把默认实现临时换成会打印的版本，跑全量 `swift test`，数打印行数，改完还原（还原后逐字节校验）。

**为什么没有新增断言**：这条契约的可观测面在**进程外**（系统麦克风指示、`coreaudiod` 占用），`swift test` 里读不到。能钉住的只有「替身被注入了」这一层，而那一层已经由 `AudioEngineResolutionTests` 从**容器**侧钉住；再从**直接构造**侧钉一遍，等于把测试的实现细节抄第二份。

**这条留白是本条最该记住的一点**：判据是「计数」，而**计数不进 CI** —— 它是我手动跑的。所以**这条修复目前没有防线**，只有一条实测记录。要真有防线，得让三个注入点**必须成组提供**（例如收成一个 struct），让「只堵两个」编译不过。见 §9 第 1 条。

## 7. 影响面

- **状态机**：无。
- **协议（线上）**：无。
- **音频**：`deinit` 的行为变了 —— **从未采集过**的实例不再碰输入节点。`hasInstalledTap` 为真时（真的装过 tap）照旧摘，与改动前一致。
- **生产路径**：默认实现与改动前逐字相同（`$0.inputNode.removeTap(onBus: 0)`）；`stopCapture()` 的 `.removeTap` 分支只是换了调用形式。**生产分支行为不变。**
- **回滚**：`git revert` 该提交即可。

## 8. 门禁

| 项 | 命令 | 结果 |
|---|---|---|
| 构建（macOS） | `swift build --disable-sandbox` | `Build complete!` |
| 测试 | `swift test --disable-sandbox` | **591 tests / 28 suites 全通过，连跑 6 次 6 绿** |
| Debug 构建（iOS） | `xcodebuild -project FluentWorkHost.xcodeproj -scheme FluentWorkHost -configuration Debug -destination 'generic/platform=iOS Simulator' build` | `** BUILD SUCCEEDED **` |

**连跑 6 次的耗时**：`6.185 / 6.174 / 6.222 / 6.173 / 6.172 / 6.184` 秒 —— 抖动在 **±50ms** 以内。

### 8.1 顺带：这同时关掉了一处 flaky

改动前全量测试耗时 **8.1–8.7s 且抖**，并且 `captureDiagnosticsKeepTheirMarkNamesAndPropertyKeys` 约 2/3 的运行会红。改动后 **6.17s 且极稳**，连跑 6 次全绿。

**机制**：那 28 次输入设备打开是真实硬件 I/O，会把进程卡住；测试里那道「等泵处理完」的屏障因此有时要 1.5–3.4s 才等到，而它的预算只有 2s。

**这条值得单独记**：我一开始把那个 flaky 诊断为「**屏障的预算低于最坏情况**」（实测 1463/1547/1602/2541/3389 ms vs 预算 2000ms）。那个**观察**是对的，但**根因**错了 —— 3.4s 不是屏障本身需要的，是**硬件停顿**造成的。真正的原因是本条（测试在开真机麦克风）。**症状与根因之间的这一步，只有把设备访问去掉之后才看得出来。**

## 9. 未覆盖 / 未决

1. **本条没有防线**（见 §6）。三个注入点（`installCaptureTap` / `startCaptureEngine` / `removeCaptureTap`）应当**成组提供**，让「只堵两个」编译不过。**建议单独立项。**
2. **第四处仍无判据**：`reconfigureForRouteChange()` 里的 `inputNode.removeTap(onBus: 0)`（`:724`）是无条件的。它只在采集已经跑起来时才执行，所以**不影响测试**；但同一个决定在那里也没有判据 —— 与 `deinit` 原来那处同形，只是后果小。
3. **`removeCaptureTap` 的参数类型是「求值边界」的判据**（§5.1）。如果将来有人把签名改成收 `AVAudioInputNode`，替身会静默失效。**这条没有编译期保护。**
4. **真机听感未验证**：本条只保证「测试不碰设备」，不保证真机的采集行为 —— 后者仍归 `08_` §3 的真机验证（S0-3）。
