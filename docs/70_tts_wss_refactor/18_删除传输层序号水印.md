# 18 — 实现说明：删除传输层序号水印

> 对应缺陷：`10_事实基线与缺陷清单.md` **D2**（🔴，三条子命题 D2a / D2b / D2c）。
> 改动：删除 `AudioFrameDropGate.swift` 整文件（四个类型）与它的全部接线（6 个源文件 + 5 个测试文件）。
> **本改动落在高风险区**（`AGENTS.md` High-Risk Paths 第 1 条：audio engine 与打断逻辑），影响面见 §5。
> 落地方式：**直接删除**，同 `07_` 的先例（2026-09-20 用户决定），不采用仓库惯例的「先标记后删」。

## 1. 这条改动守的是什么契约

**传输层不丢弃音频帧。**

理由是能力问题，不是偏好问题：丢弃是「这一帧属于哪一轮」这个问题的答案，而回答它需要**轮次轴**。传输层只有**序号轴**——`WSAudioFrame` 上只有 `sequence` 和 `payload`（`WSAudioFrameCodec.swift:9`），线上帧不带 `turn_id`。所以传输层不是「回答得不好」，是**没有回答这个问题所需要的信息**。

契约的后半句（归属由谁回答）不是本次发明的，它写在仓库自己删掉引擎侧同款水印时给出的论证里（`07_Stage4_删除死路径.md` §2），逐字：

> 水印是一个**序号**水印，而序号说不出一个帧属于哪一轮。想用序号去归属轮次，就会在这里失败。归属必须由轮次本身承载——这正是 `TTSPlaybackCoordinator` 按 `ai.tts.start` / `ai.tts.end` 括起来的轮次做归属、而 `AudioPlaybackGate` 被删掉的原因。

契约的前半句（传输层不丢）是本次补上的，并且现在写进了代码：`URLSessionSocketTransport.handle(message:)` 的 `.data` 分支无条件 `emit(.audio(frame))`。

**改动前，这个契约在传输层不成立**，而且不成立的方式有两处，互相独立（§2.1、§2.2）。

## 2. 根因：水位线在错误的轴上，而它恰好是唯一能无声吞掉整轮音频的机制

### 2.1 D2a — 它做不到它被声称做的工作【实证】

改动前的机理：

- `BargeInAudioGate.markInterrupted()` 把水位设成 `gate.maxObservedSequence`，即**已经收到的最高序号**；
- 判定是 `shouldDrop(seq) = seq <= watermark`。

WS 是保序流。所以打断**之后**到达的帧，序号**必然大于**水位 → **一律放行**。它只能挡住序号**等于或小于**已收最高值的帧，也就是重复帧与乱序帧——而那不是它注释里写的职责（注释写的是「drop late TTS chunks from before the interrupt」，即「被打断那一轮还在链路里的帧」）。

改动前的测试亲手钉住了这一点。`10_` §D2a 引用的 `SocketTransportTests.swift:562-567`（**改动前**的行号）：

```swift
await transport.markInterrupted()                          // maxObserved = 2
#expect(await transport.emitAudio(sequence: 2) == false)   // 重复帧 → 丢
#expect(await transport.emitAudio(sequence: 3) == true)    // 后续帧 → 放行（注释：「A later frame closes the run」）
```

**推论**：真正让被打断那一轮停下来的是 `TTSPlaybackCoordinator.onInterrupt` → 把该轮标成 `.superseded` + `sink.interruptNow()`（`TTSPlaybackCoordinator.swift:103-108`），**不是**传输层水印。

于是三处文档断言是错的，本次一并订正（§3.3）：`README.md:23`「今天 barge-in 的丢弃**只在传输层发生一次**（`BargeInAudioGate`）」、`LiveAudioEngine.swift:826`、`AppDependencies.swift:130-132` 的同一句话。

### 2.2 D2b — 它能在窗口期内把**下一整轮**音频吞掉，而客户端无自愈【实证，本次坐实】

机理：

- 水位从武装到 `ai.turn.end` 之间一直有效；
- 网关的帧编号**每轮从 0 起**（`08_` §2 实测）；
- 所以水位武装期间到达的下一轮 `0..N`（≤ 水位）会被**全部丢弃**。

这正是 F18 的形状。改动前的 `SocketTransportTests.swift:500-505` 记着它的后果：

> numbering restarted at 1 while the watermark sat in the hundreds, and every frame after it was dropped **in silence**——text kept arriving, audio was simply gone.

改动前，遮住这条的**只有后端承诺**，不是客户端不变量：

1. 被打断那一轮的 `ai.turn.end` 必须先于下一轮首帧到达（改动前的代码注释称「B15 guarantees it on every exit path」）；
2. 网关不得重启编号。

**客户端没有自愈**：清除水位的路径只有 `ai.turn.end` 与 `connect()`。若被打断的那一轮**永远收不到** `ai.turn.end`——连接断了、回合被放弃、后端把它当会话级中止——水位会一直武装到下一次 `connect()`，期间每一轮都可能整轮静音。

> **本条在 `10_` 里标的是【推断】**，理由是「dev harness 是一次性突发 + `ai.tts.end` 紧随，barge-in 的端到端行为从未被验证」。本次没有新增真机事实，而是把它**变成了可复现的单元测试**：脚本里不给被打断轮发 `ai.turn.end`，下一轮编号从 0 重启。逐字红输出见 §6.1。**确定性因此从【推断】升到【实证】——实证的是「客户端在这个脚本下确实吞帧」，不是「真机上必定发生」。**

### 2.3 D2c — 它违反了仓库自己删掉另一道水印时的论证【读码】

引擎侧那道 `AudioPlaybackGate` 与传输层这道 `BargeInAudioGate` **同轴（序号）、同类（水位线）**。§1 引的那段论证逐字适用于它。

当时的处理是「删掉一道，留下另一道，然后声称留下的那道是**唯一一处**」（`README.md:23`、`07_` §2 末、`LiveAudioEngine.swift:826`、`AppDependencies.swift:130-132` 四处都这么写）。**把「少了一道」当成了「留下的那道是对的」——这两件事不一样。** 而保留的那道，恰好是两道里唯一能无声吞掉整轮音频的。

## 4. 为什么是「删」，而不是「补一道兜底」

评审（`11_` §7 第 2 问）给这一条留了余地：也可以「留一道兜底，最小改动是给它补上『下一个 `ai.tts.start` 也清水位』」。下面是为什么选了删。

### 4.1 补水位生命周期只能治标，治不了 D2a

补「下一个 `ai.tts.start` 也清水位」能缩小 D2b 的窗口，但 **D2a 一点没动**：那道门仍然做不到它被声称做的工作，仍然只是一道按序号挡重复帧的门。而且它**仍然是唯一能无声吞掉整轮音频的机制**——只是窗口更窄。一个不干活、只在特定时序下有害的机制，加一层生命周期管理并不会让它开始干活。

### 4.2 「留一道」与「删一道」的收益是数量级不对称的

| | 改动前水位能挡下的 | 改动前水位会造成的 |
|---|---|---|
| 内容 | 序号 ≤ 已收最高值的帧，即**重复帧 / 乱序帧** | 水位武装期间下一轮的 `0..N`，即**整轮音频** |
| 可能性 | WS 保序 ⇒ 乱序不可能；重复需要网关自己重发同一个序号 | 需要一个后端承诺失守（`ai.turn.end` 缺席 / 编号重启） |
| 后果量级 | 一帧 = 20 ms（640 B payload）的重复或毛刺 | 一整条回复静音（`07_` §2 记的实测是 61 秒 / 113 帧） |

删掉之后，重复帧/乱序帧会**到达协调器**并按轮次放行。代价是一帧 20 ms 的重复（而且只在网关重发同序号时才出现）；换来的是「整轮静音」这个失败模式从客户端消失。这个交换不是五五开。

### 4.3 为什么连 `markInterrupted()` 一起删

它是水印的**武装手柄**，协议注释逐字就是水印。删掉水印而留着它，等于留一个注释在说谎的空方法（三处实现里两处会变成空体，第三处只剩一个没人读的计数器）。

`07_` 的先例是同一个形状：删 `AudioPlaybackGate` 时**连它的入口 `play(frame:)` 一起删**。这里照做。

删掉之后，一次 barge-in 在传输层就是**一个出站控制帧**（`send(control: .interrupt)`），没有别的。`14_`（D3）关于「一次打断只发一次 `interrupt`」的结论不受影响——被删掉的只是那半句「顺带重新武装水印、丢掉第一段丢弃运行的报告」。

### 4.4 为什么 `audioFrameDropped` 与 `AudioDropReport` 一起删（`77_` P1-22 的关切迁去哪）

`AudioDropReport` 是为 `77_` P1-22 建的：「回复回来少了一半」时第一个该问的问题是「丢弃可观测吗」。**这个关切不会因为删掉水印而消失**，但它已经有更好的载体：

- 谁决定丢弃，谁负责上报——`TTSPlaybackCoordinator` 的 `.dropped(turnID:reason:errorDescription:)` 就是那个上报；
- 中间件把它记成 `tts_frame_dropped`（reason ∈ `superseded` / `unknownTurn`）与 `tts_decoder_failed`；
- 它有水印上报**没有**的东西：`turn_id`。水位上报的三个字段是 `sequence` / `watermark` / `dropped`，全是序号轴上的数——**丢了一整轮的时候，它说不出丢的是哪一轮**；
- 它已有测试：`TTSPlaybackCoordinatorTests.bareFrameBetweenInterruptAndEndIsDropped`（`:222-236`）钉住 `.dropped(reason: .superseded)`。

留一个「永远不会发生的诊断事件」是另一类缺陷，而且是本仓刚刚在 `16_` 里定性过的那一类：**一个从不取真值的判据**。

## 5. 影响面（高风险区，逐条）

- **状态机**：无影响。`SpeechSessionMachine` 未改动。
- **协议**：无影响。线上二进制帧格式（4 B 大端 seq + payload）、控制帧集合、鉴权与 ping/pong 全未动。本次只删客户端本地机制。
- **音频**：**行为有变化，方向是「更少丢弃」。** 改动前，被打断轮之后的下一轮有被整轮吞掉的可能（§2.2）；改动后不会。代价见 §4.2：重复帧/乱序帧不再被传输层挡下，改为到达协调器按轮次放行。
- **打断路径**：`DefaultSpeechSessionClient.submitTranscript("__interrupt__")` 从「两件事」变成「一件事」。出站 `control.interrupt` 的行为与顺序**未变**，`14_` 修的那个顺序问题不受影响。
- **可观测性**：`transport_audio_dropped` 埋点消失；`tts_frame_dropped` / `tts_decoder_failed` 保留且是更好的载体（§3.2、§4.4）。
- **DI / 启动路径**：`SocketTransportProtocol` 少一个方法，三处实现同步改。`AppDependencies` 的 `socketTransport` 绑定未动。
- **回滚**：`git revert` 该提交即可恢复整条机制（一个文件 + 六处接线 + 五处测试）。

turn-2: seq 0, seq 1, seq 2            ← 编号每轮从 0 重启

↳   delivered → [1, 2]
✘ Test aBargeInMustNotSwallowTheNextTurnsAudio() failed after 0.007 seconds with 1 issue.

## 7. 记录：本次自己的一个操作失误（工具层）

改动 `URLSessionSocketTransport.swift` 时，我**在同一条消息里并发提交了两处编辑到同一个文件**，两次都返回「成功」，但**只有后一次真正落盘**。结果是 `private var bargeIn = BargeInAudioGate()` 与 `markInterrupted()` 两处删除被静默丢弃，靠改完后的全仓 grep 才发现。

这不是本仓代码的问题，但它是一条会重复踩的坑：**对同一文件的多次编辑必须串行提交，并在改完后用 grep 复核，不能相信编辑工具的「成功」回执。** 本次的复核方式就是 §3.1 那张表——每一行都在全仓 grep 里确认过零残留（只剩注释里的历史引用）。

## 8. 顺带记录：这条链路的真机验证仍未做

`08_` §3 已经记着「**没有在途帧可丢**」——dev harness 是一次性突发（250 帧 ~10 ms 到齐）+ `ai.tts.end` 紧随，所以 **barge-in 的端到端行为从未被验证过**。

本次删除**不改变这一点**，也不依赖它：删掉的机制在改动前就做不到它被声称的工作（§2.1 是实证），所以「真机上有没有在途帧」不影响这次删除的正确性。真机仍待验证的是**协调器那条归属路径**，与本改动正交：

1. 打断后上一轮的尾音不得混进下一轮（现在只有协调器在管这件事，所以更需要验）；
2. 断线重连后序号不回退、还有声。

## 9. 门禁

| 项 | 命令 | 结果 |
|----|------|------|
| 构建 | `swift build --disable-sandbox` | `Build complete! (5.53秒)` |
| 测试 | `swift test --disable-sandbox` | **583 tests in 28 suites passed** |
| Debug 构建 | `xcodebuild -project FluentWorkHost.xcodeproj -scheme FluentWorkHost -configuration Debug -destination 'generic/platform=iOS Simulator' build` | **BUILD SUCCEEDED** |

> **构建目标勘误（沿用 `15_` §8）**：`-destination` 必须是 `generic/platform=iOS Simulator`。用 `platform=macOS` 会失败——`project.yml` 声明 `platform: iOS` / `deploymentTarget: "17.0"`，macOS 目标会让它去为本机真机签名，报 `Provisioning profile ... doesn't include the currently selected device`。

`swift test` 的那批 2 秒超时 flaky（`15_` §7 记录，已证明在未改动的基线上同样失败）本次未复现。
