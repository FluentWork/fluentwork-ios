# 启动性能优化与测量指南

**版本**：V1  
**日期**：2026-09  
**适用范围**：`fluentwork-ios` 当前 `Redux + Middleware + Bootstrap` 架构

---

## 1. 先说结论

在当前架构下，启动性能优化的重点不是简单地“少做事情”，而是**重新安排关键路径与非关键路径的顺序**。

目标有两个：

1. 真正缩短 `appLaunched -> bootstrap ready -> 首屏可交互` 的总耗时
2. 在无法完全缩短时，降低用户感知等待

当前链路的关键事实是：

1. 启动入口不再是单一 `didFinishLaunching` 里的顺序代码
2. 启动链会经过 `Action -> Middleware -> Client -> Reducer -> UI`
3. 真正的大头通常不在 Redux 本身，而在：
   - 网络请求
   - 本地持久化读取
   - 首屏渲染范围
   - 测试/调试配置带来的隐性阻塞

---

## 2. 传统 UIKit 与当前架构的差异

| 维度 | 传统 UIKit | 当前 Redux 架构 |
|---|---|---|
| 启动入口 | `didFinishLaunching` 内直接串行执行 | `.lifecycle(.appLaunched)` 触发 middleware |
| 控制方式 | 开发者手动安排顺序 | 通过 action / reducer / middleware 链流转 |
| 主要阻塞点 | 主线程同步工作 | 网络、状态流转、首屏投影 |
| 启动完成标志 | `window.makeKeyAndVisible()` | `bootstrapStatus == .ready` 且 UI 完成投影 |

因此，当前架构下不能只盯着 `AppDelegate`。  
必须把优化对象放到以下链路：

```text
appLaunched
  -> appBootstrapMiddleware
  -> bootstrapClient.loadBootstrap()
      -> 网络 / 缓存 / 本地存储
  -> bootstrapSucceeded
  -> AppReducer 投影
  -> SwiftUI 首屏渲染
```

---

## 3. 当前仓的启动关键路径

当前实现的主要文件：

- `Shared/FluentWorkCore/Architecture/Middleware/AppBootstrapMiddleware.swift`
- `Shared/FluentWorkCore/Dependencies/AppDependencies.swift`
- `Shared/FluentWorkCore/Architecture/AppReducer.swift`
- `Shared/FluentWorkCore/Architecture/AppState.swift`
- `Shared/FluentWorkCore/AppEnvironment.swift`

当前时间线可以抽象为：

```text
AppLaunched
    ↓ (A) middleware 调度
BootstrapClient.loadBootstrap()
    ↓ (B1) ensureGuestToken()
    ↓ (B2) resolver.refresh() / snapshot()
    ↓ (C) 组装 BootstrapResult
bootstrapSucceeded
    ↓ (D) reducer 投影到 AppState
    ↓ (E) SwiftUI 根据 bootstrapStatus / workspace / featureFlags 重绘
用户看到首屏
```

这里真正值得优化的优先顺序通常是：

1. `(B)` 网络与缓存
2. `(E)` 首屏渲染范围
3. `(A)+(D)` 状态链路不必要的放大

---

## 4. 优化优先级

### P0：网络与缓存

这是收益最大的部分。

#### 4.1 并行拉取可并行的启动依赖

如果启动阶段有两个彼此独立的依赖，不要串行：

```swift
async let authInfo = ensureGuestToken()
async let refresh = resolver.refresh()

let (_, auth) = try await (refresh, authInfo)
let remote = resolver.snapshot(for: AppFeatureFlag.allCases)
```

当前口径下，`ensureGuestToken()` 与 feature flag refresh 理论上可以评估并行化。  
前提是：

1. `resolver.refresh()` 不依赖 token
2. 后端 feature flag 请求不要求先拿 guest token

如果依赖真实后端鉴权，则不能直接并行，需要先明确契约。

#### 4.2 缓存优先，后台刷新

如果本地已有上一次成功的 bootstrap 快照，可以采用：

1. 先读缓存
2. 立即投影首屏
3. 后台刷新网络结果
4. 有差异再二次更新 Store

适合缓存的内容：

1. `FeatureFlagSnapshot`
2. `preferredSurface`
3. 纯展示型启动快照

不适合长期信任缓存的内容：

1. 短时效 token
2. 强依赖后端实时态的安全字段

#### 4.3 区分冷启动 / 热启动 / 回前台

不是每次都需要完整 bootstrap。

建议分三类：

1. 冷启动：完整 bootstrap
2. 热启动：优先缓存，后台刷新
3. 前后台切换：按 TTL 决定是否静默刷新

这样可以避免把冷启动成本无差别施加到每次前台恢复。

---

### P1：UI 感知速度

#### 4.4 首屏先显示框架，不等所有数据

不要把所有首屏展示都绑死在 `bootstrapStatus == .ready` 的最终完整数据上。

更合理的拆法是：

1. bootstrap 只负责全局前置条件
2. 首屏页面自己的内容异步加载
3. 首屏先显示可交互框架或骨架屏

例如：

1. Tab 框架先出来
2. 当前选中 surface 先出来
3. 次级内容后续填充

#### 4.5 延迟渲染非首屏模块

如果启动后默认只进入一个 surface，就不要在首帧把所有 Tab / route 对应页面一起重建。

重点原则：

1. 首屏只渲染当前活跃 surface
2. 其他模块按需加载
3. 不让 bootstrap 成功后的第一轮渲染带出太多非关键子树

---

### P1：Reducer 与状态投影

#### 4.6 保持增量更新，避免全量重建

当前 `AppReducer` 已经是增量写入，这个方向是对的。

启动阶段不应做：

1. 全量重建 `AppState`
2. 把不相关模块一并 reset
3. 在一个 action 中做过多派生写入

推荐保持：

1. `bootstrapStatus`
2. `featureFlags`
3. `workspace.activeSurface`
4. `auth`

只更新必须更新的字段。

#### 4.7 不要把高频或次级状态塞进 bootstrap success

启动成功 action 只应承载启动快照，不应顺带混入：

1. 首屏业务列表
2. 轮询结果
3. 音频链路实时状态
4. 大量 analytics 附带信息

否则 reducer 和首屏渲染范围都会被放大。

---

### P2：Middleware 与依赖装配

#### 4.8 非关键 middleware 延后参与

不是所有 middleware 都必须在首屏 ready 前参与关键路径。

适合延后的：

1. analytics
2. 次级预取
3. 非首屏业务模块轮询
4. 调试辅助能力

必须留在关键路径的：

1. bootstrap
2. network monitor
3. 首屏必需的认证 / feature flag

#### 4.9 把“预加载”与“正式 bootstrap”区分开

如果后续要做更激进的启动优化，可以考虑在更早时机启动预加载，但必须注意：

1. 预加载结果只能作为输入源或缓存
2. 不要让预加载绕开正式 bootstrap 链
3. 正式 Store 投影仍然应通过统一的 bootstrap action 完成

否则调试、测试和生产行为会分叉。

---

### P2：持久化与本地读取

#### 4.10 把启动快照作为整体缓存，而不是散字段读取

比起零散地从 `UserDefaults` / Keychain / 本地存储读多个碎片字段，更推荐：

1. 定义单独的 bootstrap cache model
2. 一次 decode 整个快照
3. 命中后直接投影

这样更容易：

1. 控制版本
2. 做 TTL
3. 统计缓存命中率

#### 4.11 内存缓存优先于磁盘缓存

二次启动或同次 session 内再次使用时：

1. 先读内存
2. 再回落磁盘

这能减少重复解码与 I/O 抖动。

## 5. 必须先做测量

没有测量就没有优化。

建议把启动链路至少打四个点：

1. `app_launched`
2. `bootstrap_started`
3. `bootstrap_network_ready`
4. `bootstrap_state_ready`
5. `first_surface_rendered`

可以先用轻量实现：

```swift
enum LaunchPerfMark {
    static var marks: [String: CFAbsoluteTime] = [:]

    static func mark(_ key: String) {
        marks[key] = CFAbsoluteTimeGetCurrent()
    }

    static func duration(from: String, to: String) -> Double? {
        guard let start = marks[from], let end = marks[to] else { return nil }
        return (end - start) * 1000
    }
}
```

更推荐最终接入：

1. `os_signpost`
2. Instruments Time Profiler
3. Network Instruments
4. Core Animation / SwiftUI render diagnostics

## 6. 当前仓建议的落地顺序

### 第一阶段：先把现状量出来

建议先加以下埋点或日志：

1. `appLaunched` 到 `bootstrapStarted`
2. `bootstrapStarted` 到 `BootstrapClient.loadBootstrap()` 返回
3. `bootstrapSucceeded` 到首屏 surface 可见

如果没有这三段时间，后面优化容易拍脑袋。

### 第二阶段：评估 bootstrap 依赖并行化

重点审查：

1. `ensureGuestToken()` 是否真必须先于 feature flag
2. `resolver.refresh()` 是否可与 token 获取并行

如果契约允许，这是最便宜的一次收益。

### 第三阶段：补 bootstrap cache

建议新增一个独立缓存层，例如：

1. `BootstrapCacheStore`
2. `CachedBootstrapSnapshot`

策略：

1. 冷启动先读缓存
2. 命中则先 ready
3. 后台刷新再二次投影

### 第四阶段：拆首屏渲染与业务加载

确保：

1. bootstrap ready 不等于所有首页数据都 ready
2. 只要求全局前置条件 ready
3. 次级内容按需异步加载

---

## 7. 当前架构下不推荐的做法

1. 把所有初始化逻辑塞回 `didFinishLaunching`
2. 为了快而绕过 Store，直接在 UI 层偷偷改启动状态
3. 把非关键请求也并入 bootstrap 主链
4. 启动时把所有模块页面一起预构建
5. 为了“看起来快”而牺牲状态一致性

这些做法会把短期收益换成长期维护成本。

---

## 8. 推荐优先级清单

| 优先级 | 优化项 | 预期收益 | 实现难度 |
|---|---|---:|---:|
| P0 | 启动链路测量点 | 明确瓶颈位置 | 低 |
| P0 | 评估 token / flags 并行化 | 100~300ms 级 | 中 |
| P0 | bootstrap cache + 后台刷新 | 二次启动显著提升 | 中 |
| P1 | 首屏框架先渲染 | 降低感知等待 | 低 |
| P1 | 延迟非首屏模块渲染 | 降低首帧压力 | 中 |
| P1 | 保持 reducer 增量投影 | 降低重绘开销 | 低 |
| P2 | 延迟非关键 middleware 工作 | 缩短关键路径 | 中 |
| P2 | 统一启动快照缓存模型 | 降低本地读写成本 | 中 |

---

## 9. 一句话原则

**在当前 `Redux + Middleware + Bootstrap` 架构里，启动优化的核心不是把所有工作删掉，而是让“必须先完成的工作”更少、更并行、更可缓存，让“不必阻塞首屏的工作”更晚发生，并且用测量数据持续校正优化方向。**
