# 真机测试指导手册

**日期**：2026-09-11
**定位**：**所有只能在真机上回答的问题，一本手册跑完。** 手机会在你手里 —— 所以这本手册只写**做什么、看什么、记什么**。
**诊断与背景**不在这里：P1-6 / P1-8 的原理见 [`59_真机验证简报`](./59_device_verification_briefing.md)；
AEC 的三条路径与失败退路见 meta `77_` §3。

## 0. 开工前的准备（**一次做完，缺一项后面全废**）

| # | 检查 | 怎么确认 | 不做会怎样 |
|---|---|---|---|
| 1 | 本地栈在跑 | `lsof -nP -iTCP:8080 -iTCP:8081 -sTCP:LISTEN` 有两个进程 | 全部失败 |
| 2 | 真机与 Mac **同网段** | 手机浏览器打开 `http://<Mac IP>:8080/healthz` | 连不上 |
| 3 | `AppEnvironment.local(host:)` 指向 **Mac 当前 IP** | 注意：工作区里那个改动**没有提交**，本机是 `192.168.2.111` | 连不上 |
| 4 | **真机语料已灌**（⚠️ 见下） | 灌库后 `GET /internal/v1/corpus/blocks?user_id=<真机 user_id>` 返回 10 条 | **徽章永不出现，且不报错** |
| 5 | 后端日志可读 | `tail -f /tmp/fluentwork-backend.log` | AEC 那条验不了 |

### ⚠️ 第 4 项是**最容易踩空**的一项

`dev-up.sh` 的自动灌库**写死** `device_id=corpus-seed-dev-device`，而**真机永远不是这个 id**。
语料按 `user_id` 隔离，所以真机那边是**空的** —— 于是 `feedback.badge` 永不出现，
**而且没有任何报错**，看起来就像"徽章功能坏了"。

```bash
cd fluentwork-backend
go run ./cmd/corpus-seed -device-id <真机 device_id>
```

`device_id` 从 iOS 日志或 Keychain 取（历史上形如 `DA87E7D4-1371-4984-AD3F-D6D70B4D17D2`）。

**灌进去的 10 条锚点（说左边 → 命中右边）**：

| 说 | 命中徽章 |
|---|---|
| I am blocked on the API review. | I'm blocked on the API review. |
| how about we pair on this tomorrow | How about we pair on this tomorrow? |
| I don't want to push the deadline | I'd rather not push the deadline. |
| thanks for your time | Thanks for your time today. |
| let's ship it | Let's ship it. |
| could you clarify | Could you clarify what you mean by that? |
| does that work for you | Does that work for you? |
| I'm not sure yet | I'm not 100% sure yet, but I'll confirm by EOD. |
| let's wrap up the meeting | Let's wrap up. |
| bottom line | Bottom line: we'll ship next Tuesday. |

> **DEBUG 版的注入徽章按钮走 `badgeHit` 直通路径，绕过后端检测。**
> 它验的是**渲染**，不是**命中**。所以 **T2 不能**用它，**T1 可以**。

## 建议的执行顺序

**先跑只读的、再跑会改变状态的。** 顺序按"一次会话能覆盖多少"排：

```
T4 (AEC)  →  T2 (徽章)  →  T1 (音频流式)  →  T3 (静音保活)  →  T5 (abort 串味)
   独立         需要语料       需要连续几轮        需要一次长间隔      需要刻意中止
```

**T3 必须最后**（它要求两轮之间静默 >60s，插在中间会把其他项拖长）。
**T5 建议单独一轮**（它故意制造中止，会污染同会话的其他观察）。

## T1 — 音频流式：AI 是不是更早开口

**验证**：P1-2 音频半边（`57e2128`）。**这是唯一靠听感判断的一项。**

| | |
|---|---|
| **前置** | 无（不需要语料） |
| **做什么** | 连续跑 **3 轮**正常对话，每轮等 AI 说完再答。**不要打断** |
| **看什么** | ① **首响**：你停下到听见第一个音节，是否明显更早 ② **整轮音频**：有没有**爆音 / 剪尾 / 重复** ③ 长回复（20s 以上）**尾部有没有被掐掉** |
| **判据** | ②③ 是**通过/不通过**；① 是**主观对比**，记下感受即可 |
| **记什么** | 每轮：首响感受（"更快/一样/更慢"）+ 有没有爆音/剪尾/重复 + 回复大致长度 |
| **不过的话** | ②③ 出问题 → 先查音频流式的重采样与分块（backend `docs/56` §7） |
| **⚠️ 附带一项未测的假设** | `LiveAudioEngine` 的播放缓冲是**按"轮末一次性爆发"调的**（`.unbounded`，见 F13/F18）。现在音频来得**更早也更均匀**，**这个假设从没测过**。听感上表现为：声音断续、忽快忽慢、或开头被吞。**专门留意这一条。** |

## T2 — 徽章与音频是两个时钟

**验证**：P1-8 的三条。**细节与背景见 `docs/59` §P1-8。**

### T2a — 4 秒窗口 vs 播放长度（**人的判断，不是日志**）

| | |
|---|---|
| **做什么** | 说一句命中徽章的话（如 `bottom line`），引 AI 给一段**长**回复 |
| **看什么** | 徽章出现时**你在听音频** —— **你注意到徽章了吗？** |
| **判据** | 台账原话：**「判据是"用户看得见吗"，不是日志」** |
| **记什么** | **如实记注意力状态**。「我在听，没看见」是有用数据；「我盯着屏幕所以看见了」**不是** |
| **不过的话** | 那是**产品判断**（窗口该多长），不是 bug —— 改 `BadgeFeedbackFeature.visibleWindowSeconds` 前**先定产品意图** |

### T2b — 超时后到达的徽章，状态机不认

| | |
|---|---|
| **做什么** | 说一句命中徽章的话，**20 秒内不出声**，等徽章 |
| **看什么** | 徽章**会显示**（`badgeHit` 无条件派发），但机器**已经不记"评估已到"** |
| **要判断的是** | **这个"不记"有没有害** —— 先看它有没有喂给 turn outcome / 回顾页 |
| **记什么** | 徽章到得比 20s 早还是晚 + 显示是否正常 |

### T2c — `EvaluationArrivalBox` 不按轮

| | |
|---|---|
| **做什么** | 造出一次"徽章迟到"（同 T2b），**紧接着开下一轮**，说另一句命中徽章的话 |
| **看什么** | 下一轮的评估阶段**有没有跳过 20s 计时器**（不等超时就跳走） |
| **注** | **这是既有问题，F19 没引入。** 验出来有害再修 |

## T3 — 静音保活（P0-4）

**验证**：`762d26e`。**一直挂着没验。**

| | |
|---|---|
| **前置** | 无 |
| **做什么** | 正常说完一轮 → **静默等待 90 秒以上**（不要说话、不要切后台、不要让屏幕锁） → 再说一轮 |
| **判据** | 第二轮**正常**：能被识别、AI 正常回复、**没有 `provider_audio_failed`** |
| **记什么** | 实际间隔秒数 + 第二轮是否正常 + 失败的话贴后端日志里那一行 |
| **不过的话** | 看 `keepaliveIdleThreshold`（60s）与 `CommitInputMute` 的时序（backend `docs/53`） |
| **⚠️** | 这是本手册里**最容易因"顺手动了手机"而作废**的一项 —— 屏幕锁、切后台、接电话都会让结论无效。**记下你有没有碰过手机。** |

## T4 — AEC：**本手册最重要的一项**

**验证**：P0-2。**AEC 从来没被验证过**，而它就是"AI 会不会听见自己说话"。

| | |
|---|---|
| **前置** | 后端日志可读 |
| **做什么** | 让 AI 说一段**含独特短语**的话（例如引它说 `bottom line` 那句），**你全程不出声**。**重复 3 次** |
| **判据** | **该轮 transcript 为空 / 没有触发新一轮** |
| **工具** | 静默一轮之后跑：`./scripts/check-aec.py /tmp/fluentwork-backend.log`（exit 0 = 无自激；1 = 发现自激） |
| **还要看** | 三个自激信号：①转录里出现 **AI 自己刚说过的话** ②**没开口却触发新一轮** ③**`interrupt` 自触发**（AI 被自己的声音打断） |
| **记什么** | 三次各自的：transcript 内容 + `check-aec.py` 的 exit code + 有没有自触发新一轮 |
| **不过的话** | **不是回去调参，是走退路**：先上半双工（播放时停上行，barge-in 暂时降级为按钮触发），见 meta `77_` §3.4 |

> **这一项决定 P0-2 的方向。**
> 通过 → 主方案（Apple Voice-Processing I/O）成立，`setVoiceProcessingEnabled(true)` 那条改动才值得做。
> 不通过 → 先别改引擎级开关，**直接上兜底**。

## T5 — `abort` 之后 ASR 会不会串味

**验证**：P1-6。**细节与原理见 `docs/59` §P1-6。建议单独一轮。**

| | |
|---|---|
| **做什么** | ① 说「**蓝鲸在深海用声呐交流，频率很低**」，**说到"频率"就点中止** ② 等 2 秒 ③ 说「**今天下午三点开会，会议室在三楼**」，说完 |
| **判据** | 第 2 轮的转录**只有第 2 轮的话** |
| **记什么** | 第 2 轮转录的**原文**（不是结论）；第 1 轮有没有被落库 |
| **最少 3 次** | **时序问题，一次通过说明不了什么。** 三次里有一次串味就成立 |
| **不过的话** | 先怀疑**音频序号**而不是 ASR（F18 的坑：重开把序号从 1 重来） |

## 记录模板（照抄，别只写结论）

**时序问题的结论在单次上不可信，在转述里更不可信。** 每项至少记：

```
## T?  <项目名>   <日期时间>
设备:  <device_id 前 8 位>     构建: <commit 短哈希>
间隔/条件: <如 T3 的实际静默秒数；T5 的中止时机>

第 1 次:  <现象原文 / 日志行>
第 2 次:  ...
第 3 次:  ...

结论: 通过 / 不通过 / 无法判定（说明为什么）
```

**三条纪律**：

1. **贴原文，不贴转述。** 转录就贴转录，日志就贴日志行。
2. **失败时贴失败那次的原始输出。** 那是唯一能回放的东西。
3. **"无法判定"要写清原因**（手机锁了 / 说错词了 / 后端日志断了）—— 它比一个含糊的"通过"有用。
