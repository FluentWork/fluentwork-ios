## 二、第二波的目标

第二波聚焦把"说 -> 读 -> 入库"完整流水线做实：

1. 回顾页从骨架升级为完整版（转录 / 三层评价 / 双栏对照）
2. 炼化卡可编辑并入库
3. 语料库页可浏览、筛选、搜索，弱网本地优先
4. 每日一读可消费，跟读只录音不出分
5. 对话中命中已练表达时可见轻量徽章

> **第二波目标不是再开新链路，而是让第一波打通的链路长出完整的"读"与"入库"两面。**

## 七、必须遵守的禁区

继承第一波禁区：

1. 不修改人写的 `SpeechSession` 状态机本体
2. 不随意重构 AudioEngine 边界
3. 不在 View 中直接依赖 transport 或 audio 底层实现
4. 不把每帧高频数据塞进全局 Store
5. 不因为方便而绕开上游契约

第二波补充：

1. 跟读不出分是硬口径，不提前引入评分展示
2. 徽章展示不得阻塞语音流，不弹窗不震动
3. 语料库弱网缓存不得绕过同步层直接写服务端状态

## 八、第二波仍需特别盯住的功能薄弱点

1. 回顾页这波虽然进入完整版范围，但最容易漏掉的是失败态与渐进到达时序：如果只做 ready path，`review failed` 或炼化卡未就绪时会退化为空白页，用户会误判为数据丢失。
2. `I13` 若只写同步主路径，不覆盖游客归并后的本地缓存失效 / 重建、删除语义、收藏状态同步，`I9` 上线后会在弱网与换账号场景出现脏数据残留。
3. 每日一读的功能漏洞不在页面壳，而在“生成未就绪 / 生成失败”时有没有稳定兜底：至少要保证轮询态、预置内容或最近成功内容三者之一可落地，否则入口可见但内容不可消费。
4. 徽章展示当前只定义了“轻量、不阻塞”，但还缺一条防刷屏口径：同一话轮的重复命中应做去重或合并展示，否则 UI 容易在高频命中时失控。
5. `I12` 若只追求“能录能播”，但不补首响、打断、后台播放三类量化验证，第二波结束后仍无法判断语音链路是否真的从 stub 进入可发布状态。

## 九、提交与评审口径

沿用第一波口径：

1. 每个 PR 尽量只对应一个 iOS issue 或一个 PR 级任务
2. 行为变化必须补测试或说明为什么当前只能先补占位
3. 若接口依赖 backend 未就绪，优先保留清晰边界，不做硬编码临时方案
4. 若发现 PRD 或技术文档口径冲突，应先回写 `meta`，不要在本仓自行定案
5. 第二波薄弱点是否过检，以 `fluentwork-meta/docs/50_测试与验收/51_FluentWork第一波能力验证与第二波薄弱点检查门禁.md` 的对应门禁为准
