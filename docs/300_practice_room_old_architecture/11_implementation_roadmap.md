## 二、Week 1-2: 基础设施层

### 2.1 目标

- 建立 WebSocket 全双工连接
- 实现音频采集与播放
- 验证首响延迟 ≤ 1.5s (P90) ← **GO/NO-GO 决策点**

### 2.2 任务清单

**Day 1-3: WebSocket 基础**
- [ ] 实现 `WebSocketTransport` actor
- [ ] 实现消息序列化/反序列化
- [ ] 实现自动重连机制
- [ ] 编写 WebSocket 集成测试
- **产出**: WebSocket 连接可用，能收发消息

**Day 4-6: 音频引擎**
- [ ] 实现 `AudioCaptureEngine` (16kHz PCM)
- [ ] 实现 `AudioPlaybackEngine` (流式播放)
- [ ] 实现音频格式转换
- [ ] 测试音频采集质量（SNR, 录音清晰度）
- **产出**: 音频双向通路打通

**Day 7-10: 对话控制器**
- [ ] 实现 `DialogueController` (轮次管理)
- [ ] 实现 VAD 静音检测
- [ ] 实现音频数据流水线
- [ ] **首响延迟性能测试**
- **产出**: 端到端对话流程，首响延迟数据

### 2.3 验收标准

| 指标 | 目标 | 测试方法 |
|------|------|----------|
| WebSocket 稳定性 | 99% 连接成功率 | 100 次连接测试 |
| 音频质量 | SNR ≥ 20dB | 音频质量测试 |
| **首响延迟 P90** | **≤ 1.5s** | **100 轮对话压测** |
| 音频播放连续性 | 无卡顿、爆音 | 人工听测 |

### 2.4 GO/NO-GO 决策

**Week 2 结束前必须验证**:

```
✅ GO 条件:
- 首响延迟 P90 ≤ 1.5s
- 音频质量合格
- WebSocket 稳定

❌ NO-GO 风险:
- 首响延迟 > 2s → 需要后端优化或架构调整
- 音频严重卡顿 → 需要优化音频处理链路
```

**如果 NO-GO**: 暂停后续开发，集中资源优化延迟/音频问题。

## 附录：关键决策记录

### A.1 为什么选择 Actor 模式？

**原因**:
- 天然线程安全，避免数据竞争
- 与 Swift Concurrency 完美集成
- 清晰的状态隔离

**权衡**:
- 学习曲线稍高
- 需要 iOS 17+ (但我们的目标就是 iOS 17+)

### A.2 为什么选择 SwiftData？

**原因**:
- Swift-first，类型安全
- 与 SwiftUI 深度集成
- 性能优秀

**权衡**:
- 成熟度不如 Core Data
- 需要 iOS 17+

### A.3 为什么 Week 2 设置 GO/NO-GO？

**原因**:
- 首响延迟是核心体验，如果无法达标，后续功能都无意义
- 越早发现问题，调整成本越低
- 避免在错误方向上浪费资源
